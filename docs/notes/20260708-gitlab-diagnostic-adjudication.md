# GitLab onboarding diagnostic adjudication (2026-07-08)

Source: `rigor-survey/gitlab` fresh `rigor check` onboarding, 3,909 diagnostics
(289 error / 238 warning / 3,382 info). Adjudicated read-only from
`_reports/init/gitlab.check.txt` + `gitlab.triage.json` against the real
GitLab source at `~/repo/ruby/rigor-survey/gitlab`. No `rigor` CLI was run for
this note (cache contention with a concurrent run).

Context: `db/schema.rb` is absent (GitLab ships `structure.sql`), so
`rigor-activerecord` loads in **inert** mode — every AR call check is
skipped, and (as this note documents) that inertness also **cascades** into
misinference of ordinary AR query-chain calls. 729 locked gems ship no RBS.
Active plugins: actionpack, activerecord (inert), actionmailer, rails-routes,
rails-i18n, activesupport-core-ext, devise, sidekiq, dry-types, sorbet.

## 5. Confirmed genuine bugs (2)

1. **`lib/system_check/incoming_email/imap_authentication_check.rb:39`** — `@error` is assigned a `String` on the "no mailboxes configured" path but `show_error` unconditionally calls `@error.class` / `@error.message`, which only `Exception` supports. Consistent with the "production works" heuristic rather than defeated by it: the crashing branch only runs during a `gitlab:check`-style admin diagnostic against a *misconfigured* install, so the error reporter crashes exactly when it is needed — a latent bug production traffic never exercises.
2. **`lib/uploaded_file.rb:42`** — `@upload_duration` rescue-branch default is the integer `0` instead of the `Float` `0.0` used on the happy path. Harmless at runtime (Ruby numeric coercion) but a real, fixable inconsistency; severity-appropriate as a `:warning`.

(Two further candidates — the `access_tokens_helper.rb:61-62` route-helper calls — were initially adjudicated GENUINE and **retracted on audit**; see #7 in §2. Rails' own `mapper.rb` naming rules generate exactly the helpers the code calls.)

## 6. Anomalies worth flagging

- **Triage "genuine-bugs" heuristic under-performs its confidence label.** Only 2/11 hint entries were genuine (18%, vs. its "likely" label). The low-count/scattered-rule signal is a weak proxy for "genuine" here — `def.ivar-write-mismatch` (2/2) was strong, `call.argument-type-mismatch` (0/5) and `plugin.rails-routes.wrong-arity` (0/3) were not, both dominated by systematic FP mechanisms rather than one-off defects.
- **Adjudication itself needs the "production works" cross-check.** Two `unknown-helper` sites were initially (and confidently) adjudicated GENUINE from a hand-derivation of Rails route naming, then overturned by reading the actual actionpack `mapper.rb` — the code was right and the plugin's model wrong. Verdicts of GENUINE on hot production paths (a page that demonstrably renders) should be treated as presumptively-FP until confirmed against the framework's own source, exactly the FP-cost weighting the discipline prescribes. Conversely #17 shows the inverse care: "production works" does *not* clear code on cold error-handling paths that production never exercises.
- **AR inertness has a wider blast radius than "AR checks are skipped".** It also degrades ordinary scope-chain calls to `Array`-typed receivers, which then collide with real ActiveSupport `Array` core-ext methods (`#from`) to produce phantom argument-type-mismatch diagnostics, not just phantom undefined-method ones. A `structure.sql`-as-schema-source capability (rather than just documenting the limitation) would close this at the root for every `structure.sql`-using Rails project, which is common at GitLab's scale.
- **`actionmailer.missing-view` mixin misattribution is a distinct, mechanically-verifiable bug**, independent of the false-positive-worthiness debate: the reported line number is correct for the *defining* module file but the reported file path is the *including* class's file. Cheap, high-confidence fix.
- **`grape-path-helpers` is a materially large single mechanism** (68/159 = 43% of `unknown-helper`, 68/527 = 13% of all errors+warnings) — the single highest-value fix candidate by raw count after the two "expected/inherent" mechanisms (Hash#[] nilability, AR inertness).
