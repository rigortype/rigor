# Rigor 0.2.x problem survey — type theory and Ruby runtime type model

Date: 2026-06-22. Status: **research note, no design commitments.** This
records a problem inventory for the Rigor `0.2.x` evaluation line, with v0.2.1
as the latest released cut and post-v0.2.1 master already carrying the
SKILL-driven UX work. It is a snapshot of concerns, not a normative contract:
`docs/type-specification/`, `docs/internal-spec/`, and ADRs bind when they
disagree with this note.

## Scope

The review asks: what are the current pressure points in Rigor when viewed from
both:

1. **type theory** — lattice design, gradual typing, erasure, normalization,
   structural typing, effects, and inference termination; and
2. **Ruby's runtime type system** — method lookup, open classes, dynamic
   reflection, DSLs, mutation, blocks, core extensions, and RBS coverage gaps.

The premise is important: Rigor is intentionally not a soundness-first proof
system. The core product shape is a false-positive-disciplined Ruby static
analyzer. It reports only when the evidence is strong, and otherwise prefers
`Dynamic`, `maybe`, conservative widening, or silence over speculative alarms.
That is a good Ruby-facing product choice, but it leaves real type-system and
runtime-model tensions that the rest of this note enumerates.

## Framing: practical precision over proof-oriented soundness

Rigor's current design is best read as:

- preserve RBS compatibility;
- infer richer internal facts than RBS can spell;
- keep dynamic-origin loss explicit through `Dynamic[T]`;
- model Ruby truthiness, equality, reflection, and method lookup as Ruby does;
- minimize false positives on working code;
- use plugins, RBS, generated signatures, and overlays to recover precision at
  dynamic framework boundaries.

This is not the same as saying "a clean Rigor run proves the program safe." A
clean run means the analyzer did not find a conclusive diagnostic under the
configured evidence base. The distinction matters for CI policy, public API
contracts, security boundaries, and future strict modes.

## Type-theory pressure points

### 1. `Dynamic[T]` is semantically strong but operationally expensive

Rigor correctly refuses to collapse RBS `untyped` into `top`:

```text
untyped = Dynamic[top]
```

`Dynamic[T]` records both a static facet and the fact that the value crossed an
unchecked boundary. That gives Rigor a better gradual-typing story than treating
`untyped` as ordinary safe-top. The cost is that every relation, narrowing rule,
diagnostic, strict mode, generic slot, and erasure path must preserve the
separation between:

- a statically known fact about the value; and
- the provenance that this fact came through unchecked or incomplete evidence.

The current open problem is not the algebra itself; it is the provenance
surface. `CURRENT_WORK.md` explicitly calls out that coverage-tractability labels
need better `Dynamic` provenance tracking: a protection hole should be able to
say whether the receiver became dynamic because of an external gem without RBS, a
framework DSL, an analyzer cutoff, a plugin-declared dynamic result, or an
explicit `untyped` contract. Without that, strict dynamic diagnostics and
coverage guidance can explain too little.

### 2. Subtyping and gradual consistency are cleanly separated but easy to blur

The spec distinguishes:

```text
A <: B
consistent(A, B)
```

Subtyping is value-set inclusion. Gradual consistency is boundary compatibility
when dynamic-origin values participate. That separation is the right theoretical
move, but it creates a load-bearing implementation invariant:

- method availability must use the static facet;
- typed boundary crossings must use consistency;
- diagnostics must retain the dynamic-origin explanation.

If any call path treats dynamic consistency as proof of subtyping, Rigor can
silently accept dynamic facts as static evidence. If any call path normalizes
`Dynamic[top]` to `top`, strict-mode explanations and source attribution are
lost. This is a continuing audit surface rather than a single feature gap.

### 3. RBS erasure is intentionally lossy

The RBS-to-Rigor direction is lossless, but the Rigor-to-RBS direction is not.
Internal facts such as literals, integer ranges, tuple positions, hash shapes,
refinements, negative facts, object shapes, and dynamic-origin provenance must be
erased to ordinary RBS when exported.

That is necessary for ecosystem compatibility, but it means:

- `sig-gen` output cannot fully represent the analyzer's internal proof state;
- rerunning from exported RBS may not recover the same precision;
- existing RBS can be more accurate than a seemingly tighter inferred return;
- dynamic provenance may disappear at the persistence boundary;
- hash-shape and literal-union precision has to be guarded by erasure budgets.

This is especially visible in the repository's own sig-gen discipline: a
`tighter-return` suggestion that drops union members is treated as a likely
inference incompleteness, not an automatic improvement.

### 4. Normalization mixes extensional value equality with diagnostic evidence

Pure value-set reasoning would simplify:

```text
1 | Integer = Integer
```

Rigor deliberately does not always collapse such unions. A value-pinned member
can carry evidence: a recursion base case, a zero-iteration seed, or another
reachable exact value that is useful for display and later value-aware
consumers. This is a pragmatic choice, but it means internal type identity is not
only extensional value equality. It also carries proof-shape and provenance-like
information.

The risk is conceptual and mechanical:

- cache keys, displays, equality checks, and normalization must remain stable;
- contributors can mistake provenance-preserving normalization for ordinary
  subtype simplification;
- the boundary between "type" and "evidence about how the type was learned"
  stays blurry.

### 5. `maybe` is safe but weak for inference

Rigor's trinary relation result is:

```text
yes / no / maybe
```

The rule that `maybe` must not narrow as `yes`, must not produce a false-edge
complement as `no`, and must not become `yes` merely by repetition is essential
for false-positive control. The tradeoff is that many Ruby-valid guarded shapes
remain weakly typed unless a plugin, RBS contract, or `RBS::Extended` effect
promotes the relation into a proof.

This is most visible near dynamic reflection:

- `respond_to?` can prove existence more easily than signature compatibility;
- `method_missing` can only be typed precisely with extra facts;
- unknown equality and case-equality methods remain relational, not narrowing,
  facts.

### 6. False-positive discipline limits proof-oriented uses

Rigor's false-positive discipline says that a running, working program is strong
evidence, and speculative diagnostics are worse than missed alarms. That stance
is product-defining. The cost is that Rigor should not be marketed or used as a
sound proof that a program cannot fail at runtime.

A clean Rigor run is therefore weaker than a clean run from a soundness-first
checker would be. This matters for:

- security-sensitive trust boundaries;
- public library API contracts;
- large mechanical refactors;
- strict CI gates;
- claims about runtime safety.

The right user-facing story is: Rigor is a high-signal bug finder and gradual
adoption tool, not a formal proof system.

### 7. The robustness principle is intentionally asymmetric

Rigor-authored types follow the robustness principle: strict returns, lenient
parameters. This improves downstream precision and avoids coercion noise at call
sites, which fits Ruby practice. It also means generated or inferred contracts
can be asymmetric relative to the implementation's true requirements.

Potential problems:

- parameter contracts may be too wide to document an API's intended capability;
- call-site bug detection can be weaker when accepted inputs are deliberately
  permissive;
- public RBS generated from inference may differ from the API design a library
  author wants;
- role/capability inference becomes important to avoid both nominal
  over-tightening and parameter over-widening.

### 8. Structural typing is bounded but not yet complete

Rigor keeps classes and modules nominal, while using RBS interfaces and inferred
object shapes for structural duck typing at specific boundaries. This is the
right Ruby/RBS compromise, but the hard parts remain expensive:

- complete method compatibility must compare visibility, arity, positional and
  keyword parameters, blocks, overloads, returns, and receiver constraints;
- named-interface matching can become a candidate-search problem;
- anonymous object shapes erase poorly when no named interface exists;
- capability-role requirement inference from method bodies is still deferred;
- `structural_growth` and `interface_candidates` are specified as budgeted
  dimensions, but the configurable budget surface is not wired.

This area is central because it is the type-theoretic form of Ruby duck typing.

### 9. The inference-budget specification is ahead of the implementation

`inference-budgets.md` defines a configurable `budgets:` table, including
recursion depth, call-graph width, overload candidates, operator ambiguity, union
size, structural growth, interface candidates, and hash erasure dimensions. The
same document records that, as of the cited implementation status, the
configurable surface is not yet wired. Only a smaller set of hard-coded guards
and the dependency-source-inference per-gem budget are operative.

Consequences:

- users cannot yet tune most intended cutoff dimensions;
- some expensive search shapes remain controlled only by ad hoc or hard-coded
  limits;
- cutoff diagnostics do not yet expose the full intended taxonomy;
- the spec describes a cleaner termination model than the implementation
  currently provides.

This is less a theoretical flaw than a product-completion gap before v1.0.0.

### 10. The effect system is partial

Rigor needs effects to keep flow facts sound across mutation, aliasing, method
calls, and block invocation. The spec has the right categories: local binding,
captured local, object content, global storage, dynamic-origin, relational facts,
mutation summaries, purity, and block-call timing. The shipped surface is still
partial, and full cross-statement mutation-effect propagation is deferred.

The main risk is that Ruby precision often depends less on nominal class and more
on whether a fact is stable:

```ruby
h = {foo: 1}
some_call(h)
h[:foo]
```

Without an effect summary for `some_call`, the hash-shape fact must be weakened.
Keeping it is unsound; dropping it loses useful precision. This tradeoff repeats
for arrays, strings, instance variables, globals, closures, callbacks, and DSL
APIs.

### 11. Parameter inference, recursion, and higher-order calls remain constrained

Recursive return precision and user-method return adoption have improved, but
`CURRENT_WORK.md` still treats ADR-67 main-check parameter inference as a queued,
careful step rather than an unconditional win. Feeding inferred parameter types
into the check walk can expose downstream false positives if callee inference is
not precise enough.

Higher-order calls add the same pressure: block timing, closure writes,
non-local effects, and call-count knowledge determine whether facts can be kept.
Rigor has the categories, but the useful coverage depends on summaries for core
methods and plugins for framework callbacks.

### 12. Lightweight HKT is useful but deliberately narrow

Rigor's defunctionalized `App[F, A]` style HKT support is a practical mechanism
for selected APIs, such as return discrimination. It is not a general type-level
language comparable to TypeScript's conditional, mapped, and indexed-access type
system.

That restraint protects RBS compatibility and keeps the analyzer tractable, but
it means many expressive type-level relationships must be encoded through
plugins, `RBS::Extended`, hand-written RBS, or conservative erasure.

## Ruby runtime type-model pressure points

### 1. Open classes, monkey patches, and load order are fundamental hazards

Ruby's type surface is the method table after code has been loaded, not merely
the class body visible in one source file. Reopens and monkey patches can replace
or add methods at any point:

```ruby
class String
  def application_specific_slug
    # ...
  end
end
```

Rigor has to approximate load order, last-definition-wins behavior, ancestors,
plugins, overlays, pre-evaluation, and framework initialization. The current
self-call undefined-method experience shows the risk: the rule remains shipped
off because abstract/template-method patterns and subclass-provided methods
produce false positives under a local per-class view.

### 2. `method_missing` and `respond_to_missing?` separate existence from type

Ruby DSLs often expose methods through `method_missing`. `respond_to?` can prove
that a send might be accepted, but it does not prove the method's arity,
keyword/block contract, return type, visibility, mutation effect, or purity.

Rigor's model treats such facts as dynamic-provenance or existence-only facts
unless a plugin or signature supplies more. That is correct but leaves many real
Ruby APIs dependent on plugins. ActiveRecord dynamic finders, routes, I18n,
GraphQL fields, dry-rb schemas, and other DSL surfaces all live near this edge.

### 3. `define_method`, `class_eval`, `instance_eval`, and macros build methods outside `def`

Ruby method definitions can be generated by ordinary Ruby execution:

```ruby
define_method(:name) { @name }
class_eval("def generated; end")
```

Framework macros go further:

```ruby
has_many :posts
scope :published, -> { where(published: true) }
validates :name, presence: true
```

Rigor's macro substrate and plugin system are the right extension point, but the
problem remains open-ended. Without a plugin or generated RBS, dynamic methods
usually collapse to `Dynamic`, unresolved calls, or conservative silence. Sig-gen
also records dynamic methods and DSL macros as places where project plugins are
the right answer.

### 4. `include`, `prepend`, refinements, and ancestor lookup are hard to replay

Ruby method lookup is sensitive to singleton classes, prepended modules, the
class itself, included modules, superclasses, refinements, and `method_missing`.
`prepend` changes override order and `super` behavior. Refinements are lexical
and depend on `using` scope. Includes and visibility changes are order-sensitive.

Rigor has improved ancestor resolution, but complete replay of Ruby's runtime
lookup remains one of the most fragile parts of the model, especially when Rails
concerns, conditional includes, or environment-specific requires participate.

### 5. Singleton methods, eigenclasses, class objects, and dynamic constants complicate the class model

Ruby classes are objects, and any object may receive singleton methods:

```ruby
obj = Object.new

def obj.special
  1
end
```

RBS provides `singleton(C)`, and Rigor intentionally prefers class/module objects
over PHP-style class-name strings. Still, factory APIs, `const_get`, autoload,
namespace-sensitive constant lookup, singleton class mutation, and dynamically
built classes remain difficult to model precisely. Class-name-string projection
is deferred for good Ruby-shaped reasons, but some factory patterns will remain
weak until class-object relationships are richer.

### 6. Ruby equality and case equality are method dispatch

In Ruby, `==`, `eql?`, and `===` are not built-in logical equality relations.
They are method sends and can be overridden. Rigor therefore only narrows on a
narrow trusted equality surface: identity facts, nil/boolean checks, and selected
finite literal domains with stable built-in dispatch. Floats, user-defined
`==`, `Range`, `Regexp`, `Module`, `Class`, and general `===` need explicit rules,
RBS metadata, or plugin effects.

The cost is limited case narrowing and exhaustiveness. That is the right
false-positive tradeoff, but it leaves common Ruby `case` idioms under-modeled.

### 7. `send`, `public_send`, and reflection erase static dispatch information

Dynamic dispatch through a computed method name defeats ordinary method lookup:

```ruby
obj.public_send(name, *args)
```

Literal method names can sometimes be recovered. Computed names, user-input
names, private calls through `send`, reflective method objects, and dynamic
argument forwarding generally require plugins or fall back to dynamic-origin
facts. This is a core Ruby runtime feature, not an edge case.

### 8. Instance variables, class variables, globals, and constants have weak stability

Ruby instance variables are untyped, declaration-free storage. They can be read
before assignment, assigned conditionally, set by callbacks, exposed by
accessors, or mutated through methods Rigor does not see. Class variables,
globals, and constants are even more global in their invalidation behavior.

Rigor has shipped useful precision such as ivar guard narrowing, but heap and
global-storage facts must remain more fragile than local binding facts. This
limits precision in idiomatic object-oriented Ruby, especially Rails lifecycle
code.

### 9. Aliasing and mutation challenge shape precision

Hash shapes, tuple-like arrays, and refined objects are only stable while the
analyzer can prove no alias or call mutated them. Ruby's default object model is
mutable and alias-heavy:

```ruby
h = {a: 1}
g = h
g[:a] = nil
h[:a]
```

`freeze`, `dup`, and `clone` are not trivial escapes. `CURRENT_WORK.md` warns not
to preserve shape carriers through `freeze` / `dup` before resolving the related
truthiness interaction. This points to a larger ownership/effect problem: Rigor
wants shape precision, but Ruby does not give the analyzer linearity, uniqueness,
or immutable-by-default guarantees.

### 10. Blocks, procs, lambdas, and callbacks make timing part of typing

Whether a block runs immediately, later, never, once, or many times changes the
facts that hold after the call:

```ruby
x = nil
[1].each { x = "hello" }
x.upcase
```

The example is only safe if the analyzer knows the block runs in time. Callback
registration, enumerator conversion, `Proc#call`, lambdas, non-local returns,
and framework lifecycle hooks make this hard. Rigor has block-timing categories,
but high precision requires a broad catalog of method summaries and plugin facts.

### 11. Core extensions change the runtime type surface

ActiveSupport-style extensions add methods to core classes:

```ruby
3.minutes
"name".present?
```

v0.2.1's Gemfile.lock-gated ActiveSupport core-ext RBS overlay fixed a concrete
false-positive source around `3.minutes`. The larger lesson is that Ruby's type
surface depends on the loaded gem world, not only Ruby's core classes. Rigor must
continue combining Gemfile.lock detection, overlays, plugins, and RBS discovery to
approximate that loaded world.

### 12. C extensions and stdlib RBS gaps block precision

Many core and stdlib methods are implemented in C or external native extensions.
Rigor cannot infer those bodies from Ruby source. It needs RBS, overlays,
constant-fold catalogs, imported refinements, or plugin rules. A small upstream
RBS gap can surface as a real false positive, as seen in the StringScanner
example recorded in `CURRENT_WORK.md`.

This creates a continuing maintenance stream:

- identify RBS gaps through real corpus failures;
- add focused overlays when the issue is user-facing;
- upstream fixes to `ruby/rbs` when possible;
- avoid over-folding native methods whose semantics are format-, locale-, or
  state-dependent.

## Prioritized current problem list

The following are the highest-leverage issues exposed by the survey, ordered by
expected impact rather than implementation size.

1. **`Dynamic[T]` provenance tracking.** Needed for tractability labels,
   strict dynamic diagnostics, and actionable protection coverage.
2. **Configurable inference budgets.** The spec's `budgets:` table is ahead of
   the implementation; `union_size`, `structural_growth`, and related limits need
   either wiring or explicit re-scoping before v1.0.0.
3. **Effect and mutation summaries.** Precision depends on knowing which calls
   mutate, escape, store, or invoke blocks.
4. **Capability-role requirement inference.** This is the type-theoretic form of
   Ruby duck typing and remains a deferred high-value surface.
5. **Plugin dependence and plugin coverage.** Real Ruby frameworks need plugins;
   missing plugin facts become `Dynamic`, false positives, or false negatives.
6. **Dynamic method and macro typing.** `define_method`, DSL macros, and
   generated framework methods remain hard for both check and sig-gen.
7. **Open-class and load-order modeling.** Monkey patches, core extensions, and
   template-method patterns make local static lookup insufficient.
8. **`method_missing` signature recovery.** Existence facts are not full method
   contracts; plugins or metadata need to fill the gap.
9. **Lossy RBS erasure.** Internal precision and dynamic provenance disappear at
   the RBS boundary, complicating sig-gen and re-analysis.
10. **False-positive discipline versus soundness claims.** The product should
    keep presenting itself as a high-signal analyzer, not a formal safety proof.

## Follow-up tracks suggested by this survey

This note does not decide work, but it suggests useful tracks:

- design and implement first-class `Dynamic` source/provenance categories;
- re-evaluate the configurable budget table before v1.0.0: either wire it, split
  it into shipped versus target budgets, or mark rows as explicitly future;
- continue expanding effect summaries for core/stdlib methods that preserve or
  invalidate common shape facts;
- finish or explicitly defer capability-role requirement inference with a clear
  user-facing explanation;
- keep running external corpus diffs before widening diagnostics on union,
  nilable, dynamic, or structural receivers;
- collect DSL/macro gaps from sig-gen and baseline-reduction sessions into plugin
  opportunities;
- treat RBS overlay fixes as part of the product surface, not incidental test
  patches.

## Non-goals

This note does not propose replacing RBS, changing the false-positive discipline,
turning Rigor into a soundness-first checker, or importing a general TypeScript-
style type-level language. The point is to name the tensions Rigor must manage
while staying Ruby-shaped and RBS-compatible through the `0.2.x` evaluation line.
