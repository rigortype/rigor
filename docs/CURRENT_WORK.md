## Gotchas (load-bearing, learned the hard way)

- **ADR-46** — do NOT extract the `Runner#initialize` ivar pre-seeds (`@class_decl_paths_snapshot = {}` etc.) into a helper; moving them out of the constructor hides them from the engine's OWN flow analysis and `make check` self-flags `snapshot.size` as a nil-receiver false positive. Keep them inline (the constructor carries an `AbcSize` disable).
- **ADR-45** — `@collect_stats` is true by default (can't gate the cache on it; a hit returns nil stats); a lazy `@io_boundary ||=` on a frozen plugin → `FrozenError` (use `instance_variable_get`); a cache write / serialize failure is swallowed (never breaks a run).
- **ADR-24** — a check-rules *reimplementation* of self-call resolution diverges from the engine's real one (which already handles `module_function` / `Data.define` accessors / mixins for precision) → 135 FPs (reverted). The landed route is the evaluation-time `SelfCallResolutionRecorder` ("collect, don't recompute").
- **ADR-62 / ADR-63** — `make verify` gates only `lib` + `plugins`; the **external corpus can still expose false positives** from receivers Rigor mistypes. A union/nilable undefined-method rule inherits the scalar rule's "only as good as the inferred type" exposure — the nilable study caught a `Hash | Hash`#pack FP on mail (`compose_codepoints` mistyped an `Array`). Run a `rigor-survey` corpus diff (`cd $proj; BUNDLE_GEMFILE=$rigor/Gemfile nix develop $rigor -c bundle exec $rigor/exe/rigor check --format json $paths`) before trusting any diagnostic-widening on union / nilable receivers. Also: the inference scanners (`PrecisionScanner` / `ProtectionScanner`) are NOT autoloaded by `require "rigor"` (require them explicitly, as their specs do); rubocop enforces annotated `%<name>s` format tokens; and a `Data.define(:method, …)` member shadows `Data#method` (use `:method_name`).
- **Self-mutation (Product C, `tool/mutation/self_mutate.rb` — mutate `lib/rigor` itself, kill by self-check ∪ Rigor's own rspec)** — the `--coverage-gap` whole-tree hole count is meaningless without **method-coldness** de-noising: Ruby line-coverage credits a multi-line expression to its FIRST line, so the continuation lines of a *covered* expression (a tested `to_h`'s hash-literal entries) read as uncovered. Count a hole only inside an entirely-uncovered `def`; exclude class-body/constant sites (data, not logic). That de-noise took the raw whole-tree count **1969 → 22** on `lib/rigor` (all in `cli/mcp_command`, now closed — the unit suite is otherwise method-level complete). The test axis needs an **in-bundle** rspec runner — NOT `with_unbundled_env`, which is for a *foreign* project's Gemfile and breaks Rigor's own suite. The effectiveness tier (covered-but-not-asserted) is worked per-file via the fused mode and converges on an equivalent-mutant floor (message/inspect text), not zero. Living tracker: [`docs/notes/20260618-self-mutation-testing-plan.md`](notes/20260618-self-mutation-testing-plan.md); roadmap entry under § "Analyzer self-testing".
- **bench-perf** — the Make target is `bench-perf`, not `bench` (the bare name collides with the `bench/` data directory; the file keeps its no-`.PHONY` convention). The `release-gate.yml` workflow that runs it on a `release/x.y.z` push is **advisory during the `0.2.x` trial** — it reports but does not block the merge (`ci.yml` is the required gate); the signal is still release-quality and worth reviewing. Both baselines (`bench/baseline.json` perf targets + `data/oss-sweep/mastodon-thresholds.json`) are **recalibrated only when the deterministic signals drift** — the v0.2.0 cut set lib allocations ≈18.77 M / peak RSS ≈232 MB / wall 13.75 s and Mastodon `app lib config` to 468 diagnostics at min precision 0.4284; **v0.2.1 held both unchanged** (allocations ≈19.3 M stayed within band, sweep green). These are exact-count / banded gates with little headroom, so a precision or allocation change flips them red **until recalibrated, by design**. Recalibrate perf from the **CI-measured Linux values** in the failed run's log (allocations is the deterministic signal; **wall_s is noisy → `gh run rerun --failed` clears a wall-only flake, never recalibrate the baseline for wall alone** — v0.2.1's only red was exactly this), and **diff the OSS-sweep diagnostics for false positives before blessing a higher count** (the v0.2.0 recalibration found 3 `StringScanner#[]` FPs → fixed via `data/core_overlay/string_scanner.rbs`, not blessed into the threshold).
