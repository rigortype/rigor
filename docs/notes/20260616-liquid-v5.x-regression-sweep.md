# liquid v5.x regression sweep — baseline-drift over a full major line

**Date:** 2026-06-16. **Rigor:** v0.1.19 (`master`, HEAD `3c43864c`).
**Target:** `Shopify/liquid`, 32 tags `v5.0.0` → `v5.12.0`.

Third run of the [`rigor-regression-sweep`](../../.claude/skills/rigor-regression-sweep/SKILL.md)
procedure, after the Mastodon v4.5.x
([`20260521-mastodon-v4.5-regression-sweep.md`](20260521-mastodon-v4.5-regression-sweep.md))
and Redmine 6.x
([`20260521-redmine-6.x-regression-sweep.md`](20260521-redmine-6.x-regression-sweep.md))
sweeps. Three firsts for the corpus:

- **First non-Rails target** — both prior sweeps were Rails apps with the
  `rigor-activesupport-core-ext` RBS bundle wired. liquid is a pure Ruby
  library: no plugins, no bundled `sig/`, **pure inference** — every type
  Rigor knows about liquid, it inferred.
- **First full-major-line sweep** — the entire `v5.x` series (v5.0.0 →
  v5.12.0, ~4 years), not a patch window plus one minor bump.
- **First sweep to surface two genuine Rigor false positives** — both
  **self-cleared by liquid's own churn**, which is exactly why a frozen
  baseline + a moving project is the right instrument for finding them.

## Setup

- Blobless clone of `Shopify/liquid`; 32 tags in release order
  (`v5.0.0 v5.0.1 v5.1.0 … v5.5.1`, the `v5.6.0.rc1/rc2/rc3` RCs,
  `v5.6.0 … v5.8.7 v5.9.0 v5.10.0 v5.11.0 v5.12.0`).
- **Frozen config** (`.rigor.dist.yml`, held byte-identical across every
  tag): `paths: [lib]`, `target_ruby: "3.3"`, `severity_profile: lenient`,
  **no plugins, no `signature_paths`**, `cache.path` absolute under
  `_liquid-sweep/`. `target_ruby` is "3.3" by the Redmine precedent —
  liquid declares `>= 2.5.0` at v5.0.0 and `>= 3.0.0` at v5.12.0, and the
  onboarding guide writes Prism's 3.3 floor.
- Baseline at `v5.0.0`: **4 diagnostics / 4 buckets** (rule mode) —
  `context.rb` `flow.always-truthy-condition`, `profiler.rb`
  `call.undefined-method`, `profiler.rb` `flow.always-truthy-condition`,
  `tags/if.rb` `call.possible-nil-receiver`. A clean zero point (cf.
  Redmine's 145).
- `lib` scope: 59 `.rb` files at v5.0.0, 63–65 across the v5.6+ tags.

## Result — flat zero with three transient single-event blips

| Tag(s) | raw | silenced | **surfaced** | what |
| --- | --- | --- | --- | --- |
| v5.0.0 … v5.5.0 | 4 | 4 | **0** | baseline holds |
| **v5.5.1** | 5 | 4 | **1** | `rbs.coverage.missing-gem` (info) |
| v5.6.0.rc1 … **v5.6.0** | 15 | 4 | **11** | `call.undefined-method` (error) |
| v5.6.1 … v5.9.0 | 4 | 4 | **0** | back to baseline |
| **v5.10.0** | 5 | 4 | **1** | `call.possible-nil-receiver` (warning) |
| v5.11.0, v5.12.0 | 4 | 4 | **0** | back to baseline |

Three distinct events, each lasting exactly one release (or one RC→GA
window) and each **cleared by the next tag** — no event persisted, none
compounded. The baseline absorbed an essentially rewritten library
(see churn cross-check) with three momentary breaches, all explained
below. Two of the three are genuine Rigor false positives; the third is
a project lockfile-churn artifact.

### Event 1 — the +11 `call.undefined-method` at v5.6.0 (the headline)

All 11 are `undefined method 'peek_byte' / 'scan_byte' for StringScanner`
in `lib/liquid/lexer.rb`. The story is a textbook FP-discipline
interaction:

- **The methods are real.** `StringScanner#peek_byte` and `#scan_byte`
  ship in `strscan` 3.1.0 (bundled with Ruby 3.4). liquid's v5.6.0 lexer
  rewrite (`8ecb703 use StringScanner to improve Expression Parsing and
  Tokenizer`) adopted them. liquid is correct; **Rigor is wrong.**
- **The RBS gap is a pinned-gem lag.** Rigor's runtime type environment
  comes from `RBS::EnvironmentLoader.new` → `RBS::Repository::DEFAULT_STDLIB_ROOT`,
  i.e. the **`rbs` gem** — pinned at **`rbs (4.0.2)`** in `Gemfile.lock`.
  In 4.0.2's `stdlib/strscan/0/string_scanner.rbs`, `peek_byte`/`scan_byte`
  appear **only in a doc-comment table** — there is no `def peek_byte` /
  `def scan_byte`. Upstream `rbs` already fixed this
  (`references/rbs` `3f807b44`, 2026-05-21, "Update StringScanner
  signatures to match strscan 3.1.6" — the submodule HEAD v4.1.0.pre
  declares both at lines 1023/1281), but that landed **after** the
  4.0.2 cut. (The vendored `references/rbs` feeds the builtins **catalog**,
  not the live dispatch env — so its having the methods does not help the
  run.)
- **It fires only at v5.6.0 because the receiver was concretely typed.**
  v5.6.0's lexer is an instance with `@ss = StringScanner.new(input)`
  (`lib/liquid/lexer.rb:29`) → `@ss` types as a concrete `StringScanner`,
  so `@ss.peek_byte` resolves against StringScanner's RBS, misses, and
  fires.
- **It clears at v5.6.1 not because the methods left, but because the
  receiver became `Dynamic`.** The v5.6.1 refactor (`04bd9db refactor
  Lexer to only take StringScanner`, `7c592c1 store StringScanner in
  ParseContext`) turned the lexer into a static `def tokenize(ss)` taking
  the scanner as an **unsignatured parameter**. `ss.peek_byte`/`scan_byte`
  are *still called* at v5.6.1 → v5.12.0 (in `lexer.rb`, `tokenizer.rb`,
  `expression.rb`), but on a `Dynamic` receiver — and Rigor never fires
  `call.undefined-method` on `Dynamic` by FP discipline. So the same
  latent RBS gap goes invisible. **The clear is precision-masking, not a
  fix.**

**Take-away / feedback:** a real `strscan` RBS-coverage gap in the pinned
`rbs` gem, surfaced *only* when the receiver is concretely typed. Fix =
bump the pinned `rbs` gem to ≥ 4.1.0 once released (the methods are
already upstream; the `references/rbs` `widen-strscan-resolv-stdlib-sigs`
WIP branch widens `StringScanner#[]`/`Resolv#initialize` but is unrelated
to these two). This is the inverse lesson of the Mastodon/Redmine
flat-curve runs: on a **library that tracks new stdlib APIs**, a frozen
Rigor pin will momentarily false-positive exactly where the project moves
ahead of the pinned `rbs`.

### Event 2 — the v5.5.1-only `rbs.coverage.missing-gem` (a lockfile artifact)

A single `info` on `.rigor.yml`: "22 gem(s) in Gemfile.lock have no RBS
available". It appears at **v5.5.1 and nowhere else** because liquid
**tracked a `Gemfile.lock` only at that one tag** (`git ls-tree`:
tracked at v5.5.1, untracked at v5.5.0 / v5.6.0.rc1 / v5.6.0 / v5.12.0 —
a gem normally gitignores its lockfile; v5.5.1 committed one by accident
and dropped it next release).

**Methodology finding** (a cousin of the Redmine parse-error floor): a
**project-level** diagnostic keyed to the synthetic `.rigor.yml` path
with no source line. The baseline at v5.0.0 had no `Gemfile.lock`, so it
never bucketed this rule; when the input file later materialises, the
diagnostic surfaces past the frozen envelope. It is `info` severity and
harmless in acknowledge mode, but it shows the baseline tracks *input
state*, not just *source code* — a transient build-artifact in the tree
can move `surfaced` by one. Unlike the Redmine floor it is **not** a
constant (it tracks the lockfile's presence), and needs no `exclude:`.

### Event 3 — the v5.10.0 `call.possible-nil-receiver` (a confirmed Rigor FP)

`possible nil receiver: 'render_to_output_buffer' is undefined on
NilClass` in `lib/liquid/tags/render.rb`. At v5.10.0, `render_tag`
assigns a local across a three-arm conditional and reads it afterwards:

```ruby
if template.respond_to?(:to_partial)
  partial = template.to_partial            # Dynamic-typed arm
elsif @template_name_expr.is_a?(String)
  partial = PartialCache.load(template, …) # concrete arm
else
  raise ::ArgumentError                    # exhaustiveness via raise
end
# … partial.render_to_output_buffer(…)      # ← spurious possible-nil
```

`PartialCache.load` never returns nil at runtime (it returns a truthy
`cached` or the parsed partial), and the `else` raises — so `partial` is
assigned on every reachable path. The warning is a **false positive**,
reduced to an 8-line minimal repro and bisected:

| Shape | fires? |
| --- | --- |
| 2-arm `if/else: raise`, single concrete arm | no |
| 3-arm `if/elsif/else: raise`, two **concrete** arms | no |
| 3-arm `if/elsif/else: raise`, one **Dynamic** + one concrete arm | **yes** |
| bare `Dynamic` receiver (no conditional) | no |
| ternary / 2-arm `if/else` (no `raise`) `Dynamic`-or-concrete | no |

So the trigger is the conjunction of: a conditionally-introduced local,
**exhaustiveness established via `else: raise`**, and a **`Dynamic |
concrete` union** among the assigning arms. A *bare* `Dynamic` receiver
is correctly silenced by FP discipline, but the union appears to leak the
`Dynamic` interior's nil past that gate specifically when the merge's
exhaustiveness comes from a `raise` arm (an all-arms-assign merge — the
no-`raise` rows — is clean). It cleared at v5.11.0 because liquid
collapsed `render_tag` to a single unconditional assignment
(`template_name = @template_name_expr; raise ::ArgumentError unless
template_name.is_a?(String); partial = PartialCache.load(template_name,
…)`), removing the multi-arm merge entirely.

**Take-away / feedback:** a narrow but realistic flow-precision FP —
the defensive `if/elsif/else: raise` + an unsignatured (`Dynamic`)
method-call arm is a common Ruby shape (liquid wrote it by hand).
Queued as an engine precision item; the bisected minimal repro is the
acceptance fixture. Neighbour of ADR-47 (clause reachability) and the
conditional-local / block-capture write-back work (ADR-56/57).

## Mechanical checks

- **Churn cross-check.** `git diff --stat v5.0.0 v5.12.0 -- 'lib/**/*.rb'`:
  **56 files changed, +2917 / −774** — for a `lib` of ~60 files, the
  library was *essentially rewritten* across the range (a brand-new
  StringScanner lexer, a reworked render/partial path, etc.). The flat-0
  curve is therefore *meaningful*: it is baseline stability under heavy
  real churn, not "nothing moved."
- **Cold-cache spot check.** v5.12.0 re-run with `--no-cache`
  `--no-baseline` → **4 diagnostics** (2× `flow.always-truthy-condition`,
  1× `call.undefined-method`, 1× `call.possible-nil-receiver`), matching
  the swept `raw = 4`. The shared content-hashed cache masked nothing.
- **Rename caveat — N/A.** The v5.6.0 spike is *not* a rename artifact:
  `lib/liquid/lexer.rb` keeps its path across the boundary; the surface /
  clear is the concrete→`Dynamic` receiver-typing change described above.
- **Parse-error floor — none.** Unlike Redmine (a constant 22 from a
  generator ERB-as-`.rb` template), liquid's `lib` carries no rule-less
  parse-error floor: every blip is a properly-ruled diagnostic that
  buckets or clears. The surfaced count returns cleanly to 0.

## Interpretation

The three sweeps now bracket the spectrum:

- **Mastodon v4.5.x** — flat 0, a mature Rails app over a patch line:
  baseline stability, no standing diagnostics added.
- **Redmine 6.x** — flat 22 (an un-baselineable parse-error floor) plus a
  +6 minor-bump breach that was an FP-pattern / rename churn artifact:
  the baseline blind spot for rule-less diagnostics.
- **liquid v5.x** — flat 0 *with* three one-tag blips on a
  heavily-rewritten pure library: the baseline mechanism is sound (every
  breach is attributable and self-clearing), and the moving project
  acted as a **fuzzer for Rigor's own precision**, surfacing two real
  FPs (a pinned-`rbs` strscan gap; a `Dynamic`-union / `else: raise`
  flow leak) that a single-snapshot survey would have missed — both only
  *because* the code moved through the shape that triggers them and then
  out of it.

**Validated:** baseline stability under near-total `lib` churn; the
record-and-validate cache (no masking); the pure-inference (no-plugin,
no-`sig`) config path. **Queued feedback:** (1) bump the pinned `rbs`
gem to ≥ 4.1.0 to close the strscan `peek_byte`/`scan_byte` gap;
(2) the `Dynamic`-union / `else: raise` conditional-local
`possible-nil-receiver` FP, with the bisected minimal repro as fixture.

## Reproduce

Artefacts live outside the rigor tree under
`~/repo/ruby/rigor-survey/_liquid-sweep/` (`baseline.yml`, `sweep.sh`,
`tabulate.rb`, `reports/<tag>.json|err`, `cache/`); the frozen
`.rigor.dist.yml` is untracked in the liquid checkout. Re-run:

```sh
nix … develop --command bash  ~/repo/ruby/rigor-survey/_liquid-sweep/sweep.sh
nix … develop --command ruby  ~/repo/ruby/rigor-survey/_liquid-sweep/tabulate.rb
```
