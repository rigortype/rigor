## Gotchas (load-bearing, learned the hard way)

- **ADR-46** — do NOT extract the `Runner#initialize` ivar pre-seeds (`@class_decl_paths_snapshot = {}` etc.) into a helper; moving them out of the constructor hides them from the engine's OWN flow analysis and `make check` self-flags `snapshot.size` as a nil-receiver false positive. Keep them inline (the constructor carries an `AbcSize` disable).
- **ADR-45** — `@collect_stats` is true by default (can't gate the cache on it; a hit returns nil stats); a lazy `@io_boundary ||=` on a frozen plugin → `FrozenError` (use `instance_variable_get`); a cache write / serialize failure is swallowed (never breaks a run).
- **ADR-24** — a check-rules *reimplementation* of self-call resolution diverges from the engine's real one (which already handles `module_function` / `Data.define` accessors / mixins for precision) → 135 FPs (reverted). The landed route is the evaluation-time `SelfCallResolutionRecorder` ("collect, don't recompute").
- **ADR-62 / ADR-63** — `make verify` gates only `lib` + `plugins`; the **external corpus can still expose false positives** from receivers Rigor mistypes. A union/nilable undefined-method rule inherits the scalar rule's "only as good as the inferred type" exposure — the nilable study caught a `Hash | Hash`#pack FP on mail (`compose_codepoints` mistyped an `Array`). Run a `rigor-survey` corpus diff (`cd $proj; BUNDLE_GEMFILE=$rigor/Gemfile nix develop $rigor -c bundle exec $rigor/exe/rigor check --format json $paths`) before trusting any diagnostic-widening on union / nilable receivers. Also: the inference scanners (`PrecisionScanner` / `ProtectionScanner`) are NOT autoloaded by `require "rigor"` (require them explicitly, as their specs do); rubocop enforces annotated `%<name>s` format tokens; and a `Data.define(:method, …)` member shadows `Data#method` (use `:method_name`).
- **Self-mutation (Product C, `tool/mutation/self_mutate.rb` — mutate `lib/rigor` itself, kill by self-check ∪ Rigor's own rspec)** — the `--coverage-gap` whole-tree hole count is meaningless without **method-coldness** de-noising: Ruby line-coverage credits a multi-line expression to its FIRST line, so the continuation lines of a *covered* expression (a tested `to_h`'s hash-literal entries) read as uncovered. Count a hole only inside an entirely-uncovered `def`; exclude class-body/constant sites (data, not logic). That de-noise took the raw whole-tree count **1969 → 22** on `lib/rigor` (all in `cli/mcp_command`, now closed — the unit suite is otherwise method-level complete). The test axis needs an **in-bundle** rspec runner — NOT `with_unbundled_env`, which is for a *foreign* project's Gemfile and breaks Rigor's own suite. The effectiveness tier (covered-but-not-asserted) is worked per-file via the fused mode and converges on an equivalent-mutant floor (message/inspect text), not zero. Living tracker: [`docs/notes/20260618-self-mutation-testing-plan.md`](notes/20260618-self-mutation-testing-plan.md); roadmap entry under § "Analyzer self-testing".
- **Corpus gating — a git worktree isolates the ENGINE, never a PLUGIN.** `exe/rigor` unshifts its own tree's `lib/`, so running `$worktree/exe/rigor` against a survey project measures that worktree's engine. It does **not** isolate `plugins/` — those resolve from the main repo, so a worktree "before" run silently loads the modified plugin and the diff comes out empty (verify with `rigor plugins`, which prints each plugin's manifest version). For a plugin change, swap the plugin directory instead: `git checkout origin/master -- plugins/rigor-<name>` (plus `rm` any file the change adds), run the before side, then `git checkout HEAD -- plugins/rigor-<name>`. A `trap restore EXIT` around it is worth the two lines. This bit once (2026-07-10, the grape slice) and it presents as a *passing* gate.
- **Perf measurement (2026-07-13, learned during the campaign)** — (1) warm-run numbers are only comparable within one process model: an in-process cold-then-warm chain is ~186k allocs cheaper than a fresh-process warm purely from Ruby VM per-process warmup, which manufactured a phantom "warm regression" against the `20260627` note. (2) Self-check allocation numbers require `vendor/bundle` present (the RBS env ingests vendored-gem sigs, ~8M allocs on this repo); a worktree without the bundle silently measures a smaller env. (3) YJIT does not move allocations (≤ +0.007%), so the deterministic gates survive PR #75. Details: [`20260713-corpus-perf-campaign.md`](notes/20260713-corpus-perf-campaign.md).
- **bench-perf** — the Make target is `bench-perf`, not `bench` (the bare name collides with the `bench/` data directory; the file keeps its no-`.PHONY` convention). The `release-gate.yml` workflow that runs it on a `release/x.y.z` push is **advisory during the `0.2.x` trial** — it reports but does not block the merge (`ci.yml` is the required gate); the signal is still release-quality and worth reviewing. Both baselines (`bench/baseline.json` perf targets + `data/oss-sweep/mastodon-thresholds.json`) are **recalibrated only when the deterministic signals drift** — the v0.2.0 cut set lib allocations ≈18.77 M / peak RSS ≈232 MB / wall 13.75 s and Mastodon `app lib config` to 468 diagnostics at min precision 0.4284; **v0.2.1 held both unchanged** (allocations ≈19.3 M stayed within band, sweep green). These are exact-count / banded gates with little headroom, so a precision or allocation change flips them red **until recalibrated, by design**. Recalibrate perf from the **CI-measured Linux values** in the failed run's log (allocations is the deterministic signal; **wall_s is noisy → `gh run rerun --failed` clears a wall-only flake, never recalibrate the baseline for wall alone** — v0.2.1's only red was exactly this), and **diff the OSS-sweep diagnostics for false positives before blessing a higher count** (the v0.2.0 recalibration found 3 `StringScanner#[]` FPs → fixed via `data/core_overlay/string_scanner.rbs`, not blessed into the threshold).

### ADR-52 — compiled plugin contribution dispatch (COMPLETE — slices 1–6 landed 2026-06-10/11)

Every per-call / per-def / per-file / per-node plugin consultation is gated by a key the engine already holds, via a table compiled once per run at registry build — plugin code runs only on candidate hits. All five legacy `flow_contribution_for` users migrated (the AR "receivers-gate blocker" was resolved with **no new gate form** — the run-time `methods:` callable never reads the receiver type, so it fits the existing slice-4 gate), the hook was **deleted** (load-time `ArgumentError` + CHANGELOG migration note), and one engine-owned `Plugin::NodeRuleWalk` runs per file. Full slice-by-slice record (commit hashes, the resolved AR blocker, delegation lessons) lives in [ADR-52](adr/52-compiled-plugin-contribution-dispatch.md) + [`docs/ROADMAP.md`](ROADMAP.md) § "compiled plugin contribution dispatch". Demand-gated leftovers only: a node-major diagnostic re-sort (not taken — would break byte-identity) and the exact-membership-Set gate refinement if a profile ever shows the receiver-ancestry walk hot.

### ADR-24 — implicit-self method-call resolution, remaining

- **Slice 4 (recorder + `call.self-undefined-method` rule, shipped `:off`) — LANDED v0.1.17; WD4 corpus FP eval DONE 2026-06-14 → rule stays `:off`, NOT promotable** ([note](notes/20260614-adr24-slice4-self-undefined-fp-eval.md)). The eval landed the universal-base exclusion (Bucket 1, `Object`/`BasicObject`/`Kernel`, 287 corpus FPs) but found the **abstract / template-method base-class pattern** (Bucket 2, 167) is an unaddressable FP under the current per-class gate. **Do NOT widen the standalone-only gate to superclass / include chains** until the abstract-base FP is solved — the required shape is **subclass-aware gating** (record at the recorder whether the missed method is defined on a known subclass; suppress if so). **Arity diagnostics** on resolved closed-class self-calls were NOT part of slice 4 (undefined-method only) — a later extension once the rule proves out.
- **Non-`Bot` general adoption inside class bodies** — a resolved self-call return type is adopted ONLY when it is `Bot`. Unconditional adoption of precise non-`Bot` returns regressed `rigor check lib` by 16 diagnostics (pre-existing callee-return-inference imprecisions surfacing downstream); this follow-up needs callee-return inference precise enough that adopting precise types does not surface those imprecisions.

### Inference budgets — spec table unwired (Layer 1 doc hygiene DONE)

The spec's configurable `budgets:` table ([`docs/type-specification/inference-budgets.md`](type-specification/inference-budgets.md)) is normative-for-v1 but **not wired** — the only operative cutoffs are three hard-coded silent guards (recursion re-entry ≈ depth 1, ancestor walk 100, HKT fuel 64) plus ADR-10 `budget_per_gem`. **Layer 2 resolved, and it was not a budget:** the large-app cost cliff was a 4.2 M-retained-String leak in `rigor-activerecord` (fixed v0.1.16), and `union_size` was refuted as uncorrelated with memory. Budget wiring is **demand-deferred** — no corpus project demonstrates a budget-shaped cost; if one does, re-run the 2a distribution probe first ([ADR-41 WD3](adr/41-inference-budget-design.md)). The `RIGOR_BUDGET_TRACE` / `RIGOR_HEAP_PROFILE` / `RIGOR_HEAP_TRACE` probes are reusable.

### Stdlib RBS coverage-gap pattern + the staged upstream PR

When an upstream `ruby/rbs` gap is surfaced by a single internal call site, prefer **(a')** an in-source `# rigor:disable` + load the library; across multiple call sites or user-facing code, escalate to **(b)** a focused RBS overlay under Rigor's own `sig/`, or **(c)** an upstream `ruby/rbs` fix. The `references/rbs` branch `widen-strscan-resolv-stdlib-sigs` (widens `StringScanner#[]`, `Resolv#initialize`) is staged — **branch push + `ruby/rbs` PR creation are the user's task.**

### Sig-gen (ADR-14) remaining gaps
