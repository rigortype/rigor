# Rigor 0.2.x compatibility-safe strengthening survey

Date: 2026-06-22. Status: **research note, no design commitments.**
This records a survey of ways to strengthen Rigor during the `0.2.x`
evaluation line without violating the public compatibility discipline. It is
written against the 2026-06-22 working tree: `CHANGELOG.md` contains entries
through v0.2.3, while some planning material still uses v0.2.1 as the resume
bookmark for the same evaluation line. This note is not normative;
[`../compatibility.md`](../compatibility.md), ADRs, `docs/type-specification/`,
and `docs/internal-spec/` bind when they disagree with it.

## Scope

The question for this survey is:

> Where can Rigor become stronger while preserving backwards compatibility?

"Stronger" here means better detection, precision, explanation, performance,
onboarding, plugin capability, or user guidance. "Backwards compatibility" is
read in the ADR-50 sense: conforming users should not have their documented CLI
usage, `.rigor.yml`, plugin code, suppressions, baselines, cache artifacts, or
`RBS::Extended` annotations invalidated by an ordinary minor-line upgrade.

The scope is deliberately narrower than "what should Rigor build next." It
classifies strengthening routes by their compatibility risk and records guardrails
for choosing between:

1. internal improvements that do not touch the public surface;
2. additive public-surface improvements with current-behavior defaults; and
3. opt-in `bleeding_edge:` features for changes that would impose a new
   authoring discipline.

## Compatibility frame

ADR-50 and `docs/compatibility.md` make the main split unusually clear:
Rigor's public surface is compatibility-sensitive, but the inference engine is
free to evolve. That means the safest strengthening work is not the least
ambitious work; it is the work that stays on the right side of the public /
internal line.

The public surface includes:

- CLI commands and documented flags;
- `.rigor.yml` keys and value grammar;
- the plugin contract, including `Plugin::Base` hooks, manifest fields, and
  pinned read-side namespaces;
- diagnostic identifiers, suppression markers, and `severity_overrides:` keys;
- the baseline file format;
- the persistent cache schema / format marker;
- the `RBS::Extended` `%a{rigor:v1:...}` grammar; and
- structured diagnostic JSON fields that agents or scripts are meant to consume.

The non-contract surface includes:

- `Rigor::Inference::*` internals;
- internal `Rigor::Type::*` carrier representation;
- dispatch tiers and inference strategies;
- which diagnostics happen to fire on a given file; and
- the exact precision of `rigor sig-gen` output.

This makes three broad strengthening routes safe.

### Route A — improve non-contract internals

Internal inference, dispatch, normalization, type-carrier, effect, cache, and
performance changes are compatibility-safe when they preserve the documented
surface. They may still change diagnostic output, but diagnostic output is not a
contract; the compatibility risk is false positives and user trust, not a formal
API break.

The practical gate for this route is therefore empirical: run the self-check,
plugin check, and relevant corpus / regression sweeps before default-widening a
diagnostic. `make verify` is necessary but not sufficient for receiver-typing or
flow-rule widening because external Ruby projects expose mistyped-receiver false
positives that Rigor's own codebase may not contain.

### Route B — add public surface only additively

New public affordances can be compatible when they are additive and default to
current behavior. Examples include a new CLI flag that defaults off, a new
subcommand, a new `.rigor.yml` key whose default is the old behavior, optional
plugin hooks, new read-only plugin services, new diagnostic metadata fields, or a
new rule that is `:off` / `:info` by default.

Additive is not a synonym for casual. Public additions must still be documented,
covered by the public-API drift machinery where relevant, and designed with the
v1.0 freeze in mind. Once a field, flag, hook, or feature id becomes a contract
vocabulary item, future removal or semantic inversion becomes a major-version
move.

### Route C — use `bleeding_edge:` for new disciplines

A change that makes previously clean, idiomatic Ruby fail under the default
profile because it demands a new authoring discipline is compatibility-sensitive.
ADR-50's route for that class is the `bleeding_edge:` overlay: ship the
discipline under a stable feature id, make it inspectable, allow granular opt-in,
and graduate it only at a major.

The implementation foundation already exists. `Rigor::BleedingEdge::FEATURES` is
currently empty, `bleeding_edge:` is parsed, `rigor show-bleedingedge` exists,
and severity composition is wired. The first real discipline can therefore land
as a single feature entry rather than a new engine mechanism.

The severity resolution order is important and should not be disturbed:

1. user `severity_overrides:`;
2. active `bleeding_edge` severity overrides;
3. active `severity_profile:`; and
4. the rule's authored severity.

User overrides winning over `bleeding_edge` is a compatibility feature: even an
early-adopted next-major discipline remains locally suppressible by the user's
existing configuration vocabulary.

## Compatibility facts to preserve

### Diagnostic vocabulary is contract; diagnostic firing is not

Rigor may strengthen an existing rule in a minor if the new firing is a genuine
instance of that rule's remit. The user-facing absorber is the baseline. What
must remain stable is the vocabulary the user writes down: rule ids,
family-suppression names, legacy aliases, disable comments, and
`severity_overrides:` keys.

The current rule machinery supports that distinction:

- `CheckRules::ALL_RULES` enumerates rule ids.
- `CheckRules::LEGACY_RULE_ALIASES` keeps old suppression identifiers working.
- `CheckRules::RULE_FAMILIES` supports family-level suppression / override.
- `RuleCatalog` carries additive metadata such as `evidence_tier`,
  `documentation_url`, and `severity_by_profile`.

A compatibility-safe rule change therefore keeps or aliases the identifier,
preserves suppression behavior, and treats message text as presentation.

### Structured JSON fields are public when agents branch on them

ADR-61 makes a useful rule explicit: if an agent, CI integration, or `jq`
pipeline needs a datum for aggregation or branching, it should be a structured
field, not something parsed out of `message` text. Message wording is
presentation and may change; structured fields such as `receiver_type`,
`method_name`, and triage `selectors` are public vocabulary once exposed.

The safe direction is additive: add fields when they remove message parsing, keep
existing fields stable, and avoid normalizing away per-site precision on the raw
`check` stream. Aggregation-specific normalization belongs in aggregation layers
such as `triage`.

### Artifact format changes must invalidate, not mis-read

The baseline and cache each have explicit version markers:

- `Analysis::Baseline::CURRENT_VERSION` is currently `1`; loading a different
  version raises instead of interpreting it as the current schema.
- `Cache::Descriptor::SCHEMA_VERSION` and `Cache::Store::FORMAT_VERSION` combine
  into the cache marker, currently `4.2`; schema / format changes create misses
  rather than silent mis-reads.

That gives internal freedom to improve cache layout and descriptor content, but
only under the invalidate-never-misread discipline. Baseline format changes are
more user-visible than cache changes and should be treated as public-surface work
with migration guidance, not as ordinary internal refactors.

### `RBS::Extended` grammar is versioned

The `%a{rigor:v1:...}` namespace is part of the public type-language surface.
Compatible additions may extend what Rigor understands, but incompatible grammar
or semantic changes must use a new version prefix rather than changing
`rigor:v1:` meanings. Unknown or unsupported metadata should be preserved by RBS
tooling, and conflicts must be diagnostics rather than first-wins / last-wins
behavior.

### Public plugin namespaces are pinned deliberately

The public API drift spec pins method sets for `Scope`, `Environment`,
`Type::Combinator`, `Reflection`, `Source::Literals`, `Plugin::*`,
`FlowContribution`, `TypeNode::*`, and plugin macro structures. A public method
addition can be compatible, but it is still a contract expansion. It should ship
with matching RBS coverage and an intentional drift-spec update so plugin authors
see a stable shape rather than accidental exposure.

## Compatibility-safe strengthening opportunities

### 1. Continue self-mutation and protection-effectiveness work

The self-mutation / teeth measurement track is one of the safest ways to make
Rigor stronger. It improves Rigor's own test oracle and finds false negatives in
the analyzer without changing user-facing semantics directly. The current work
queue already treats this as repeatable: batch files, inspect surviving mutants,
classify genuine holes versus equivalent-mutant floor, add targeted tests, and
rerun the fused self-check plus unit-spec axis.

Compatibility value:

- strengthens the implementation without expanding the public surface;
- reduces the chance that future internal precision work regresses silently;
- gives evidence before default-widening diagnostics; and
- supports ADR-62 / ADR-63's "teeth" goal without imposing a user discipline.

Guardrails:

- keep the harness's test axis scoped to convention-mapped unit specs;
- do not run the fused harness concurrently with `make verify`; and
- treat equivalent-mutant floors as floors, not as failures to force to zero.

### 2. Expand deterministic builtin and stdlib precision

Deterministic constant folding, tuple lifting, shape dispatch, and focused RBS
overlays are compatibility-friendly when they model pure Ruby behavior more
precisely. They can reduce `Dynamic`, improve `type-of`, sharpen downstream
checks, and make `sig-gen` evidence better without adding public grammar.

The current carrier sweep has already drained many obvious scalar and structural
wins, so the next safe work should be empirical rather than checklist-driven:
probe `MethodDispatcher.dispatch` on constant receivers, identify actual misses,
and prioritize methods whose behavior is pure, deterministic, and not secretly
format-, locale-, filesystem-, time-, or block-dependent.

Compatibility value:

- usually internal-only;
- often reduces false positives by avoiding overly-wide RBS fallback;
- can improve diagnostics without adding new rule vocabulary; and
- gives users better explanations in `type-of`, `annotate`, and coverage tools.

Guardrails:

- decline folds that route through user-overridable coercions unless that call is
  known not to happen for the folded literal form;
- prefer upstream RBS fixes or focused overlays for signature gaps;
- run corpus diffs if a precision change can widen real diagnostics; and
- do not treat old coverage-audit TODO marks as proof of a current gap without
  dispatch probes.

### 3. Track `Dynamic[T]` provenance for explanations

`Dynamic[T]` is already the right semantic carrier for unchecked evidence, but
users need to know why a value became dynamic. Coverage and protection reports
should be able to distinguish at least these causes:

- external gem without RBS;
- framework DSL or macro boundary;
- analyzer budget / cutoff;
- plugin-declared dynamic return;
- explicit `untyped` contract; and
- unsupported syntax or inference fallback.

This can begin as internal provenance carried alongside dynamic-origin facts and
surface additively through coverage / protection labels or diagnostic metadata.
It does not require changing `untyped = Dynamic[top]` semantics.

Compatibility value:

- improves user guidance rather than increasing obligations;
- makes `rigor coverage --protection` more actionable;
- helps `rigor-next-steps` / `rigor-ask` route users to RBS setup, plugin tuning,
  monkey-patch pre-eval, or engine-gap reporting; and
- creates evidence for any future strict-dynamic discipline.

Guardrails:

- do not make provenance labels part of a hard failure by default;
- add structured fields rather than requiring message parsing;
- preserve existing `Dynamic[T]` relation semantics; and
- if a later strict-dynamic policy is proposed, gate it behind `bleeding_edge:`.

### 4. Improve effect and mutation modeling conservatively

Better effect modeling can strengthen both precision and false-positive
reduction: method calls that cannot mutate a receiver should preserve facts, and
calls that may mutate aliased state should invalidate them. This includes
self-mutating methods, block timing, escaping closures, `freeze`, `dup`, `clone`,
writer methods, and container aliasing.

Compatibility value:

- mostly internal;
- can reduce spurious `always-truthy`, nilability, and receiver-shape errors;
- can make protection reports more honest; and
- can support stronger future diagnostics with evidence.

Guardrails:

- prefer conservative invalidation over optimistic fact preservation;
- do not preserve shape carriers through `freeze` / `dup` until the known
  reflexive `always-truthy` interaction is resolved;
- test against realistic mutable Ruby idioms, not only synthetic examples; and
- treat any default diagnostic widening as requiring corpus false-positive
  evaluation.

### 5. Improve cache, incremental, and performance behavior

Performance improvements are compatibility-safe when they preserve output and
respect cache versioning. The public contract is not the internal layout; it is
that schema / format changes do not silently mis-read stale entries.

Compatibility value:

- makes CI adoption easier without changing user code;
- reduces the cost of precision improvements;
- supports the release-engineering perf gate; and
- can be validated mechanically through benchmark baselines.

Guardrails:

- bump descriptor / store markers when serialized meaning changes;
- preserve cache miss semantics over stale-read semantics;
- keep worker / process paths using the same effective configuration; and
- recalibrate performance baselines only from deterministic signals, not from
  wall-time noise alone.

### 6. Wire configurable inference budgets with current-behavior defaults

The type-specification already describes a richer budget table than the current
hard-coded guards. Wiring budget configuration can be compatibility-safe if the
defaults preserve today's behavior and the initial user-facing effect is
observability or opt-in tuning rather than stricter failure.

Compatibility value:

- gives large projects a documented knob instead of hidden cutoffs;
- makes budget-related `Dynamic` provenance explainable;
- can support `rigor doctor` recommendations; and
- avoids making internal fuel constants de facto public API.

Guardrails:

- default to current behavior;
- expose budget exhaustion as explanation before making it a default diagnostic;
- avoid promising stable internal budget names before the shape is proven; and
- treat any new config key as public surface once documented.

### 7. Add CLI helpers that route existing evidence

Commands such as `rigor doctor`, `rigor upgrade`, or `rigor skill describe
--deep` can be additive and compatibility-safe when they route existing checks
rather than changing default `check` behavior. The strongest form is a helper
that runs or reuses analysis, classifies already-produced findings, and suggests
next actions.

Compatibility value:

- improves adoption without requiring code changes;
- uses the existing diagnostic / baseline / plugin surfaces;
- helps users distinguish setup problems from clean runs; and
- can be added as new commands or flags with no default behavior change.

Guardrails:

- do not make an expensive deep probe the default presence-only path unless the
  CLI contract says so;
- if JSON output is exposed, design it as a stable structured contract;
- keep message wording presentation-only; and
- avoid duplicating check-runner setup in a way that diverges from `rigor check`.

### 8. Improve plugins and plugin precision additively

Bundled plugin precision improvements, new production plugins, additional
recognizers, config-schema defaults, and optional hooks can all strengthen Rigor
without breaking compatibility. This is especially valuable for Ruby framework
boundaries where ordinary static inference has too little evidence.

Compatibility value:

- reduces false positives at dynamic DSL boundaries;
- keeps application code annotation-free;
- uses the intended extension surface rather than core special cases; and
- can be shipped per plugin with focused integration specs.

Guardrails:

- optional hooks only; required hook changes are contract changes;
- public plugin-service additions need RBS and drift-spec updates;
- plugin diagnostics must use stable rule ids or plugin-qualified ids; and
- new recognizers should not turn positive recognition trace into actionable
  default errors.

### 9. Add diagnostic metadata instead of parsing prose

`evidence_tier`, `documentation_url`, `receiver_type`, `method_name`, and
`triage` selectors show the safe pattern: add structured fields when a human,
agent, or CI integration needs to reason over diagnostics. This strengthens
explainability and automation while leaving existing rule ids and suppressions
alone.

Compatibility value:

- improves agent workflows;
- makes release-to-release message wording freer;
- allows better triage and clustering; and
- avoids multiplying rule ids for presentation differences.

Guardrails:

- additive fields are safe; field removal or semantic inversion is not;
- do not require consumers to parse `message`;
- keep per-site streams faithful and put lossy grouping in aggregation layers;
  and
- document any new field that agents are expected to branch on.

### 10. Add new rules as off-by-default or info-first

A new diagnostic can be compatibility-safe if it ships `:off` or `:info`, has a
stable identifier, and gathers corpus evidence before default promotion. Existing
examples include rules that remain off or low-severity until their false-positive
envelope is understood.

Compatibility value:

- lets Rigor experiment with new evidence without breaking default CI;
- gives early adopters an override path;
- creates a measurable promotion queue; and
- keeps suppression vocabulary stable from the first public appearance.

Guardrails:

- use `bleeding_edge:` rather than a silent default promotion when the rule
  imposes a new authoring discipline;
- keep legacy aliases if a rule id is renamed;
- promote only after external corpus false-positive sweeps; and
- avoid deciding severity from aggregate statistics alone.

### 11. Use the first `BleedingEdge::FEATURES` entry deliberately

The overlay is empty today. The first feature id will set the style for all
future next-major disciplines, so it should be chosen only for a clear case:
default-on would force a new authoring expectation, but early adopters can get
value by opting in and the migration story can be explained with one stable id.

Compatibility value:

- exercises ADR-50's intended non-breaking path;
- gives users an explicit preview of the next major;
- keeps default `0.2.x` behavior stable; and
- creates a named migration note for the eventual major.

Guardrails:

- do not use `bleeding_edge:` as a dumping ground for ordinary precision fixes;
- keep each feature inspectable and granular;
- ensure user `severity_overrides:` still wins; and
- remove or graduate the feature only as part of the planned major behavior
  change.

## Prioritized compatibility-safe backlog

### P0 — Evidence before default diagnostic widening

Before widening receiver-typing, nilability, flow, or override diagnostics in the
default profile, run an external corpus false-positive sweep. `make verify` alone
is not enough because Rigor's own code does not contain the full range of Rails,
ActiveSupport, DSL, monkey-patch, RBS-gap, and dynamic-constant patterns that
produce user-facing false positives.

This is not a feature, but it is the highest-priority strengthening guardrail.
Without it, a technically compatible diagnostic improvement can still erode trust
by surfacing false positives on real code.

### P1 — Continue self-mutation batches

The self-mutation track improves the analyzer's own test oracle with no public
contract expansion. It should remain one of the default ways to spend capacity
between larger inference changes.

### P2 — Add `Dynamic` provenance and tractability labels

This is the highest-value explanatory improvement because it turns generic
"dynamic receiver" holes into next actions: install RBS, enable a plugin, add a
project overlay, pre-evaluate monkey patches, or report an analyzer gap.

### P3 — Internal precision with deterministic folds and RBS overlays

Continue only where empirical dispatch probes show real gaps. Prioritize pure,
deterministic, structure-returning methods that lift to `Tuple`, `Constant`, or
shape facts without invoking user code.

### P4 — Conservative effect / mutation modeling

Improve invalidation and preservation rules where the semantics are clear. Use
false-positive reduction as the first success metric; defer default-widened
mutation diagnostics until corpus evidence is strong.

### P5 — Additive UX helpers

`rigor doctor`, `rigor upgrade`, and `skill describe --deep` are plausible
additive improvements if they reuse the existing check/baseline/plugin evidence
and expose structured output carefully.

### P6 — Optional plugin-surface additions

Add read-only services or optional hooks only when a concrete bundled or external
plugin needs them. Update RBS and public drift snapshots deliberately in the same
change.

### P7 — First `bleeding_edge:` discipline

Do this only when there is a real next-major authoring expectation to preview.
The first feature should be small, inspectable, and backed by a migration story.

## Change-classification checklist

Use this quick filter before implementing a strengthening change:

1. **Does it alter documented CLI, config, plugin, diagnostic-vocabulary,
   baseline, cache, or `RBS::Extended` behavior?** If yes, treat it as public
   surface work.
2. **Is it internal precision only?** If yes, the compatibility question becomes
   false-positive risk, not public API risk.
3. **Does it add a new field, flag, hook, or config key?** If yes, default to old
   behavior, document it, and decide whether it enters drift-spec / RBS coverage.
4. **Does it make previously clean idiomatic code fail by asking users to write
   code differently?** If yes, use `bleeding_edge:` or keep it off by default.
5. **Does it only catch a genuine instance of an existing rule's remit?** If yes,
   a minor-line change is allowed, but still run corpus false-positive gates.
6. **Does it change an artifact schema?** If yes, bump or migrate explicitly;
   never silently mis-read.
7. **Does it change `rigor:v1:` annotation meaning?** If incompatible, do not;
   introduce a new version prefix.
8. **Will agents or CI branch on it?** If yes, expose structured data and avoid
   message parsing.

## Compatibility traps to avoid

- Do not treat `make verify` as sufficient evidence for default diagnostic
  widening on user projects.
- Do not restart ADR-24 slice 4 through a check-rules reimplementation; use the
  engine's recorded evidence path.
- Do not promote `call.self-undefined-method` by broadening its gate until the
  abstract / template-method false-positive pattern is solved.
- Do not extract `Runner#initialize` ivar pre-seeds into a helper; hiding them
  from Rigor's own flow analysis has previously caused self-check false
  positives.
- Do not preserve shape carriers through `freeze` / `dup` until the known
  interaction with reflexive truthiness is resolved.
- Do not rename diagnostic ids without preserving legacy aliases for
  suppressions and overrides.
- Do not make a plugin hook mandatory in a minor; add optional hooks and keep
  existing manifests valid.
- Do not add public JSON fields whose meaning is "whatever the current message
  says"; structured fields need stable semantics.
- Do not change `rigor:v1:` grammar incompatibly; version the directive instead.

## Non-goals

This note does not choose a next implementation task, propose an ADR, or freeze a
new public contract. It also does not authorize a version bump, a release, a
baseline-format migration, a default severity promotion, or a commit. It records
compatibility-safe strengthening routes and the guardrails that should make those
routes safe during the `0.2.x` evaluation line.
