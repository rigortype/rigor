# Elixir v1.20 の漸進的集合論型システム — Rigor 観点考察

**Status:** research note, no design commitments. 外部言語の型システムリリースを Rigor と突き合わせた観察。
**Date:** 2026-06-04.
**Rigor version:** working tree（master @ `4eccc390`）に対する観察。
**対象:** Elixir v1.20.0（2026-06-03 リリース）の型システム。一次資料は
[Elixir v1.20.0 released](https://elixir-lang.org/blog/2026/06/03/elixir-v1-20-0-released/)、
背景は [Strong arrows: a new approach to gradual typing](https://elixir-lang.org/blog/2023/09/20/strong-arrows-gradual-typing/)、
[Gradual set-theoretic types (HexDocs)](https://hexdocs.pm/elixir/main/gradual-set-theoretic-types.html)、
[The Design Principles of the Elixir Type System (Castagna, Duboc et al., arXiv:2306.06391)](https://arxiv.org/pdf/2306.06391)。

**Why:** Elixir は注釈ゼロの漸進的集合論型を「毎コンパイルで全プログラムに」走らせる方向で完成度を上げてきた。
Rigor とゴール（漸進・低 FP・推論優先）がほぼ同型でありながら、健全性（soundness）の扱いだけが正反対なので、
両者を突き合わせて (a) Rigor の方針が業界最前線と一致している確証、(b) FP 規律を崩さず取り込める改善、(c) 共通の難所、を棚卸しする。
後続の改善検討／ADR 起票はこのノートを根拠にする。

**読み順.** §1 が Elixir 側のサーフェス棚卸し、§2 が共通点マッピング、§3 が設計判断の分岐、§4 が Rigor に取り込めそうな改善、§5 が共通の難所と ADR 要否の判断。

## 1. Elixir v1.20 側のサーフェス棚卸し

1. **アノテーション不要の完全な漸進的型付け。** ソースに型注釈を書かずに全プログラムへ推論＋検査を走らせる。
   後方互換のため「すべての引数が `dynamic()` で注釈されているかのように」振る舞う。
   v1.18 でパターン推論、v1.20 で**パターン＋ガードの完全推論**が完成。

2. **集合論的型（set-theoretic types）が土台。** 型を union / intersection / negation の集合演算で記述・合成する
   （Giuseppe Castagna・Guillaume Duboc らの設計）。

3. **`dynamic()` 型 — `any()` ではない。**
   - *Compatibility*: 受理型と供給型が **disjoint（交わりが空）のときだけ**違反として報告する。既存コードでの誤検知を防ぐ。
   - *Narrowing*: 実行に沿って `dynamic()` が絞り込まれる。`data.a` と `data.b` にアクセスすると
     `data` は `%{..., a: number(), b: number()}` に narrow される。

4. **ガード／パターンマッチ解析。**
   - `when is_list(x) and is_integer(y)` → union/negation を推論
   - `def example({:ok, x} = y) when is_binary(x) or is_integer(x)` → `x` は binary|integer、`y` は 2 要素タプル
   - `when is_map_key(x, :foo)` → `%{..., foo: dynamic()}`、否定側は `foo: not_set()`（**キー不在を正の事実として保持**）
   - `when tuple_size(x) < 3` → タプル長の上限を追跡
   - `case` 各節で型を絞り、`nil ->` 節通過後の `value` は `binary()` と判定。**冗長節＝デッドコードも報告**。

5. **Strong arrows による健全性。** VM が行う実行時型テストを静的型に織り込み、
   「ランタイムチェックを追加せずに漸進的型付けを健全に保つ」。報告するのは
   **「実行されれば実行時に必ず失敗する verified bug」だけ**で、誤検知率は極めて低い。

6. **意図的に先送りした項目。** 型シグネチャ（注釈）構文の導入は次の条件付き — (a) v1.20 の性能が満足なら、
   (b) 再帰型を効率的に実装できれば、(c) パラメトリック型を効率的に実装できれば、
   (d) map のキー値ペアを enumerable として走査する型付け問題が解ければ。

## 2. Rigor との共通点

| 観点 | Elixir v1.20 | Rigor |
| --- | --- | --- |
| 誤検知の徹底回避 | 「verified bug＝実行時に必ず失敗するものだけ」「極めて低い FP 率」 | 最上位価値「動いているコードを脅かさない」（`feedback_false_positive_discipline`） |
| 寛容な動的型 | `dynamic()`、disjoint のときだけ違反 | `Dynamic[T]` 代数＋漸進的整合性＋trinary certainty（[value-lattice.md](../type-specification/value-lattice.md), [relations-and-certainty.md](../type-specification/relations-and-certainty.md)） |
| 集合論的演算 | union / intersection / negation が土台 | 型演算子 `~T`（否定）・`T - U`（差）・value lattice（[type-operators.md](../type-specification/type-operators.md)） |
| 制御フロー narrowing | `case` 節での `nil` 除去、ガード由来の絞り込み | edge-aware narrowing・fact store（[control-flow-analysis.md](../type-specification/control-flow-analysis.md)） |
| 構造的なキー追跡 | `is_map_key` でキー有無を追跡 | 推論オブジェクトシェイプ・構造的インターフェース・capability roles（[structural-interfaces-and-object-shapes.md](../type-specification/structural-interfaces-and-object-shapes.md)） |
| 注釈より推論を志向 | 注釈ゼロで推論、注釈は後回し | `rigor sig-gen` 優先、推論精度を上げ手書き RBS を不要にする思想（`feedback_no_ai_generated_rbs`） |

両者とも「漸進的・誤検知最小・実行時に壊れるものを最小限の摩擦で捕まえる」という哲学が驚くほど近い。
Rigor の方針は独自路線ではなく、業界最前線の独立した到達点と一致している。

## 3. 異なる設計判断

1. **健全性のスタンス（最大の差）。**
   Elixir は strong arrows で「健全（sound）」を積極追求し、違反は構成上 verified bug に限る。
   Rigor は明示的に**非健全**で、robustness principle（戻り値は厳格／引数は寛容という非対称、
   [robustness-principle.md](../type-specification/robustness-principle.md)）＋trinary certainty というヒューリスティックで FP を抑える。
   **ゴールは同じ（低 FP）だが機構が逆方向** — Elixir は理論的保証で、Rigor は確実性ランク＋予算で達成する。

2. **言語基盤への埋め込み度。**
   Elixir はコンパイラ統合で毎コンパイル時に推論が走り、注釈構文はまだ無い。
   Rigor は Ruby+RBS の外付けチェッカで、**RBS スーパーセット＋拡張注釈が既に完備**、プラグインでフレームワークを拡張する。立ち位置が対照的。

3. **実行時テストの活用。**
   Elixir の strong arrows は BEAM VM の実行時型テストを静的型に取り込む。Ruby/Rigor には等価な VM 機構が無く、直接移植はできない。

4. **records と dictionaries の区別。**
   Elixir は atom キーの map（record 的）と dictionary を型レベルで区別。Rigor は object shape＋capability role で等価のことをするが、切り分けの軸が違う。

## 4. Rigor が取り込めそうな改善

1. **使用箇所からの構造シェイプ合成（demand-driven shape accretion）。**
   Elixir は `data.a` / `data.b` のアクセスを観測して `dynamic()` を `%{a:, b:}` に絞る。
   Rigor の capability role は近いが、「メソッド本体で実際にアクセスされたメンバから必須構造を累積する」
   use-site 駆動の絞り込みをもう一段進められる余地がある。注釈なしで構造を立ち上げるのは sig-gen 思想と合致。

2. **デッドコード／到達不能節の診断。** ✅ **LANDED**（v0.1.17、[ADR-47](../adr/47-narrowing-driven-clause-reachability.md)）。
   `flow.unreachable-clause`（`case`/`when` + `case`/`in` 裸クラスパターン）を WD1+WD2+WD3a で実装、
   WD4 で 16 OSS コーパス掃引（発火ゼロ → balanced は `:info` 据え置き）。Elixir の冗長節報告の Ruby 版。
   残り（demand-driven）: WD3b（デコンストラクション/値/変数パターンの exhaustiveness）。

3. **キー不在を正の事実として保持。** ✅ **真分岐は LANDED**（v0.1.17、`is_map_key` 相当）。
   `h.key?(:foo)`/`has_key?` の真分岐で HashShape の optional キーを required に昇格し、`h[:foo]` が `T|nil`→`T`
   になる（`Narrowing#analyse_key_presence_predicate`、optionality 由来の nil のみ除去＝健全）。
   残り（demand-driven）: Elixir の `not is_map_key(x, :foo)` → `foo: not_set()` に相当する**偽分岐のキー不在事実**
   （現状は保守的 no-op）。

4. **コレクション長／タプル長のリファインメント追跡。** ✅ **非空 narrowing LANDED**（v0.1.17）。
   `arr.empty?`（偽分岐）/`any?`（真分岐）/`none?`（偽分岐）で `Array[T]`→`non-empty-array[T]` に narrow し、
   `arr.size`/`length`/`count` が `non-negative-int`→`positive-int` になる（`Narrowing#analyse_array_emptiness_predicate`、
   既存 `non-empty-array` リファインメント＋empty-removal projection を活用）。Elixir の `tuple_size` 相当。
   残り（demand-driven）: `tuple_size(x) < 3` のような**上限長**の追跡（長さ範囲キャリアが必要）。

5. **ガード後ブランチの「強い」型化。**
   Rigor は既に `is_a?` で narrow するが、strong arrows の発想 — `is_a?` / `respond_to?` / `case ===` 通過後の分岐を
   `Dynamic` を落とした強い型として扱う — を徹底すれば、**FP を増やさず実バグ検出（FN 削減）を伸ばせる**。
   Ruby のランタイムガードを静的精度の根拠にする方向。

## 5. 共通の難所と ADR 要否

Elixir が型シグネチャ導入の前提に挙げた残課題は、Rigor の難所とも重なる:

- **再帰型・パラメトリック型の効率** — Rigor の軽量 HKT（ADR-20, `project_lightweight_hkt`）と直結。性能予算
  （[inference-budgets.md](../type-specification/inference-budgets.md), `project_inference_budgets_unwired`）と併せて先回りする価値がある。
- **map を enumerable として走査する型付け** — Hash/Enumerable の走査型付けは Rigor でも未解決領域。

**ADR 要否の判断.** このノート単体では設計コミットしない。最も取り込みやすいのは §4-2（到達不能節診断）と §4-3/4-4
（ネガティブ事実・長さリファインメントの narrowing 拡張）で、いずれも FP 規律を崩さず実バグ検出を増やせる。
§4-2 は既存のデッドコード調査ノートを足場に独立 ADR 化を検討、§4-3/4-4 は control-flow-analysis 仕様の追補として扱うのが妥当。
§3-1（健全性スタンス）は Rigor の基本設計（robustness principle）と相反するため、追従はしない（記録のみ）。

## 6. クロージング — 統合の総括と、ベンチマークとしての Elixir

### このレビューから実際に landed したもの（v0.1.17、master）

| §  | Elixir 機能 | Rigor 実装 | 観測効果 |
| --- | --- | --- | --- |
| 4-2 | 冗長 `case` 節のデッドコード報告 | `flow.unreachable-clause`（ADR-47 WD1+WD2+WD3a+WD4 sweep） | 到達不能 `when`/`in` 節・dead `else` を診断（`:info`） |
| 4-3 | `is_map_key(x, :foo)` | Hash キー存在 narrowing | `h.key?` ガード内で `h[:foo]` が `T?`→`T` |
| 4-4 | `tuple_size` / 非空 | 配列非空 narrowing | 非空ガード内で `arr.size` が `non-negative-int`→`positive-int` |

3 項目とも **FP 規律を一切崩さず**（narrowing-only ＝ 新規診断を増やさない、`Dynamic` には絶対に発火しない）着地した。
§3-1（strong arrows による健全性）は robustness principle と相反するため**意図的に不採用**、§4-1（シェイプ accretion）と
§4-5（ガード後の `Dynamic`→`C` 強化）は規模・FP リスクの観点で見送り。

### 正直な収量評価（重要）

§4-2 の WD4 掃引（16 コーパス・発火ゼロ）と、§4-3/§4-4 が possible-nil-receiver を減らさず**精度向上に留まった**
（`Array#first` は Rigor では既に非 nil、index 結果の `T?` に nil-receiver は発火しない）事実は、同じ結論を指す:
**これらは「実バグを大量に捕まえる機能」ではなく、推論精度の底上げ**である。価値は (a) sig-gen / annotate / dump の精度、
(b) 下流推論（連鎖呼び出し・戻り値）への波及、(c) 将来の診断が消費できる事実の蓄積、に現れる。
派手な FP 削減を期待すると過大評価になる — Rigor の保守的エンベロープ自体が「捕捉対象の形を人がほぼ書かない」ことを意味する。
それでも、**業界最前線（Elixir）が踏んだ narrowing を Rigor が同じ健全性で持てた**ことの確証価値は大きい。

### Elixir 型システムの現状（2026-06 時点）

v1.20 で**パターン＋ガードの完全推論**が完成したが、ユーザ向け**型シグネチャ構文はまだ無い**。
導入は (a) v1.20 の性能、(b) 再帰型・(c) パラメトリック型の効率的実装、(d) map を enumerable として走査する型付け、
の 4 条件待ち（§1-6）。＝ Elixir はいま「注釈ゼロ・推論専一・strong arrows で健全」というフェーズにあり、
**Rigor が既に持つもの（RBS スーパーセット＋拡張注釈、プラグイン拡張）を Elixir はこれから設計する**という非対称がある。
逆に Rigor が将来直面する難所（§5: 再帰・パラメトリック型の効率、Hash/Enumerable 走査の型付け）は、
**Elixir がほぼ同じ順序で先に解く**可能性が高く、設計の先行指標になる。

### Ruby ↔ Elixir の関係と、継続ベンチマークとしての位置づけ

Elixir は Ruby と**同一の意味論・構文論を共有しているわけではない** — BEAM 上の不変・関数型、パターンマッチ第一級、
アクターモデル並行性で、Ruby の可変オブジェクト・メソッドディスパッチ中心の世界とは型推論の前提が異なる
（narrowing の健全性条件、`dynamic()` の流れ方、exhaustiveness の意味がそれぞれ違う）。
一方で歴史的つながりは強い: 作者 José Valim は Rails コミッタ出身で、`do…end` ブロック・`end` キーワード・
メタプログラミング文化・DX 重視といった**エルゴノミクスの系譜**を共有する。型システム面でも、両者は独立に
「漸進的・低 FP・推論優先」という同じ到達点に着いた（§2）。

この近さと差の両方が、Elixir を **Rigor の継続的ベンチマーク**として有用にする:

- **共有する目標**（漸進・低 FP・set-theoretic 演算・注釈より推論）ゆえ、Elixir の設計判断は Rigor に翻訳可能なことが多い。
- **異なる基盤**（健全 vs 非健全、不変 vs 可変、VM ランタイムテストの有無）ゆえ、どこまでが移植可能でどこからが
  「Ruby だからこその設計」かを、Elixir との対比が常に浮き彫りにする（§3）。
- 翻訳の作法は本セッションで確立: Elixir 機能 → Ruby の等価イディオム（`is_map_key`→`Hash#key?`、`tuple_size`→`empty?`/`any?`）
  → 既存キャリア・narrowing 機構への最小マッピング → FP 規律ゲート。

**今後の再レビュー契機**（このノートを更新する価値があるタイミング）: Elixir が (1) 型シグネチャ構文、
(2) 再帰型・パラメトリック型、(3) set-theoretic な map 型付け、(4) `not_set()` などのネガティブ・キー事実を出した時。
いずれも Rigor の未解決領域（HKT 効率・Hash 走査・§4-3 偽分岐）と直結するため、着地し次第ベンチマークし直す。
