## [Unreleased]

### Changed

- **[cli]** `rigor unused` now reuses the analysis cache for its RBS environment and its plugins' prepare work, and scans templates for class names against only the identifier-bearing fraction of each file — the report is byte-identical and 1.4–3.3× faster on the measured corpus (8.3 s → 2.5 s warm on Mastodon).

## [0.3.5] - 2026-08-25

v0.3.5 is about making the effect system usable rather than merely present. The `rigor effects` report went from 31,191 lines on a mid-size Rails application to 2,733 with nothing lost, gained `--label`, `--pure` and `--limit` so it can be asked a question, and can now print the label vocabulary itself. A larger group of fixes is about what the report *sees*: an optional receiver, a module a worker includes, a base class from a gem, a `super`, and a class-level annotation were each contributing nothing, several of them while the method still read as exhaustive. The manual gained a [chapter on effect labels](docs/manual/19-effect-labels.md), and [ADR-103](docs/adr/103-effect-labels.md) § WD17 records which labels a declared bound can actually fail on and where to enforce the rest.

### Added

- **[cli]** `rigor effects --list-labels` prints the effect vocabulary your project can name, with each root's meaning ([#471](https://github.com/rigortype/rigor/pull/471), [#429](https://github.com/rigortype/rigor/issues/429)).
  - Four configuration keys and two annotation forms require you to type an effect label, and nothing in an installed Rigor could say what the labels are. The listing includes whatever your plugins and your own `effects.labels:` opened, and it analyses nothing, so it is instant.

- **[cli]** The `rigor effects` report can be asked a question: `--label=LABEL` selects the methods carrying that label or one under it, `--pure` selects the methods proven to do nothing, and `--limit=N` caps the output ([#470](https://github.com/rigortype/rigor/pull/470), [#457](https://github.com/rigortype/rigor/issues/457)).
  - On Redmine, `rigor effects --label io.net` is five rows and `rigor effects --pure` is 436. Both questions previously needed `--full`, a `grep`, and a guess about the row grammar.

- **[effects]** An effect policy or envelope that names Steins' `failure.*` labels now parses instead of earning `effect.unknown-label`, so a policy written for the sibling PHP analyzer reads unchanged here ([#426](https://github.com/rigortype/rigor/pull/426), [#378](https://github.com/rigortype/rigor/issues/378)).
  - Rigor produces no `failure.*` label of its own, so a bound that names one is satisfied vacuously. That is the same footing `io.output.buffer` already has.

- **[docs]** The manual gained a chapter on effect labels, [Effect labels](docs/manual/19-effect-labels.md), walking the feature end to end for the first time.
  - It covers the vocabulary in one table, what the report really looks like on a mid-size Rails application, the direct-versus-transitive split between the report and the snapshot, the `update` / `check` / `explain` review loop, the CI step and its exit codes, and the envelopes and annotations that turn an observation into a bound.

- **[docs]** [Effect labels](docs/manual/19-effect-labels.md) now says which labels a declared bound can actually fail on, and where to enforce the ones it cannot ([ADR-103](docs/adr/103-effect-labels.md) § WD17).
  - A bound is checked against a method's *proven* labels, meaning what Rigor established by reading your code. On a Rails application `io.db.*`, `cache.*`, `telemetry`, `email.send`, `job.enqueue` and every `rails.*` are a plugin's claim about a framework Rigor did not read, so an envelope naming them is satisfied vacuously and the committed snapshot is what enforces them.

- **[docs]** The CI templates carry a commented-out `rigor effects check` step, so adopting the effect gate is one line to uncomment rather than a workflow to compose ([#443](https://github.com/rigortype/rigor/pull/443)).

### Fixed

- **[cli]** The `rigor effects` report is sized for an application instead of for a fixture: 2,733 lines on Redmine where it printed 31,191, with nothing lost ([#470](https://github.com/rigortype/rigor/pull/470), [#434](https://github.com/rigortype/rigor/issues/434)).
  - A row with no label in either lane says nothing at all and is now omitted, which is 1,953 of Redmine's 4,683 units. The unresolved-reason block is collapsed to a count that `--why` expands, and the report closes with a footer counting the proven and the declared lanes apart, because only the first can ever fail a build.
  - `--why` also names the plugin row behind each declared label, which nothing did before: a bundled plugin's row is trusted and so leaves no taint line to read it off. `--full` still prints exactly what the old default did, and `--format json` carries the same totals as the footer.

- **[cli]** A path argument to `rigor effects` selects which methods are **printed** instead of narrowing the analysis, so it reports exactly what the whole-project run reports for those methods ([#468](https://github.com/rigortype/rigor/pull/468), [#439](https://github.com/rigortype/rigor/issues/439)).
  - `rigor effects app/controllers/issues_controller.rb` used to answer `IssuesController#create: [] …?` where the whole-project run answered several labels, and nothing distinguished that from a method which genuinely does nothing. A note on stderr now says how many of how many units you are looking at, and a path that names no method says so instead of printing an empty report.

- **[effects]** A call on an optional receiver is read as a call on the class behind it, so `@record.save` in a method other than the one that assigned `@record`, and `thing&.destroy!` after a `find_by`, both report what they do ([#459](https://github.com/rigortype/rigor/pull/459), [#455](https://github.com/rigortype/rigor/issues/455)).
  - Both are ordinary idioms, and both used to contribute nothing while the row still claimed to be exhaustive. On Redmine the entry points recorded as writing to the database go from 27 to 35 and on Mastodon from 114 to 169; three of Redmine's twenty-seven `#update` actions now record the write they perform, where none did before.

- **[plugins]** `rigor effects` reports the job enqueues and mail sends a Rails application performs ([#464](https://github.com/rigortype/rigor/pull/464), [#456](https://github.com/rigortype/rigor/issues/456)).
  - `job.enqueue` and `email.send` shipped in the vocabulary with nothing able to produce them: across two real applications the count of both was zero. A Sidekiq worker has no base class, so a plugin row could never reach one; the ancestry walk now follows included modules as Ruby's own method lookup does, `rigor-sidekiq` gained the enqueue rows, and a mail delivery is attributed through the whole receiver chain.
  - On Redmine 175 methods now declare `email.send` and 173 `job.enqueue`, where none did; on Mastodon 737 declare `job.enqueue` and 39 `email.send`. `rigor check`'s diagnostics are unchanged on both.

- **[plugins]** A class you subclass from a gem no longer cuts off the effects Rigor knows about it, so `class UserMailer < Devise::Mailer` and `class Auth::SessionsController < Devise::SessionsController` get ActionMailer's and ActionPack's effects ([#467](https://github.com/rigortype/rigor/pull/467), [#465](https://github.com/rigortype/rigor/issues/465)).
  - Rigor reaches a framework's effects by following your own `class … <` and `include` lines, so a chain that leaves your source never came back. A bundled plugin can now declare the ancestry its own gem introduces, and `rigor-devise` declares the six; on Mastodon that is 68 methods declaring `email.send` where 39 did.

- **[effects]** A call on a class the source names by constant gets that class's effects even when no signature for it is installed, so `Net::IMAP.new(…)`, `Net::POP3.APOP(…)` and `Net::FTP.open(…)` report `io.net` instead of nothing ([#466](https://github.com/rigortype/rigor/pull/466), [#463](https://github.com/rigortype/rigor/issues/463)).
  - Rigor withheld a catalogued class's default effects whenever it could not type the receiver, which is right when it had to guess the class and wrong when you wrote the class's name. Whether a call was reported therefore depended on whether `rbs` happens to ship a signature for the library, and Redmine's IMAP and POP3 mail pollers reported no network access at all.

- **[effects]** `Socket.gethostname` and the other calls that read this machine's own identity report `io` rather than `io.net`, so a method no longer reads as network traffic because something under it looked up a hostname ([#462](https://github.com/rigortype/rigor/pull/462), [#458](https://github.com/rigortype/rigor/issues/458)).
  - On Redmine the label travelled a long way from its source, because `Mailer` builds each Message-ID from the hostname: 219 of 4,234 rows claimed `io.net`, including every model `save`. Three rows carry it now, all of them genuine DNS resolution, and `Socket.gethostbyname` and every other socket call are unchanged.

- **[effects]** An effect envelope written on a class or module as an rbs-inline comment is now checked, instead of being silently ignored while the identical bound in a `.rbs` file worked ([#461](https://github.com/rigortype/rigor/pull/461), [#452](https://github.com/rigortype/rigor/issues/452)).
  - It is the cheapest bound in the feature: one line above `class Memo`, no per-method annotation, distributed over every method of the class. Before this, writing one and getting a clean run meant nothing had been checked; a method's own annotation still wins over the class bound.

- **[effects]** A `super` call contributes its parent implementation's effects to a method's summary, and a `super` whose parent Rigor cannot resolve marks the summary non-exhaustive instead of reporting the method as effect-free ([#453](https://github.com/rigortype/rigor/pull/453), [#446](https://github.com/rigortype/rigor/issues/446)).
  - An override that delegates upward is judged against its declared envelope like any other method, where `def emit = super` used to pass `%a{pure}` while its parent was correctly flagged.

- **[effects]** `effect.envelope-exceeded` is reported on every run, not only on the first one after clearing `.rigor/cache` ([#442](https://github.com/rigortype/rigor/pull/442), [#428](https://github.com/rigortype/rigor/issues/428)).
  - A warm run used to serve its diagnostics from the cache without re-checking your envelopes, so a project whose CI caches `.rigor/cache` between builds saw the check fire once and stay silent afterwards, with the silence reading as a clean result. Editing an envelope, a `tolerated:` list or an annotation now re-judges your code even though no Ruby file changed, which costs a warm run about three quarters of a second on a mid-sized Rails application.

- **[effects]** `effect.annotations-unchecked` reports an `%a{pure}` written as an rbs-inline comment in your Ruby source on every run that analyses anything, not only on the runs that write the result cache ([#447](https://github.com/rigortype/rigor/pull/447), [#441](https://github.com/rigortype/rigor/issues/441)).
  - `rigor check --no-cache`, `--workers N` and `--incremental` used to report the notice for an annotation in a `sig/*.rbs` file and stay silent about the identical annotation written inline, so which lane you had chosen decided whether you learned your annotations were inert.

- **[effects]** An effect envelope written as an rbs-inline comment reports the line of the comment itself, instead of a line number from the synthesized signature that could land inside a file's licence header ([#450](https://github.com/rigortype/rigor/pull/450), [#432](https://github.com/rigortype/rigor/issues/432)).

- **[plugins]** `rigor effects` reports the database write on an ActiveRecord model's own `save` row, where a model with a callback or a uniqueness validator used to read `AuthSource#save: ≤ io.db.read` ([#445](https://github.com/rigortype/rigor/pull/445), [#440](https://github.com/rigortype/rigor/issues/440)).
  - The write was always reported at the call sites; what was missing was the row that names the method, which is the row a Rails reviewer checks first. `save!`, `update`, `touch`, `increment!`, `destroy` and the `create` twins were all affected the same way and all report the write now.

- **[cli]** `rigor effects explain --symbol` with a misspelled key is an error naming the nearest one, instead of printing `Nothing to explain.` and exiting 0 ([#471](https://github.com/rigortype/rigor/pull/471), [#435](https://github.com/rigortype/rigor/issues/435)).
  - Exiting 0 is exactly what a method with no effects does, so a typo and a real answer were indistinguishable, and a script could not tell them apart at all.

- **[cli]** `rigor effects check`'s failure footer offers `rigor effects explain` beside `rigor effects update` ([#471](https://github.com/rigortype/rigor/pull/471), [#435](https://github.com/rigortype/rigor/issues/435)).
  - The two answer the questions a drift report raises, and the footer used to name only the one that makes the report go away.

- **[cli]** A first `rigor effects update` explains what to do about an empty `reach:` in the written file itself, not only in the run's output ([#471](https://github.com/rigortype/rigor/pull/471), [#436](https://github.com/rigortype/rigor/issues/436)).
  - `reach:` records what your entry points cause, which is the half of the snapshot most worth reviewing, and a project that never configured one committed the other half with no way to know. The default stays empty deliberately, so the run names the presets your plugins actually registered and the file carries the same hint.

- **[cli]** A mistake in `.rigor.yml` prints a single `rigor:` line naming the key instead of a Ruby backtrace ([#451](https://github.com/rigortype/rigor/pull/451), [#433](https://github.com/rigortype/rigor/issues/433)).
  - An `effects.snapshot.reach:` preset no plugin registered, a malformed `effects.attribution:` key and an unparseable file are all covered, and the unregistered-preset error lists the presets your project's plugins actually registered.

- **[cli]** The `documentation_url` carried by every diagnostic in `rigor check --format json`, and printed by `rigor explain`, now resolves instead of landing on a 404 ([#444](https://github.com/rigortype/rigor/pull/444), [#438](https://github.com/rigortype/rigor/issues/438)).
  - It pointed at a GitHub branch this project has never had. Three more links shipped with the same wrong branch and are fixed too: the plugins link in the `.rigor.yml` that `rigor init` writes, and the homepage and installation links of the VS Code extension.

- **[plugins]** `rigor-activesupport-core-ext` no longer collides with rbs's bundled `stdlib/date` on `Date#to_time`, so `Date` and `DateTime` type as themselves instead of degrading to an untyped value for every project that activates the plugin ([#448](https://github.com/rigortype/rigor/pull/448), [#437](https://github.com/rigortype/rigor/issues/437)).
  - `date.to_time(:utc)` keeps resolving through ActiveSupport's widened arity.

- **[plugins]** The experimental `ruby_box` plugin-isolation strategy reaches a gem-installed target library, and declines cleanly when the library is genuinely absent instead of aborting the whole run with a `LoadError` ([#469](https://github.com/rigortype/rigor/pull/469), [ADR-39](docs/adr/39-plugin-target-library-invocation.md)).
  - `Ruby::Box#require` resolves only plain load-path files, so the strategy falls back to the require inside the box, which activates gems. An absent library now silences the affected check, as the other strategies already did.

## [0.3.4] - 2026-08-21

v0.3.4 is about what your code *does*, not only what it returns. The headline is the effect system ([ADR-103](docs/adr/103-effect-labels.md)): `rigor effects` reports the effects of every method, `rigor effects update` commits that report as a reviewable record the way `db/schema.rb` records a schema, and an `%a{pure}` or `%a{rigor:v1:effect io.db}` annotation becomes a contract Rigor checks. The whole family is opt-in behind an `effects:` block, and a project without one gets a byte-identical `rigor check` at unchanged cost. Alongside it, `rigor unused` ([ADR-102](docs/adr/102-unused-code-reachability-report.md)) reports classes and modules nothing reachable references, with your plugins supplying the roots a framework reaches by name. Other fixes cover constant resolution through the ancestor chain and several `rigor unused` edge cases.

### Added

- **[effects]** `rigor effects` reports what each method *does* — `io.output.stdout`, `nondet.time`, `mutate.self` — beside what it returns, opt-in through an `effects:` block in `.rigor.yml` and never as a diagnostic ([#396](https://github.com/rigortype/rigor/pull/396), [#379](https://github.com/rigortype/rigor/issues/379), [ADR-103](docs/adr/103-effect-labels.md)).
  - Labels are transitive across the project's own call graph, including every override of a called method, and a method whose calls could not all be resolved is marked "and possibly more" with the reason rather than being guessed at — an unresolved call never turns into a finding. Methods that only mutate objects they allocated themselves are treated as pure and omitted; `--full` lists them, and `--format=json` carries each method's own contribution broken down per origin.
  - With no `effects:` block nothing changes: `rigor check` produces byte-identical output at unchanged cost. See [`rigor effects`](docs/manual/02-cli-reference.md#rigor-effects) and [the effect-labels specification](docs/type-specification/effect-labels.md).
- **[effects]** `rigor effects` now reads a hand-audited catalogue of Ruby's core and standard library, so `open("|cmd")` reports running a subprocess where `open(path)` reports reading a file, `Time.new(2020, 1, 1)` is effect-free where `Time.new` reads a clock, and `File.open(path, "w")` is a write where the same call without a mode is a read ([#399](https://github.com/rigortype/rigor/pull/399), [#380](https://github.com/rigortype/rigor/issues/380), [ADR-103](docs/adr/103-effect-labels.md)).
  - Around 80 core and stdlib classes are covered — `Kernel`, `IO` / `File` / `Dir` / `FileUtils` / `Pathname`, `Process`, the socket and `Net::HTTP` families, `ENV`, `Time` / `Date`, `Random` / `SecureRandom`, `GC` / `ObjectSpace`, `Logger`, the object-model writers — and a method a listed class does not name falls back to that class's posture, so an unfamiliar `IO` method still reports `io` rather than nothing. Classes the catalogue does not list are unchanged: they contribute nothing and are never guessed at. Every label reported is an upper bound, and where an argument does not settle the question the broader label is reported rather than the convenient one.
- **[effects]** `rigor effects update` writes a committed record of what your code does — `.rigor-effects.yml`, the effect equivalent of `db/schema.rb` — and `rigor effects check` fails CI when a pull request changes it, so an unintended effect is caught by review rather than by an annotation you had to write first ([#398](https://github.com/rigortype/rigor/pull/398), [#415](https://github.com/rigortype/rigor/pull/415), [#381](https://github.com/rigortype/rigor/issues/381), [#411](https://github.com/rigortype/rigor/issues/411), [ADR-103](docs/adr/103-effect-labels.md)).
  - The file lists what is attributable: a method whose effects the analyzer could not read exhaustively, and which proved nothing, is left out rather than recorded as a row saying only that — `--full` records the whole table. It keeps each listed method's own effects, plus the full reach at the entry points `effects.snapshot.reach:` names, and its diff *is* the review signal: `PaymentGateway#charge + io.net.http` next to the code that caused it. Intent is expressed by regenerating and committing the file. `rigor effects explain` prints the route behind a change — `OrdersController#create → OrderService#place → PaymentGateway#charge → Net::HTTP.get` — and `rigor effects diff` prints the same comparison without gating.
  - A removal fails the gate as readily as an addition, because a job that stopped enqueueing is news too; `effects.snapshot.gate: additions` opts into a growth-only ratchet instead, and `effects.tolerated:` lists labels whose comings and goings you do not want to review. The record itself never hides anything — the policy applies when a difference is judged, so a policy edit diffs your config rather than the record. Two runs over one tree write byte-identical files. See [the effect snapshot](docs/manual/02-cli-reference.md#the-effect-snapshot).
- **[effects]** Effect summaries are cached, so `rigor effects` after `rigor check` in the same job costs the propagation and nothing else, and an incremental run re-reads only the files you edited ([#401](https://github.com/rigortype/rigor/pull/401), [#382](https://github.com/rigortype/rigor/issues/382), [ADR-103](docs/adr/103-effect-labels.md)).
  - The summaries are cached under their own identity — Rigor's effect vocabulary, its built-in catalogue and your `effects:` block — separately from the diagnostics your check already caches. Upgrading Rigor to a version whose catalogue changed re-reads your effects without re-running your check, and turning `effects:` on or off invalidates neither.
  - A project with no `effects:` block is untouched: nothing extra is written, the cache key is unchanged, and `rigor check` still answers from a warm cache exactly as before.
- **[cli]** `rigor unused` reports project classes and modules that nothing reachable references — a starting point for dead-code removal ([#357](https://github.com/rigortype/rigor/pull/357), [#347](https://github.com/rigortype/rigor/issues/347), [ADR-102](docs/adr/102-unused-code-reachability-report.md)).
  - Constants something can name at runtime are demoted to a `cannot decide` section with the reason rather than claimed as unused: `"Foo".constantize` names `Foo` exactly and counts as an ordinary reference, while `"Foo::#{key}".constantize` marks everything under `Foo` undecidable, and a class name appearing as a string in a `.yml` or template file demotes it the same way.
  - Read it as a review queue rather than a defect list: on a hand-adjudicated corpus target only 7% of the rows were genuinely unused, which is why this is its own command and never a `rigor check` diagnostic. Reachability is computed from roots — `--entry-point=GLOB` plus anything referenced at file level — so a cluster of classes that only reference each other is still reported. Classes reachable only from test code get their own section, because a class used solely by its own spec is dead production code with a live test. References are harvested from `.rake` tasks, `config/`, specs and your `sig/` as well as the analysed paths.
- **[effects]** You can now declare what a method is *allowed* to do and have Rigor check it: `%a{rigor:v1:effect io.db}` in your RBS bounds a method to the database, `%a{pure}` bounds it to nothing at all, and a method that exceeds its bound is reported as `effect.envelope-exceeded` ([#402](https://github.com/rigortype/rigor/pull/402), [#383](https://github.com/rigortype/rigor/issues/383), [ADR-103](docs/adr/103-effect-labels.md)).
  - The bound covers everything the method's code reaches, so a repository declared `io.db` that calls a helper that calls `Net::HTTP` is a finding — and the message names the route it took, the label it proves, your own spelling of the bound, and the signature line you wrote it on. The diagnostic sits on the Ruby `def`, where the fix goes and where `# rigor:disable` works.
  - `%a{pure}` is rbs' own purity annotation, the one Steep already reads, rather than a Rigor synonym for it; mutating objects the method itself allocated and never let out is tolerated by every envelope, so memoising into a local array is still pure. Write either annotation on a `class` or `module` and it applies to every method of that class — reopenings and `attr_writer`-generated methods included, never to subclasses — with a per-method annotation winning over it. The same annotations work in `.rb` files through rbs-inline's `# @rbs %a{…}` comments.
  - Nothing fires that Rigor did not prove: a call it could not resolve makes a summary read "and possibly more", and *possibly* is never a finding. Nothing fires at all without an `effects:` block, so an `%a{pure}` you wrote for Steep stays inert until you opt in; `effects.check: false` keeps the report and the snapshot while silencing the diagnostic. A label the vocabulary does not recognise makes the whole annotation read as unbounded rather than as the part that parsed, so a typo cannot turn into findings on correct code. See [effect envelopes](docs/type-specification/effect-labels.md#effect-envelopes).
- **[effects]** A misspelt effect label no longer fails in silence: `%a{rigor:v1:effect io.bd}` still bounds nothing — a typo can never turn into findings on correct code — but Rigor now says so as `effect.unknown-label`, on the line you wrote it on, naming the nearest real label ([#403](https://github.com/rigortype/rigor/pull/403), [#384](https://github.com/rigortype/rigor/issues/384), [ADR-103](docs/adr/103-effect-labels.md)).
  - It fires only where the spelling is evidently meant to be a label: close to a known one, next to a known one in the same list, carrying a dot, or retired by a vocabulary bump (in which case it names the replacement). A word the vocabulary resembles in no way stays silent, because you may be opening a root of your own. The same check reads the labels in `effects.tolerated:`, reported at `.rigor.yml`. Authored `:info`, `:warning` under `strict`, and gated by `effects.check` like `effect.envelope-exceeded` — opting into envelope enforcement is what turns on the diagnostic that keeps it honest.
- **[effects]** Effect annotations in a project with no `effects:` block now earn one `effect.annotations-unchecked` `:info` per run instead of being silently inert ([#403](https://github.com/rigortype/rigor/pull/403), [#384](https://github.com/rigortype/rigor/issues/384), [ADR-103](docs/adr/103-effect-labels.md)).
  - An annotation must never turn effect collection on by itself — one line in one signature file would otherwise make every run of the project more expensive — so this is how a `%a{pure}` nobody checks tells you it is doing nothing. `effects: {}` and `effects: {check: false}` are both answers and silence it, and a project with no effect annotations at all is untouched.
- **[docs]** `%a{rigor:v1:…}` annotations are documented as writable in `.rb` files through rbs-inline's `# @rbs %a{…}` comments — which has worked since [ADR-93](docs/adr/93-default-rbs-inline-ingestion.md) and was previously documented as impossible ([#403](https://github.com/rigortype/rigor/pull/403), [#384](https://github.com/rigortype/rigor/issues/384)).
  - `%a{}` is rbs-inline's own upstream grammar, not a Rigor dialect, and every directive is read from the same annotation object whichever buffer it arrived in. There is still no Rigor-only comment directive: `# rigor:` comments remain suppression-only. See [RBS::Extended annotations](docs/manual/16-rbs-extended-annotations.md).
- **[effects]** Effect envelopes can now be written by **convention** in `.rigor.yml` instead of per method: one `effects.envelopes:` stanza bounds a whole architectural layer, by path glob or by constant namespace, so a project with no RBS at all gets a checked contract on day one ([#404](https://github.com/rigortype/rigor/pull/404), [#385](https://github.com/rigortype/rigor/issues/385), [ADR-103](docs/adr/103-effect-labels.md)).
  - `match: "app/presenters/**/*.rb"` with `effect: []` says presenters do not query; `namespace: "Policies::*"` bounds exactly the classes one segment under `Policies`, and `Policies::**` reaches any depth. A stanza distributes to every method of every class it selects, exactly as a class-level annotation does, and `effect.envelope-exceeded` names the stanza it broke — `.rigor.yml effects.envelopes[0]` — while staying positioned on the Ruby `def`. Nearest wins: a per-method annotation beats a class-level one, which beats a stanza; among stanzas the first match wins, so a list reads top to bottom.
- **[effects]** `effects.attribution:` tells Rigor what a gem method does — `{"Net::HTTP.get": [io.net.http]}` — for code it cannot read ([#404](https://github.com/rigortype/rigor/pull/404), [#385](https://github.com/rigortype/rigor/issues/385), [ADR-103](docs/adr/103-effect-labels.md)).
  - The labels are reported as a declared upper bound (`≤ io.net.http` in the report, `declared:` in the snapshot) and never as something proven, so an attribution can never make a diagnostic fire; the call still counts as unresolved, because you told Rigor what that code does and Rigor did not read it. Authored `:warning`, `:error` under `strict`, silent without an `effects:` block and under `effects.check: false`.

- **[cli]** A parallel run whose workers all die now degrades and says so instead of waiting for them forever ([#416](https://github.com/rigortype/rigor/pull/416), [#414](https://github.com/rigortype/rigor/issues/414)).

- **[engine]** `rigor unused` no longer lets a class root itself through its own RBS signature ([#374](https://github.com/rigortype/rigor/pull/374), [#373](https://github.com/rigortype/rigor/issues/373)).
  - A mixin argument inside a signature was recorded pre-qualified with the enclosing class name, and the report resolves a reference to a member as a reference to its owner — so `SignageResource::Alba::Resource` peeled back to `SignageResource` and rooted it. On one application this hid three genuinely dead classes on the default run; they were visible only with `signature_paths:` emptied.
- **[cli]** `rigor unused --entry-point` now matches `**` the way the manual documents it ([#372](https://github.com/rigortype/rigor/pull/372), [#371](https://github.com/rigortype/rigor/issues/371)).

## [0.3.3] - 2026-08-09

v0.3.3 is a false-positive clearance release: six patterns where Rigor reported an error on Ruby that runs correctly are retired, and most are plain idioms rather than exotic corners. `Class.new do … end` bodies, `Array.new(n) { … }`, `defined?` operands, singleton bodies opened on a constant, a project helper colliding with a DSL matcher, and a nil guard on a literal-hash lookup all stop warning. Inference is also more precise where it was merely vague: a generic method that passes an argument straight through now returns that argument's own type, and `inspect` / `to_s` / `Array#*` fold to exact values. The rest is correctness housekeeping, including a suppression marker that recognised its own documentation.

### Added

- **[engine]** A generic method whose signature passes an argument straight through, such as `Ractor.make_shareable(obj)` typed `[T] (T) -> T`, now returns the argument's own type instead of untyped ([#304](https://github.com/rigortype/rigor/pull/304), [#303](https://github.com/rigortype/rigor/issues/303)).
  - The bound type carries into a generic return such as `Array[T]`. The binding is deliberately declined wherever a method you defined yourself shadows the signature that resolved, so an imprecise answer never becomes a confidently wrong one.
- **[engine]** `Array#inspect` / `#to_s` and `Hash#inspect` / `#to_s` now fold to the exact string when every element, or every value of a fully-known hash shape, is a constant ([#305](https://github.com/rigortype/rigor/pull/305), [#121](https://github.com/rigortype/rigor/issues/121)).
  - `Array#*` folds both of its forms: a String argument joins, an Integer argument repeats.

### Fixed

- **[engine]** Code inside `Class.new do … end` is now analyzed as the new class's own body rather than as top-level code ([#338](https://github.com/rigortype/rigor/pull/338), [#319](https://github.com/rigortype/rigor/issues/319)).
  - `attr_reader` and friends stop being reported as unresolved top-level calls, and the class the call returns carries the methods and the `initialize` arity that body declares instead of `Object`'s. The `Module.new`, `Struct.new` and `Data.define` block forms are covered by the same change.
- **[engine]** `Array.new(n) { … }` now takes its element type from the block instead of the no-block overload's `nil` fill ([#336](https://github.com/rigortype/rigor/pull/336), [#317](https://github.com/rigortype/rigor/issues/317)).
  - `Array.new(2) { "s" }[0].upcase` no longer warns about calling a method on nil, while `Array.new(2)[0].upcase` still does, because those elements really are nil.
- **[engine]** Code written inside `defined?(…)` is no longer analyzed as if it ran ([#337](https://github.com/rigortype/rigor/pull/337), [#318](https://github.com/rigortype/rigor/issues/318)).
  - The bare `defined? x && y` spelling swallows the whole `&&` chain as its operand, so a guard like `defined? @subject && !@subject.options.empty?` stops flagging a call the runtime never makes. The parenthesised `defined?(x) && y` form is a different expression that really does evaluate its right-hand side, and still reports.
- **[engine]** A constant holding a plain object with its own singleton body no longer reports every method in that body as undefined ([#339](https://github.com/rigortype/rigor/pull/339), [#320](https://github.com/rigortype/rigor/issues/320)).
  - Both the `class << Merger = Object.new` idiom, as in haml's attribute merger, and a separate `class << Merger` on an already-assigned constant now resolve to the method you wrote and take its inferred return type. A name the body does not define still reports.
- **[engine]** A helper your project defines at the top level of one file no longer captures a same-named method a DSL block gets from a mixin somewhere else ([#340](https://github.com/rigortype/rigor/pull/340), [#316](https://github.com/rigortype/rigor/issues/316)).
  - Calling RSpec's `output`, `include` or `match` matchers in a spec file stops being checked against your helper's return value. A helper called from genuine top-level code, or defined in the same file as the block that calls it, resolves exactly as before.
- **[engine]** A nil guard on a lookup in a literal hash no longer warns that the condition is always true or always false ([#327](https://github.com/rigortype/rigor/pull/327), [#313](https://github.com/rigortype/rigor/issues/313)).
  - `rank = RANKS[name]` followed by `return if rank.nil?`, and the `||` / `&&` spellings that guard two lookups at once, are live code: a key that is not in the table really does read as nil at runtime. The branch such a guard protects is no longer dropped from the inferred type either.
- **[engine]** Copying a nilable attribute into a local before passing it no longer warns about an argument type mismatch ([#328](https://github.com/rigortype/rigor/pull/328), [#324](https://github.com/rigortype/rigor/issues/324)).
  - `r = @right` followed by `insert(r)` now gets the same answer as passing `@right` directly, instead of only from the check that reports calling a method on it.
- **[rigor check]** A `# rigor:disable` / `# rigor:disable-file` marker is now recognised only when it opens the comment ([#314](https://github.com/rigortype/rigor/pull/314), [#306](https://github.com/rigortype/rigor/issues/306)).
  - A comment that merely quotes the syntax, such as documentation prose, a doc-tool `##` line or an `=begin` block, no longer silences diagnostics and no longer warns about its own quoted examples. A whole-line or trailing directive works exactly as before, including with no space after the `#`.

## [0.3.2] - 2026-08-08

v0.3.2 makes the mutation tier of `rigor coverage` practical on a whole project: each file's measurement is cached, the run forks across workers, and two opt-in bleeding-edge features let it choose sites and judge kills with the same cross-file knowledge `rigor check` already has. The editor surface widens in the same direction, so a save, an in-flight buffer, and a batch of open buffers are all now answered against the whole project rather than one file at a time. The `dry-schema` and `dry-validation` plugins type a Contract's own result shape, and a batch of engine fixes retires false positives on correct code. The largest correctness fix is the least visible: Rigor's own bundled signatures collided with the ones the `rbs` gem ships, silently disabling type checking for `Gem::Specification`, `Time`, `Bundler` and six more classes.

### Added

- **[rigor coverage]** `--protection --mutation` (Tier 2) now caches each file's measurement and serves it back on a re-run while nothing that could change it has moved, so a whole-project deep dive stops re-measuring the files nobody touched ([#134](https://github.com/rigortype/rigor/issues/134), [#270](https://github.com/rigortype/rigor/pull/270)).
  - A cached result is served only while the file itself, every file it was recorded as reading from, the resolved configuration, your `sig/`, the gem set, the engine version, `--limit` / `--seed`, and the adopted bleeding-edge features are all unchanged. Edit one file and that file plus the files recorded as reading from it are re-measured; the rest are served.
  - It reads the cross-file dependency edges a `rigor check --incremental` run records, so warm one once per project. Without a usable snapshot, under `--no-cache`, or with `dependent-closure-kill-oracle` adopted, every file is measured afresh and never silently served.
  - One stderr line always reports which of the two happened, and a run where the measurement harness itself raised is never cached.
- **[rigor coverage]** `--protection --mutation` (Tier 2) can now pick the sites it measures against the same cross-file project discovery Tier 1 already uses, behind the new `discovery-seeded-mutation-sites` bleeding-edge feature ([#253](https://github.com/rigortype/rigor/issues/253), [#259](https://github.com/rigortype/rigor/pull/259)).

Seeded, both tiers judge a site by one standard, and since a constant receiver is the dominant call shape in a Rails tree the gap was largest exactly where the report is most used.

### Changed

- **[rigor coverage]** `--workers=N` now applies to the mutation tier (`--protection --mutation`), forking the per-file measurement across worker processes with byte-identical output ([#134](https://github.com/rigortype/rigor/issues/134), [#257](https://github.com/rigortype/rigor/pull/257)).
  - Rigor's own `lib/rigor/analysis` falls from 35s to 23s at eight workers on a 12-core machine. The flag was already accepted and documented on that path but silently ignored; it now resolves the same way it does for `rigor check` (`--workers` › `RIGOR_RACTOR_WORKERS` › `parallel.workers:` › `0`), and the whole-project pre-pass is still paid once, on the parent.
  - The fused `--with-tests` tier deliberately stays sequential, because its test hook shells out to your test runner and concurrent runs would race over one working tree. An explicit `--workers` there is now reported as ignored on stderr instead of being dropped.
- **[perf]** A fork-parallel run's workers now inherit what is left of the run's deferred-YJIT warm-up window instead of restarting it, so a worker JITs at the moment the run as a whole would have ([#134](https://github.com/rigortype/rigor/issues/134), [#258](https://github.com/rigortype/rigor/pull/258)).
  - It is one warm-up per run rather than one per worker, for both the `rigor coverage` scans and the `rigor check` pool. Without it a long parallel coverage run was *slower* than the sequential one it replaced, because `fork` does not carry deferred YJIT into a child.
- **[rigor check]** A cold run on a project that ships RBS spends roughly a third fewer allocations, because the signature scan that looks for references to undeclared types no longer builds every class in the project to find them ([#207](https://github.com/rigortype/rigor/issues/207), [#240](https://github.com/rigortype/rigor/pull/240)).
  - It reads the declarations instead, applying the same membership test RBS itself applies, so the same names are found. On Rigor's own `lib` that scan falls from 7.84M allocations to 25k, or 33% of the run to 0.15%, and on a Rails-shaped project the whole run drops 84%. Diagnostics are unchanged across the eight RBS-shipping projects the change was measured on.
- **[rigor check]** `--verify-incremental` now refuses an editor buffer (`--tmp-file` / `--instead-of`) instead of silently comparing it against a full analysis of the files on disk ([#244](https://github.com/rigortype/rigor/pull/244)).

### Fixed

- **[engine]** Nine classes including `Gem::Specification`, `Time`, `DateTime` and `Bundler` no longer collapse to an untyped receiver, so `spec.version` comes back with its real type and a typo on any of them is reported again ([#299](https://github.com/rigortype/rigor/issues/299), [#300](https://github.com/rigortype/rigor/pull/300)).
  - Rigor's own bundled signatures re-declared methods the `rbs` gem already ships, and each collision silently disabled type checking for the whole class. The affected classes were `Gem::Specification`, `Gem::Dependency`, `Gem::Requirement`, `Bundler`, `Bundler::LockfileParser`, `Time`, `DateTime`, `BigMath` and `Nokogiri::CSS::Parser`.

- **[engine]** A class whose RBS instance or singleton definition fails to build now prints a one-line stderr warning naming the class, instead of silently degrading every call on it to `Dynamic` with no signal anywhere ([#295](https://github.com/rigortype/rigor/issues/295), [#296](https://github.com/rigortype/rigor/pull/296)).

## [0.3.1] - 2026-07-29

v0.3.1 follows `rbs` 4.1.0. The upgrade is invisible in normal use, but 4.1's core-signature rewrite would otherwise have silenced two argument checks, and its new in-object hash cache would have made every core class read as undefined on a warm cache — so most of this release is keeping the analysis honest against it. The language server also moves to incremental document sync, plugins gain a `generation_cap:` for bounding their own cache slice, and the browser playground shows inferred types on first load.

### Added

- **[lsp]** The language server now applies each editor edit to the buffer it already holds, instead of receiving and rebuilding the whole file on every keystroke ([#221](https://github.com/rigortype/rigor/pull/221), [#144](https://github.com/rigortype/rigor/issues/144)).

- **[rigor-actioncable]** A channel's `#receive(data)` now types `data` as `Hash` instead of `Dynamic[Top]`, so misuse inside the method body is caught ([#220](https://github.com/rigortype/rigor/pull/220), [#139](https://github.com/rigortype/rigor/issues/139)).
  - The contract follows the plugin's `channel_search_paths` setting rather than assuming `app/channels`.

### Changed

- **[dependencies]** Rigor now develops and tests against `rbs` 4.1.0, with the supported range unchanged at `>= 3.0, < 5.0` ([#225](https://github.com/rigortype/rigor/pull/225)).
  - 4.1 renames the type parameters of several core generics: `Array[Elem]` is now `Array[E]`, and `Enumerator[Elem, Return]` is now `Enumerator[E, R]`. Binding is positional, so a project `.rbs` that reopens one of them under the old name keeps working — following the rename is cosmetic.

  - The toolbar button starts in its "Hide types" state, so the toggle still turns the overlay off.
- **[plugin API]** `Plugin::Base.producer` accepts a `generation_cap:` declaring how many generations of a producer's cache entries survive a compaction pass ([#215](https://github.com/rigortype/rigor/pull/215), [#151](https://github.com/rigortype/rigor/issues/151)).

- **[rigor check]** The `static.value-use.void` rule no longer costs a separate AST traversal per file, whether or not it is enabled ([#210](https://github.com/rigortype/rigor/pull/210), [#207](https://github.com/rigortype/rigor/issues/207)).

- **[inference]** `[1, 2, 3].fetch("x")` is reported again under `rbs` 4.1, which rewrote `Array#fetch`'s block overload to use a bounded method type parameter ([#225](https://github.com/rigortype/rigor/pull/225)).

- **[inference]** `a[1..2]` still types as `Array[E]?` under `rbs` 4.1, which rewrote `Array#[]`'s slicing overload to take the `range[T]` alias rather than a `Range` ([#225](https://github.com/rigortype/rigor/pull/225)).

- **[sig-gen]** Updating an existing signature file now lands on the same nested layout a fresh generation would write ([#214](https://github.com/rigortype/rigor/pull/214), [#153](https://github.com/rigortype/rigor/issues/153)).
  - A class is placed inside its parent's block, and a flat `class Foo` / `class Foo::Bar` pair the file already carried is folded into one nested tree, so getting the canonical shape no longer means deleting the target `.rbs` and regenerating it.

## [0.3.0] - 2026-07-19

This release is dominated by a performance arc that makes repeat and incremental analysis of large Rails apps several times faster: an engine-free warm-hit "null build" floor, semantic propagation gates and per-file seed bundles for `--incremental`, a deadline-armed YJIT, and a broad allocation reduction ([ADR-87](docs/adr/87-null-build-floor.md), [ADR-85](docs/adr/85-seed-bundles-and-lazy-def-node-handles.md), [ADR-89](docs/adr/89-semantic-propagation-gates.md)). Inline rbs-inline annotations now work out of the box, with no `plugins:` entry and no magic comment ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md)). Several new diagnostics land — five PHPStan-derived checks, use-of-`void`, duplicate hash keys, and more — alongside sharper Hash / Struct / `Data` / Kernel value typing and opt-in call-site parameter inference. It also removes the deprecated `type_specifier` plugin hook and the verb-form `docs` / `skill` subcommands (both breaking).

### Added

- **[rigor check]** A new opt-in `parameter_inference: true` setting types an undeclared `def` / `initialize` / setter parameter from the union of its resolved call-site argument types, so the value it flows into — an ivar, a receiver, a fold — is typed and protected on the `check` walk, not just in `coverage --protection` ([ADR-67](docs/adr/67-parameter-type-inference.md) WD6, [#202](https://github.com/rigortype/rigor/pull/202)).
  - It is precision-additive only: an inferred parameter never triggers a new diagnostic, because its call-site union is a lower bound and the in-body rules decline on any value derived from it. Off by default; cannot be combined with `--incremental`.
- **[rigor check]** Using the return of a method whose RBS declares `-> void` as a value — assigning it, calling a method on it, or passing it as an argument — is now reported as `static.value-use.void`, behind the new `use-of-void-value` bleeding-edge feature ([#187](https://github.com/rigortype/rigor/pull/187)).
  - An explicit `-> void` is the author saying "do not rely on this return", so relying on the `top` it recovers to is a mistake worth surfacing. It fires only on a method resolved directly on the receiver's own class (not through an inherited fallback), and a bare-statement `void` call or a genuine `top` value stays silent. It is opt-in because a new required diagnostic is a compatibility change.
- **[rigor check]** `static.value-use.void` now also catches the transitive case — using the value of an undeclared method that just hands back a `-> void` result (`def bar; foo; end` with `foo` declared `-> void`, then `b = bar`), across any number of such hops, naming the original `-> void` method ([ADR-100](docs/adr/100-static-diagnostic-family-and-void-origins.md) WD4, [#195](https://github.com/rigortype/rigor/pull/195)).
  - Any method that can return something else — an explicit `return`, a `rescue` clause, its own declared return type — keeps its callers silent.
- **[rigor check]** A new `flow.duplicate-hash-key` rule flags a Hash literal that repeats a literal key (`{ a: 1, b: 2, a: 3 }`), where Ruby silently keeps the last entry at runtime and only warns under `-w` ([#101](https://github.com/rigortype/rigor/pull/101)).
  - The check is deliberately literal-only so it cannot fire on working code: symbols, plain non-interpolated strings, integers, floats, and `true` / `false` / `nil` participate; interpolated, constant, computed, and `**splat` keys are never compared. Symbol vs string (`:a` vs `"a"`) and Integer vs Float (`1` vs `1.0`) are distinct keys and never collide. Severity is `warning` under `balanced` (`info` lenient, `error` strict); suppress with `# rigor:disable duplicate-hash-key`.
- **[rigor check]** A new `flow.return-in-ensure` diagnostic flags an explicit `return` lexically inside an `ensure` clause, which overrides the method's in-flight return value and silently swallows any exception being raised ([#101](https://github.com/rigortype/rigor/pull/101)).
  - The check is purely syntactic and frame-aware: a `return` inside a nested `def`, a lambda, or a `define_method` block within the `ensure` body does not fire, while a `return` inside a plain block does. Severity is `warning` under `balanced` (`info` lenient, `error` strict). Suppress a deliberate use with `# rigor:disable flow.return-in-ensure`.
- **[rigor check]** A new `flow.shadowed-rescue-clause` diagnostic flags a `rescue` clause that can never run because an earlier clause in the same chain already catches a superclass of every exception class it names (`rescue StandardError => e` followed by `rescue ArgumentError`) ([#101](https://github.com/rigortype/rigor/pull/101)).
  - The rule compares only exception references resolving to concrete classes with known ancestry; dynamic expressions, splats, unresolved constants, and module tags keep it silent, and rescuing narrow-to-wide never fires. Severity: `warning` balanced, `info` lenient, `error` strict; suppress with `# rigor:disable shadowed-rescue-clause`.
- **[rigor check]** A new `call.raise-non-exception` rule flags a `raise x` / `fail x` whose first argument provably cannot be raised — not an Exception class or instance, not a String, and its class defines no `#exception` — so `raise 42`, `raise :symbol`, or `raise nil` surface at check time instead of as a runtime `TypeError` ([#101](https://github.com/rigortype/rigor/pull/101)).
  - The envelope is deliberately conservative: it never fires on `Dynamic` / unresolved types, a union fires only when every arm is independently illegal, the `#exception` duck protocol is honored, an explicit-receiver `obj.raise(...)` is ignored, and a project that redefines `raise` / `fail` silences the rule. Severity: `balanced` / `strict` `:error`, `lenient` `:warning`.
- **[rigor check]** A broken suppression comment is now flagged instead of silently doing nothing: `suppression.unknown-rule` fires on a `# rigor:disable` naming a rule that does not exist, `suppression.empty` when the marker lists no rules, and `suppression.unknown-marker` when the marker word itself is outside Rigor's grammar (the RuboCop reflex `# rigor:disable-next-line`, or `# rigor:enable`) ([#101](https://github.com/rigortype/rigor/pull/101)).
  - A typo'd suppression that no-ops is the worst baseline failure mode, because the author believes the diagnostic is handled. All three are `:warning` in every profile, carry the offending token verbatim, and are themselves suppressible. `plugin.`-prefixed tokens and known non-catalogue engine ids (`rbs_extended.*`, `dynamic.*`, …) are never flagged.
- **[rigor check]** A top-level key in `.rigor.yml` that Rigor does not recognise is now reported instead of silently ignored, with the nearest real key suggested ([#171](https://github.com/rigortype/rigor/pull/171), thank you [#166](https://github.com/rigortype/rigor/issues/166)!).
  - Previously a typo'd `exclude:` loaded in silence, so the run reported errors from the very files you meant to skip. It is a warning, never an error, and appears in `--format=json` under `config_warnings` with `"kind": "unknown_key"`. Top-level keys only — a typo inside a group (`cache: { pth: … }`) is caught by the [JSON schema](schemas/rigor-config.schema.json) as you type.
- **[type inference]** A successful `String#match?` or `=~` against a fully anchored digit/hex/octal/letter pattern now refines the string itself, so a following `Integer(s)` or `s.to_i(16)` is seen as safe ([#185](https://github.com/rigortype/rigor/pull/185)).
  - `if s.match?(/\A\d+\z/)` types `s` as a decimal-integer string in the branch (and `\h`/`[0-9a-fA-F]`, `[0-7]`, `[a-z]`, `[A-Z]`, `[[:digit:]]` map to their matching refinements). The pattern must be anchored with `\A…\z`: an unanchored `/\d+/`, the newline-admitting `\Z`, line anchors `^`/`$`, or one-sided anchoring narrow nothing, because they do not constrain the whole string.
- **[type inference]** The override-signature checks (`def.override-return-widened`, `def.override-param-narrowed`) now compare a generic parent contract at the type its subclass instantiates: when `class Sub < Parent[Integer]`, an inherited `-> T` is checked as `-> Integer` instead of being waved through ([#184](https://github.com/rigortype/rigor/pull/184)).
  - A subclass that leaves the type parameter open still reports nothing, so no correct override is newly flagged.
- **[type inference]** `Struct` and `Data.define` value objects now infer precise member types through a setter and through a block-defined class, in two more cases ([#182](https://github.com/rigortype/rigor/pull/182)).
  - After a straight-line `s.x = 5`, reading `s.x` back now infers the assigned value (and a sibling `s.y` keeps its own value) — where before the whole struct went untyped the moment you wrote to any member. A read is left untyped, exactly as before, when the struct is aliased, passed to another method, or mutated inside a loop or block, so a later write you can't see never makes an earlier read wrong.
  - A `Data.define(:x) do … end` assigned to a plain local variable now folds its member reads too, matching the constant form — unless the block redefines a member's reader (`def x`), in which case the read stays untyped because it would run your method, not return the member.
- **[type inference]** `Array#join` on an array of string literals now infers the exact resulting string: `["a", "b"].join("-")` types as `"a-b"` rather than a generic `String`, matching the precision already given to `[1, 2, 3].join` ([#180](https://github.com/rigortype/rigor/pull/180)).
- **[engine]** Hash literals with Integer, Float, `true` / `false` / `nil` keys now type as a value-pinned `HashShape` instead of degrading to a `Hash[K, V]` union, and a duplicate literal key is resolved last-wins exactly like the runtime ([#102](https://github.com/rigortype/rigor/pull/102)).
  - `{ 1 => 1, 1 => 2, 1.0 => 3, 1.00 => 4 }` types as `{ 1 => 2, 1.0 => 4 }` (previously `Hash[1 | 1.0, 1 | 2 | 3 | 4]`, with the overwritten values polluting the union), and `{ a: 1, a: 2 }` as `{ a: 2 }`. Key identity follows Ruby's `Hash#eql?` semantics: `1` and `1.0` are distinct keys while `1.0` and `1.00` collide. All existing `HashShape` projections (`[]`, `fetch`, `dig`, `key?`, `keys`, `values`, `slice`, …) fold over the new key kinds; RBS erasure stays conservative (a shape with non-Symbol keys degrades to `Hash[K, V]`), and computed / interpolated / `**splat` keys keep today's generic-Hash behaviour. Precision-additive only: no new diagnostics.
- **[engine]** `Kernel#p` / `Kernel#pp` are now typed by their actual runtime contract — they return their argument — so wrapping an expression in a debug print no longer destroys its inferred type ([#102](https://github.com/rigortype/rigor/pull/102)).
  - One argument passes through as a precision-preserving identity (`p(h)` keeps `h`'s exact type; a `Dynamic` argument stays `Dynamic`), several arguments come back as the tuple of their types (`p 1, 2` → `[1, 2]`), and the zero-arg form keeps the exact `nil`. The fold declines wherever it cannot be attributed to Kernel itself: an explicit non-Kernel receiver, a discovered user redefinition of `p` / `pp`, or a splatted / forwarded argument list.
- **[engine]** More Kernel conversion functions constant-fold when their inputs are value-pinned: `format` / `sprintf` with a constant template and constant arguments fold to the exact string, `String()` folds scalar literals (`String(42)` → `"42"`), and `Hash()` covers the trivially-sound shapes (`Hash(nil)` / `Hash([])` → `{}`) ([#102](https://github.com/rigortype/rigor/pull/102)).
- **[sig-gen]** `rigor sig-gen` now parses every signature it renders before emitting it, so it can no longer write RBS that `rbs` itself rejects ([#97](https://github.com/rigortype/rigor/pull/97)).
  - A method whose rendered line does not parse is skipped (`sig.skipped.unrenderable-rbs`) and reported on stderr, leaving the rest of the signatures valid; under `--write`, a file whose assembled content does not parse is refused (the existing file is left untouched) and the command exits `1`. Such a skip is a Rigor rendering defect, not a property of your code, and the report says so.
- **[engine]** An unparseable `.rbs` under `signature_paths:` is now reported as the `rbs.coverage.quarantined-signature` warning, so a broken signature file is visible everywhere a diagnostic is — `--format json`, SARIF, GitHub / GitLab annotations, the LSP — instead of only as a line on stderr ([#96](https://github.com/rigortype/rigor/pull/96)).
  - Such a file is quarantined (skipped) so the rest of the RBS environment still loads, but the types it declared are absent and the run comes back quieter, not cleaner — which reads as clean in CI. The diagnostic names the skipped file and the fix (`rbs validate`), and `rigor doctor` now reports the condition as a degraded RBS environment.
- **[cli]** The bleeding-edge overlay ships its first feature, `reject-unparseable-signatures`, which promotes `rbs.coverage.quarantined-signature` to `:error` so a broken signature file fails the run the way a broken source file already does ([ADR-50](docs/adr/50-release-engineering-and-stability-strategy.md) WD2/WD3, [#96](https://github.com/rigortype/rigor/pull/96)).
  - Opt in with `bleeding_edge: true` (or `bleeding_edge: [reject-unparseable-signatures]`) in `.rigor.yml`, or `rigor check --bleeding-edge` for one run; `rigor show-bleedingedge` prints what your project adopts. It is off by default because rejecting an input Rigor previously accepted is a new discipline, and one that upgrading the `rbs` gem alone can trigger. It is the intended default at a future major.
- **[rigor check]** When your `signature_paths:` RBS conflicts with Rigor's bundled RBS and collapses the whole RBS environment, Rigor now reports it as a diagnostic naming the conflicting files, so a run that came back suspiciously empty is no longer mistaken for a clean one ([#183](https://github.com/rigortype/rigor/pull/183)).
  - It reaches `--format=json`, SARIF, and CI. It is a warning by default (the conflict is usually against Rigor's own signatures, so upgrading Rigor must not turn a green build red); opting into `reject-unparseable-signatures` promotes it to an error.
- **[rigor check]** A standalone `gem install rigortype` with no `rbs-inline` library now reports `rbs.coverage.inline-annotations-unsynthesized` (`:info`) when your project carries rbs-inline annotation comments that nothing can read, so an annotated project that silently stays untyped is no longer mistaken for a clean run ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md) WD3, [#192](https://github.com/rigortype/rigor/pull/192)).
  - It points at the fix (install the `rbs-inline` gem; Rigor keeps its core zero-dependency and does not bundle it) and stays silent for a project with no real annotations (RDoc directives like `#:nodoc:` never trigger it) or whenever the library is present.

  - A stale installed `rigortype` gem silently shadowing a newer checkout's bundled plugin copy is now visible at a glance instead of taking a bisection to pin down.

### Changed

- **[rigor check]** Inline rbs-inline annotations (`#: (Integer) -> void`, `# @rbs return: T`, attribute `#:`, …) now work out of the box: when the `rbs-inline` library is installed, Rigor loads the bundled `rigor-rbs-inline` plugin automatically, with no `plugins:` entry and no `# rbs_inline: enabled` magic comment ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md), [#192](https://github.com/rigortype/rigor/pull/192)).
  - Only the per-file `# rbs_inline: disabled` directive opts a file out. A project with no annotations is unaffected (verified byte-identical on mail / kramdown / haml / liquid). Turn the auto-wiring off by adding the plugin to `plugins:` with `enabled: false` (a new per-entry key); restore the old magic-comment gate with its `config: { require_magic_comment: true }`.
- **[engine]** RBS `void` now translates to `top` instead of `untyped`, so it is no longer looser than the toolchain Rigor reads ([ADR-92](docs/adr/92-normative-status-fidelity.md) WD2, [#112](https://github.com/rigortype/rigor/pull/112)).
  - RBS defines the two as the same top type, with `void` carrying only a hint that the value should not be used; mapping it to `untyped` let a caller silently build exactly the dependency the annotation forbids, while `top` demands proof. Diagnostics on real code are unchanged (byte-identical on mail / kramdown / haml / liquid / mastodon `app/models`) — the `static.*` family that makes `top` bite is not implemented yet, so this buys the correct representation now and the diagnostic when that family lands.
- **[engine]** Every Kernel module-function fold now runs behind a single dispatcher-held ownership gate, removing a hijack of user-defined conversion-named methods ([ADR-91](docs/adr/91-kernel-intrinsic-fold-ownership-gate.md), [#111](https://github.com/rigortype/rigor/pull/111)).
  - The "is this call really Kernel's?" check was per-fold and opt-in, which left the `Array()` / `Integer()` / `Float()` conversion folds with no guard at all — a user class defining its own `Integer` method had `conv.Integer("42")` silently folded to `42`. The gate now exists once in the dispatcher (name in a compiled intrinsic table, receiver implicit or `Kernel` itself, no user redefinition in scope). Diagnostics on real code are unchanged (four-corpus gate byte-identical).
- **[inference]** An instance variable assigned only through parallel assignment in a constructor (`def initialize; @m, @n = [], []; end`) now keeps its inferred type when read from another method, instead of being widened with a spurious `nil` that masked a real `call.undefined-method` on it ([ADR-58](docs/adr/58-ivar-field-typing.md), [#201](https://github.com/rigortype/rigor/pull/201)).
- **[cache]** `cache.validation` gained an `auto` mode — the new default — that hashes file content when a CI environment is detected (a fresh checkout regenerates the timestamps and inodes the faster stat check relies on) and keeps the stat check everywhere else ([#191](https://github.com/rigortype/rigor/pull/191)).
  - Set `cache.validation: stat` explicitly on a CI runner that reuses its workspace.
- **[cli]** `rigor doctor` no longer headlines "0 issue(s) found" on a run whose only findings are warnings; the summary counts warnings too.
- **[skills]** The bundled onboarding skills (`rigor-project-init`, `rigor-next-steps`, `rigor-editor-setup`) gained guidance for non-interactive / agent-driven runs and several accuracy fixes, from an autonomous run against a real Rails app ([#108](https://github.com/rigortype/rigor/pull/108)).

- **[perf]** `rigor check` and `rigor coverage` now enable YJIT once a run outlasts a short amortization deadline, cutting wall time on large projects with no penalty to quick runs ([#75](https://github.com/rigortype/rigor/pull/75)).
  - Enabling YJIT up front is a net loss on short runs (a ~4s run regressed ~20%), so Rigor arms a background thread that enables it only after 5s. Measured cold on Mastodon `app`+`lib`: 25.4s → 15.1s (1.7×), matching always-on YJIT; short-run cases stay at parity. The `rigor lsp` / `rigor mcp` servers enable YJIT at boot. Set `RIGOR_DISABLE_YJIT=1` to opt out, or `RIGOR_YJIT_DEADLINE=<seconds>` to tune.
- **[perf]** A parallel `rigor check` / `coverage` run (`--workers=N`) now enables YJIT inside its fork workers, not just the coordinator, so a worker forked before the deadline fires no longer runs its whole analysis slice un-JITted ([#99](https://github.com/rigortype/rigor/pull/99)).
  - `fork` copies only the calling thread, so the parent's deadline thread never reached the workers. Each worker now re-arms its own deferred YJIT under the same amortization contract. Diagnostics stay byte-identical (verified pooled-vs-sequential); `RIGOR_DISABLE_YJIT=1` still disables it everywhere.
- **[perf]** A warm `rigor check` HIT — the common "nothing changed, tell me it's still clean" run — is dramatically faster: it serves the cached diagnostics without loading the inference engine, its plugin gems, or the RBS environment, and validates cached file dependencies by stat instead of re-reading and re-hashing them ([ADR-87](docs/adr/87-null-build-floor.md), [#85](https://github.com/rigortype/rigor/pull/85)).
  - Two floors are removed: a warm hit no longer re-SHA-256's every cached dependency (~115 MB across ~52k files on GitLab `app/models`) and no longer boots the analyzer at all. Measured out-of-process: GitLab `app/models` warm hit **1.41s → 0.34s**, mail / rigor `lib` **~0.36s → ~0.22s**, warm `--incremental` zero-change **1.85s → 1.44s**. Diagnostics are byte-identical; `cache.validation: digest` restores the digest-every-file behaviour.
- **[perf]** A comment-only edit under `rigor check --incremental` now re-checks only the edited file instead of its whole ancestry / file-level dependent set ([#88](https://github.com/rigortype/rigor/pull/88)).
  - When a changed file's code (comments stripped) is byte-identical to the snapshot, every cross-file fact its dependents consume is unchanged, so they are served from cache. Measured on GitLab (1,774 files): an in-place comment edit that previously re-analysed 19 / 66 / **341** files now re-analyses **1**, dropping a base-class comment recheck from ~12.3s to ~7.9s. The gate disables itself when a comment-ingesting plugin (`rigor-rbs-inline`) is configured, and is backstopped by a fabricated-edit soundness battery.
- **[perf]** A `rigor check --incremental` recheck now re-analyzes a dependent only when the edit actually changed something the dependent can consume, extending the comment-only gate to body edits ([ADR-89](docs/adr/89-semantic-propagation-gates.md), [#90](https://github.com/rigortype/rigor/pull/90)).
  - A signature-preserving body edit (a local rename, an internal literal) no longer re-checks the edited class's dependents, and a return-preserving refactor of an eligible leaf method no longer re-checks its callers. Measured on GitLab: a return-preserving edit to `ApplicationRecord.safe_find_or_create_by` that previously re-analysed **341** files now re-analyses **1**. Any signature / arity / visibility / ancestry / mutation-effect change or a line shift still propagates. Diagnostics are byte-identical (cold and via `--verify-incremental`).
- **[perf]** A warm `rigor check --incremental` recheck now serves plugin `#prepare` producers from the persistent cache instead of recomputing them, cutting warm-incremental cost on plugin-heavy (Rails) projects several-fold ([ADR-85](docs/adr/85-seed-bundles-and-lazy-def-node-handles.md) WD1, [#81](https://github.com/rigortype/rigor/pull/81)).
  - The cross-process incremental session built each analyzer with no cache store, so every plugin's cached producer recomputed on every invocation. Measured on GitLab `app/models` (10 auto-loaded Rails plugins): a warm recheck drops from 16.7M to 2.8M allocations (~6×), plugin `#prepare` alone from 14.3M to 0.34M, byte-identical.
- **[perf]** A warm `rigor check --incremental` recheck no longer re-parses the whole project to rebuild its cross-file discovery index: it folds each file's cached per-file seed bundle from the snapshot, re-walking only the files whose content changed ([ADR-85](docs/adr/85-seed-bundles-and-lazy-def-node-handles.md) WD2/WD3, [#82](https://github.com/rigortype/rigor/pull/82)).
  - The whole-project index rebuild was 80–92% of a warm incremental on a plugin-light project. Def nodes are stored as `(path, node_id, name, fingerprint)` handles and a body is materialised only when demanded (0–6 files per recheck). Measured warm zero-change: rigor `lib` 540k → 149k allocations, mail `lib` 529k → 54k; on GitLab `app/models` the combined effect with the producer cache is 16.7M → 2.06M (~8×). Diagnostics are byte-identical; the snapshot schema is bumped (a one-time clean cold rebuild).
- **[perf]** `rigor check --incremental` change detection now stats unchanged files instead of SHA-256'ing them, re-hashing only a file whose `(size, mtime, ctime, inode)` tuple moved ([ADR-87](docs/adr/87-null-build-floor.md), [#85](https://github.com/rigortype/rigor/pull/85)).
  - The SHA-256 digest stays the sole change authority (a `touch` re-hashes once and stays fresh); `cache.validation: digest` / `RIGOR_STRICT_VALIDATION=1` restores digest-every-file. `--verify-incremental` stays byte-identical.
- **[perf]** A `def self.method` / singleton-method body edit under `--incremental` now gets the same symbol-granularity scoping an instance-method edit already had, limiting its recheck closure to that method's call sites ([ADR-46](docs/adr/46-incremental-dependency-graph.md), [#87](https://github.com/rigortype/rigor/pull/87)).
  - The change-detection fingerprint and recorded call-site edge now cover class / singleton / `module_function` methods (keyed `Class.method`, distinct from instance `Class#method`). Diagnostics are byte-identical; the snapshot schema is bumped.
- **[perf]** `rigor check --incremental` now honours the worker-count knobs the standard `check` path already respects (`--workers=N`, `RIGOR_RACTOR_WORKERS`, `.rigor.yml` `parallel.workers:`), so the closure re-analysis after an edit runs across a fork-worker pool ([ADR-46](docs/adr/46-incremental-dependency-graph.md), [#87](https://github.com/rigortype/rigor/pull/87)).
  - Each worker records its slice's cross-file edges and marshals them back, so the dependency graph a pooled recheck rebuilds is identical to the sequential one. The win is on large closures (a base-class edit touching hundreds of files); the default stays sequential (`workers: 0`).
- **[perf]** A zero-change `rigor check --incremental` recheck no longer rewrites its on-disk snapshot when it is byte-equivalent to what was just loaded, and does slightly less redundant work per edit (the changed set is parsed once, not twice) ([ADR-87](docs/adr/87-null-build-floor.md) WD3, [#77](https://github.com/rigortype/rigor/pull/77)).
- **[engine]** The [ADR-57](docs/adr/57-self-call-return-adoption.md) user-method return memo is now genuinely run-scoped, so a callee's inferred return is computed once per run instead of once per consumer file ([ADR-84](docs/adr/84-cross-file-return-memo-scoping.md), [#80](https://github.com/rigortype/rigor/pull/80)).
  - The memo previously keyed on a per-file table identity, so hits never crossed a file boundary (mail's `Mail::Part#has_content_type?` was re-evaluated 564 times). Keying on a per-run generation token cuts cold callee body evaluations 3,355 → 557 on mail `lib` and 9,977 → 7,339 on Rigor's own `lib`. Because a cross-file hit skips the callee body walk, dependency recording pairs every hit with cache-and-replay, so `--incremental` edges are identical to a memo-free run (pinned by property specs).
- **[perf]** The bundled plugins' hand-rolled AST walks no longer allocate a throwaway child-node array per node: 37 `.each` sites across 21 plugin / example files now call `#rigor_each_child` ([#98](https://github.com/rigortype/rigor/pull/98)).
  - Only the plain-iteration sites migrated; the handful needing an actual array keep `compact_child_nodes`. Diagnostics are byte-identical (verified on the Redmine corpus and every plugin integration spec).
- **[engine]** AST tree walks no longer allocate a throwaway array per node visited, cutting total allocations on every `rigor check` run — most sharply on leaf-heavy sources ([#76](https://github.com/rigortype/rigor/pull/76)).
  - `Prism::Node#compact_child_nodes` builds a fresh `Array` on every call; on a Ragel-generated parser (mail's `lib`) those arrays were over half of all allocations. Loading `Rigor::Source::NodeChildren` compiles a `#rigor_each_child` method onto each Prism node class that yields the same children without the array, and the engine's walkers call it in place of `compact_child_nodes.each`. Diagnostics are byte-identical.
- **[engine]** Warm cache runs no longer re-parse the whole project, and a cold run parses each project file once instead of twice: the cross-file discovery pre-pass is deferred out of the eager pass (run only on the analysis path) and its class-discovery and def-node passes now share a single walk ([#77](https://github.com/rigortype/rigor/pull/77)).
  - Diagnostics are byte-identical; the dependency-recording and subset (`--incremental`) modes still force the build eagerly.
- **[engine]** A warm cache run no longer SHA-256-hashes the whole RBS signature tree: the run-diagnostics cache key reads only the `rbs` gem version + library list, and the vendored signature-tree digests are computed solely on a cache miss ([#77](https://github.com/rigortype/rigor/pull/77)).
  - Combined with a per-run digest memo (each absolute path is hashed at most once per run), warm runs do markedly less filesystem digesting. The memo is process-local, reset per run, so it changes nothing about what a run observes.
- **[rigor-dry-types]** The dry-types alias scan is now cached across runs, so a warm `rigor check` re-validates file digests instead of re-parsing the whole project ([ADR-60](docs/adr/60-pre-freeze-plugin-contract-consolidation.md) WD3, [#74](https://github.com/rigortype/rigor/pull/74)).
  - The plugin's `#prepare` used to Prism-parse every `.rb` file under `paths:` on every invocation (roughly a third of GitLab `app/models` warm time). The scan now rides a cached producer with a `watch:` glob, recomputing only when a source file under those paths changes. `--no-cache` recomputes fresh.
- **[perf]** The opt-in `parameter_inference:` pre-pass is cheaper: it now skips typing the receiver of any call whose name no user-defined method declares (~73% of call sites in a Rails app), cutting the pre-pass cost on a cold `rigor check` with an inferred-parameter table that is byte-identical ([#203](https://github.com/rigortype/rigor/pull/203)).

### Removed

- **[cli]** **BREAKING** — the deprecated verb subcommands `rigor docs list` / `rigor docs path <name>` and `rigor skill list` / `print <name>` / `path <name>` are removed ([#94](https://github.com/rigortype/rigor/pull/94)).
  - **Migration:** `rigor docs list` → `rigor docs --list`, `rigor docs path <name>` → `rigor docs --path <name>`, `rigor skill list` → `rigor skill --list`, `rigor skill print <name>` → `rigor skill <name>`, `rigor skill path <name>` → `rigor skill --path <name>`. The positional slot of both commands is a doc / skill name, so a removed verb now resolves as an unknown name (exit 1) rather than shadowing a same-named page. `rigor skill describe` / `--describe` (and `rigor describe`) are unchanged.
- **[plugin]** **BREAKING** — the deprecated `type_specifier` plugin hook is removed, along with the internal reader and the capability key that carried its name ([ADR-80](docs/adr/80-narrowing-facts-rename.md), [#94](https://github.com/rigortype/rigor/pull/94)).
  - **Migration:** in a plugin class body, `type_specifier methods: […] do … end` → `narrowing_facts methods: […] do … end` (the alias warned throughout `0.2.x`; it now raises `NoMethodError` at class-definition time). The class-level reader `type_specifiers` is now `narrowing_facts_rules`, the instance method `#type_specifier_facts` is now `#narrowing_facts_for`, and the `rigor plugins --capabilities` JSON key `type_specifier_methods` is now `narrowing_facts_methods`.
- **[dev]** The `parallel_tests` development dependency is dropped, along with the `make test-parallel` target and the `rake spec_parallel` task it drove ([#94](https://github.com/rigortype/rigor/pull/94)).
  - `binpacker` has been the project's parallel spec runner since [#27](https://github.com/rigortype/rigor/pull/27) (`make test-binpacker`, what `make verify` and CI run), so the second runner was dead weight. No runtime dependency of the gem changes.

### Fixed

- **[plugins]** Bundled plugins now always load from the engine's own copy, so an older `rigortype` gem installed alongside a git checkout can no longer silently shadow the engine's plugin copy with a mismatched version and produce wrong diagnostics ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md) WD5, [#198](https://github.com/rigortype/rigor/pull/198)).
  - A `plugins:` entry naming a plugin Rigor ships — including the auto-wired `rigor-rbs-inline` — was required by gem name. Rigor now requires each bundled plugin by its path inside the engine, which is versioned together with it; a trimmed or single-binary install that ships no bundled copy falls back to gem-name resolution exactly as before.
- **[cli]** The type probes — `rigor type-of`, `type-scan`, `trace`, and `annotate` — now build the same plugin-aware environment `rigor check` analyses with, so a type synthesized from an inline rbs-inline annotation is reported instead of a plugin-free `Dynamic[top]`, and a probe no longer disagrees with the check it is meant to explain ([#196](https://github.com/rigortype/rigor/pull/196)).
  - A project with no plugins, or with broken plugin setup, degrades to the previous behaviour rather than failing.
- **[cli]** `rigor check` no longer crashes with `uninitialized constant Rigor::Analysis::Baseline` when a run-cache hit is served with a `baseline:` configured, so the second ordinary `check` after wiring a baseline — the exact next step of acknowledge-mode onboarding — no longer fails outright (the workaround was `--no-cache`) ([#107](https://github.com/rigortype/rigor/pull/107)).
  - The boot-slimmed cache-hit fast path skipped the lazy engine require bundle that carried the baseline filter's dependency. The baseline filter is now a load-time dependency of the check command (it pulls only YAML, never the engine), and the hit path stays engine-free.
- **[cli]** The `rigor baseline generate` hint for a config without `baseline:` now names the config file that actually governs the project (e.g. `.rigor.dist.yml`) instead of always saying `.rigor.yml` ([#107](https://github.com/rigortype/rigor/pull/107)).
- **[type inference]** A `str =~ RE` match where the pattern is a constant (`RE = /.../` or `Regexp.new(...)`) now narrows the match globals just like a literal `str =~ /.../`, so `$1`, `$~`, and the rest read as their matched types after a successful match — removing spurious possible-nil warnings on the "compile the regex once as a constant" idiom ([#181](https://github.com/rigortype/rigor/pull/181)).
- **[type inference]** `$+` (the last matched group) is no longer assumed non-nil after a successful match whose groups are all optional or absent (`"b" =~ /(a)?b/`); it narrows to `String` only when at least one capture group is guaranteed to participate ([#181](https://github.com/rigortype/rigor/pull/181)).
- **[type inference]** A method whose RBS declares an untyped parameter list — `def call: (?) -> String` — now contributes its return type instead of silently reading as untyped ([#175](https://github.com/rigortype/rigor/pull/175)).
  - Rigor discarded the whole signature for these methods, which affected stock projects with no `sig/` of their own: core RBS ships the form on `Proc#call`, `Method#call`, `Ractor.select`, and `IO.for_fd`. `(?)` still constrains nothing about arity or argument types, so you will not see new argument diagnostics; where such a method is one arm of an overload set, a genuinely typed arm still wins.
- **[engine]** Emptying an array no longer leaves Rigor believing it is still non-empty, which produced a false "condition is always falsey" on a correct emptiness check ([#179](https://github.com/rigortype/rigor/pull/179)).
  - After a `return if arr.empty?` guard Rigor knows `arr` is non-empty, but it kept that across `arr.clear` / `pop` / `shift` / `delete_if`, so a later `arr.size == 0` was reported as impossible. Mutating the array now retracts the non-emptiness. The same fix covers instance variables (`@items.clear`) and arrays emptied inside a block.
- **[engine]** Reading a file or IO line by line (`each_line`, `File.foreach`, and friends) no longer trips a false `flow.always-falsey-condition` on a later check, now that the line-iteration block is classified as non-escaping ([#193](https://github.com/rigortype/rigor/pull/193)).
- **[rigor annotate]** `rigor annotate` no longer emits spurious inline annotations on the interior lines of a multi-line literal ([#103](https://github.com/rigortype/rigor/pull/103)).
- **[engine]** An inline-RBS contribution that declares a constant the project's own `sig/` also declares no longer collapses the entire RBS environment ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md), [#113](https://github.com/rigortype/rigor/pull/113)).
  - `RBS::Environment#add_source` appends the source before inserting declarations, so a mid-insert `DuplicatedDeclarationError` left a poisoned source behind — measured on herb (which ships both `sig/` and rbs-inline comments): 1,490 classes → 0, `require` stopped resolving, 74 false `call.unresolved-toplevel`. The skip is now transactional, the explicit `.rbs` declaration wins, and the dropped files are reported loudly.
- **[rigor init]** Fixed the generated config's editor-schema link, which pointed at a URL that did not exist — so every project started with `rigor init` had no schema validation at all: no autocomplete, no hover docs, no structural checking ([#170](https://github.com/rigortype/rigor/pull/170)).
  - An unreachable schema looks exactly like a schema with no complaints, which is why this went unnoticed. If you ran `rigor init` before this release, re-run it or repoint the `# yaml-language-server: $schema=…` line at [the schema](schemas/rigor-config.schema.json). The generated file now links the [configuration manual](docs/manual/03-configuration.md) instead of an internal contributor document.
- **[config]** `cache.max_bytes` and `cache.validation` are no longer rejected by the [JSON schema](schemas/rigor-config.schema.json), which told editors these documented, working keys were invalid ([ADR-99](docs/adr/99-config-schema-authority.md), [#170](https://github.com/rigortype/rigor/pull/170)).
  - The schema is now a named source of truth for `.rigor.yml` alongside the loader, and a `rigor_rs:` namespace is reserved for the sibling Rust implementation so one config file can serve both. Rigor never reads that namespace and never errors on its contents.
- **[plugins]** `rigor-rbs-inline`'s magic-comment-free mode no longer degrades an unannotated project by synthesizing an `untyped` skeleton for every def ([ADR-93](docs/adr/93-default-rbs-inline-ingestion.md) WD1, [#113](https://github.com/rigortype/rigor/pull/113)).
  - The mode mapped straight onto upstream rbs-inline's opt-out mode; since Rigor trusts an accepted signature over body inference, those skeletons replaced real inferred types (mail: 26 → 42 diagnostics). It now contributes only for a file that actually carries an annotation, detected with upstream's own `AnnotationParser` and filtered for RDoc directives. Annotation-free corpora (mail / kramdown / haml / liquid) are byte-identical under the mode.
- **[plugins]** `rigor-rbs-inline` no longer loses a class's inline annotations to a sibling `#:nodoc:`, which upstream reads as a `-> nodoc` return type that makes `RBS::DefinitionBuilder` raise `NoTypeFoundError` for the whole class ([#113](https://github.com/rigortype/rigor/pull/113)).
  - The plugin rewrites each RDoc directive to its spaced spelling (`# :nodoc:`, which upstream ignores) before synthesis, covering all 17 directives the Ruby docs list. Reported upstream as [soutaro/rbs-inline#248](https://github.com/soutaro/rbs-inline/issues/248).
- **[docs]** The plugin documentation no longer tells you to add `gem "rigor-rails"` to your `Gemfile` — an impossible action, in five places including the shipped [plugin chapter](docs/manual/07-plugins.md) ([ADR-96](docs/adr/96-plugin-target-gems.md) WD5, [#118](https://github.com/rigortype/rigor/pull/118)).
  - There is no `rigor-rails` gem, and `plugins: [rigor-rails]` is rejected by the loader; the meta-gem is now described as what it is (unwired, no supported use) and kept deliberately rather than removed. Also corrected: `Plugin::Loader`'s worked example used a nonexistent `{gem: "rigor-rails", id: "rails"}`.
- **[plugin]** A standalone install (`gem install rigortype`, no shared gem environment with the app) no longer silently loses every inflection-dependent Rails check ([ADR-90](docs/adr/90-target-library-resolution-from-project-bundle.md), [#109](https://github.com/rigortype/rigor/pull/109)).
  - The bundled Rails plugins inflect through the real `ActiveSupport::Inflector`, but rigortype carries no activesupport runtime dependency, so `rigor-activerecord` / `rigor-rails-routes` / `rigor-actionpack` / `rigor-actionmailer` / `rigor-factorybot` degraded to producing no diagnostics. A target library that fails to require is now retried against the analyzed project's own bundler install tree (its locked activesupport is the higher-fidelity source anyway); a project whose bundle is not installed still degrades cleanly.
- **[plugin]** The plugin isolation worker no longer dies with an opaque `Inflector::Unavailable: process isolation worker failed (EOFError)` when a target library cannot be loaded ([#109](https://github.com/rigortype/rigor/pull/109)).
  - `Rigor::Plugin::LoadError` lexically shadowed the global `LoadError`, so the worker loop's bare `rescue` matched the wrong class and the real `::LoadError` killed the forked worker; the rescues are now `::`-qualified. The same shadowing bug is fixed in `rigor-rspec-rails`'s Rack status-table loader.
