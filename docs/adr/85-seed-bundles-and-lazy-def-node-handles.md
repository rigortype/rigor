# ADR-85 — Per-file seed bundles and lazy def-node handles (pre-pass incrementalization)

Status: **Accepted — WD1 (incremental plugin-prepare cache threading) landed in [PR #81](https://github.com/rigortype/rigor/pull/81); WD2/WD3 (seed bundles + lazy handles) implemented in [PR #82](https://github.com/rigortype/rigor/pull/82); WD5 (the recorded def nesting carried on the handle) in [#707](https://github.com/rigortype/rigor/issues/707).** Completes the warm/incremental arc [PR #77](https://github.com/rigortype/rigor/pull/77) opened: a cache HIT already skips the discovery pre-pass; this ADR removes it from the MISS path — an `--incremental` recheck re-derives cross-file discovery from cached per-file bundles and parses only the files whose def bodies are actually demanded.

Grounding: [`20260714-p6-seed-cache-recon.md`](../notes/20260714-p6-seed-cache-recon.md) (the measurement basis: cost split, ADR-54 test, demand statistics, merge-semantics audit) + [`20260713-corpus-perf-campaign.md`](../notes/20260713-corpus-perf-campaign.md) (the arc's origin).

## Context

Post-#77, `ProjectPrePasses#discover` runs only on a cache miss — but every `--incremental` recheck IS a miss-path run: it parses + walks every project file to rebuild the cross-file discovery index before re-analyzing its 1-file subset. The recon measured (master with #74–#80):

- Warm single-edit / zero-change incremental on plugin-light projects is **80–92% pre-pass** (rigor lib 0.54M allocs, mail 0.53M) — the slice's audience.
- Marshal.load + fold of per-file bundles beats parse + walk by **36× wall / 10× allocs** (rigor) to **570× / 44×** (mail) — the ADR-54 "beats recomputation" bar is cleared decisively (the retired definitions blob lost this same test at 366ms vs 137ms; this tier wins it).
- Def-node demand is tiny on the incremental path: a 1–20-file recheck resolves the bodies of **0–6 distinct files** (full cold runs: 39–66%) — so def nodes must NOT be eagerly materialized from cache.
- **Rails apps are gated elsewhere**: gitlab's warm incremental spends **86% (14.2M allocs) re-running plugin `#prepare` per recheck** — the recheck path constructs a fresh runner without the producer-cache wiring (`IncrementalSession#build_runner` hardcoded `cache_store: nil`), so even the #74-cached scans recompute. Fixing that (WD1) is what makes this slice matter on Rails at all.
- Merge semantics: per-file contributions are isolable and file-order mergeable, but NOT delta-replaceable (`includes`/`class_sources` are Set-unions; `def_nodes`/`superclasses`/`methods` later-wins; `finalize_def_index` is a whole-project post-pass) — the sound reconstruction is rebuild-from-bundles-in-file-order, then finalize once. Cross-file duplicate `(class, method)` pairs measured zero on all three corpora, so later-wins order-dependence is theoretical but preserved anyway.
- Prism `node_id` is stable across repeated and fresh parses of identical bytes (0 mismatches) and non-nil for every DefNode.

## Decision

Cache each file's pre-pass contribution as a **plain-data bundle keyed by the file's digest**, hosted on the ADR-46 `IncrementalSnapshot`; on a miss run with a valid snapshot, rebuild the discovery index by folding bundles in file order (re-walking only changed files) instead of parsing + walking the project. Def-node tables store **handles** resolved lazily at the accessor choke points through a per-run parse memo that yields **one stable node object per `(path, node_id)` per run** — the ADR-84 return memo keys on def-node identity, so identity stability is a correctness constraint, not a nicety.

Criterion (the ADR-54 rule, re-applied and kept binding): **this tier exists only while load-and-fold measurably beats recompute on real corpora, and def-node materialization follows demand** — an eager variant that Marshal-dumps ASTs (dragging each file's source text) forfeits the parse-allocation win that is most of the tier's value and is rejected on the same criterion.

## Working decisions

- **WD1 — incremental rechecks reuse the plugin-producer caches (sequencing-critical, landed first).** Root cause confirmed: `IncrementalSession#build_runner` built every internal analyzer with `cache_store: nil`, so plugin `cache_for` (`Plugin::Base`) saw no store and bypassed the disk cache, recomputing each producer per cross-process recheck. Fix: thread a `Cache::Store` through the session (honoring `--no-cache`). The whole-run ADR-45 result cache is **incompatible** with these runs — a cache-served `record_dependencies` run captures no dependency graph, and an `analyze_only` subset run's partial diagnostics share the full run's result key — so `Runner#run_result_cacheable?` now excludes `record_dependencies` / `analyze_only`. Measured gitlab `app/models` warm-incremental **16.7M → 2.8M allocs (~6×)**, plugin `#prepare` alone **14.3M → 0.34M**; byte-identical diagnostics; the store is threaded into `--verify-incremental` too, so the gate asserts the cache-served path matches the uncached full run.
- **WD2 — bundles on `IncrementalSnapshot`.** Extend `Payload` with `seed_bundles` (SCHEMA 5→6; the #57 ABI marker + fingerprint gate cover invalidation for free — a pre-6 blob loads as nil, a clean cold rebuild). A bundle stores one file's pre-finalize contribution as plain data — including the pre-`subtract_def_methods` `methods` table and the `classes` table (Singleton values, Marshal-clean) — with def-node tables re-expressed as handles; `finalize_def_index` runs once after the fold. One fs read serves the whole rebuild (a per-file `Cache::Store` producer family would be ~N fs-ops on an 11k-file project — the anti-pattern ADR-54 retired). `ScopeIndexer.discovered_project_index_incremental` folds each file's bundle (digest-validated) or re-walks changed files, in canonical order; a **re-walked file (and the whole cold baseline, where `seed_bundles` is empty) keeps LIVE `Prism::DefNode`s** in the index — no on-demand re-parse for a file just walked — so only *unchanged* files carry handles (a mixed table). The cold-baseline index is therefore byte-identical to today's `discovered_project_index_for_paths`.
- **WD3 — lazy def-node handles.** A handle is `DefHandle(path, node_id, name, fingerprint, nesting)` (`nesting` added by WD5). Three sites deref node values (`Scope#user_def_for`, `#singleton_def_for`, `#top_level_def_for`); they resolve a handle via `DefNodeResolver` (a per-run parse memo) and hand callers a real `DefNode` (accessor contract unchanged; dependency recording keys on the table's PRESENCE, so it stays sound whether or not resolution succeeds). Resolution is memoized per `(path, node_id)` — **one identity per run** (this also reduces the ADR-84 cross-file identity bound to 1). `node_id` is primary with `name` as a resolution cross-check; a miss (a skew digest validation should make impossible) falls back to the first same-named DefNode in a fresh walk, then nil — conservative, never silent. **A fourth value-deref consumer the recon's Q6 audit missed** — `Runner#symbol_fingerprints` (ADR-46 slice 4) slices every def-node — is why the handle carries `fingerprint` (the SHA of the def's slice, captured at bundle-build time): symbol_fingerprints reads it off the handle without re-parsing. All other consumers read table structure (keys / object-identity) and are unaffected — pinned by the byte-identity gate and a spec that a handle-bearing table serves them unchanged.
- **WD4 — the fold replaces, never patches.** No delta-replacement of a changed file's contribution inside merged tables (unsound per the Set-union/later-wins audit); a changed file re-walks and the index rebuilds from bundles in file order. Rebuild-from-bundles is itself the fast path — the fold measured 5–8ms / 25–61k allocs against 436–485k recompute.
- **WD5 — a fact keyed by node identity must travel ON the handle ([#707](https://github.com/rigortype/rigor/issues/707)).** [#681](https://github.com/rigortype/rigor/issues/681) records each `def`'s `Module.nesting` in a discovery table keyed by `Prism::DefNode` **identity**, and WD3's resolver hands back a node from its own parse — so no table the discovery walk keyed can ever contain it, and an unchanged file's callee silently kept the pre-#681 peel of the receiver's qualified name. That is a genuine cold/warm divergence rather than a precision gap: a compact `class Admin::Maker` and the nested spelling render the same `class_name`, so the peel reached `Admin::Post` where the source names `::Post`, and `--verify-incremental` — whose entire job is comparing the two — flipped from OK to FAILED on a project the user had not changed. Fix: the chain rides the bundle row (`[node_id, name, fingerprint, nesting]`, SCHEMA 13→14) and `DefNodeResolver` re-attaches it to the node it mints, read back through the single reader `ExpressionTyper#recorded_def_nesting`. **The rehydration memo is not a rival source for the fact** — the argument [#685](https://github.com/rigortype/rigor/issues/685) used to make `Reflection.lexical_nesting_chain` the single owner still holds, on OBJECT PROVENANCE: the resolver runs its own `Prism.parse` and both tables are `compare_by_identity`, so a node it mints is never the object one of the analyzer's own walks produced, and no node is a key in both; where the two answer for the same def through different objects they agree, because a bundle is reused only when the file's content SHA-256 matches and the chain is a pure function of that file's AST. **The file-level version of that argument is false and was asserted here before it was measured:** an unchanged file re-analysed as a DEPENDENT is bundle-served in the cross-file fold and walked live by `ScopeIndexer#merge_def_node_tables` for its own per-file index, contributing to both tables in one `Runner#run`. A future change must therefore preserve the separate parse, not a file-level split. The rehydration is populated only inside `DefNodeResolver.with_run`; every entry point that consumes a handle runs inside one, and a spec pins that rather than leaving it to inspection. The SCHEMA bump is load-bearing rather than hygienic: a three-element row destructures with `nesting` nil, which is indistinguishable from the top-level `def` that legitimately records none, so a pre-14 blob had to be REJECTED and not read. (Since [#716](https://github.com/rigortype/rigor/issues/716) a top-level `def` records its empty chain instead of none, which changed what an existing row MEANS without changing its shape and bumped the schema again for the same reason — the rule below is what made that a one-line change.) **The general rule this instance teaches: a bundle serialises a table's VALUES, so any fact the live index keys by node identity is lost unless it is moved onto the row — adding one is a WD3 change, not a caller-side one.**

## Divergences from the recon (found while implementing)

- The recon's Q3 said the `classes` table could be stored **as a key-list** (values reconstructable as `Singleton[name]`). This is false for a `Const = Class.new(Super)` constant, whose value is `Singleton[Super]`. Bundles store the full `{name => Singleton}` table (Marshal-clean). One residual: cross-*file* `Class.new` superclass resolution (rare) is captured file-locally in a bundle rather than against the whole accumulated set; the `--verify-incremental` + cold-byte-identity gates backstop it (all green on mail / kramdown / mastodon / redmine / rigor lib).
- The recon's Q6 named the 3 accessors as the ONLY node-value consumers; `Runner#symbol_fingerprints` is a fourth. WD3's handle carries `fingerprint` to serve it (above).
- `IncrementalSession` gained a `plugin_requirer:` hook (mirroring `Runner`) so the WD1 cache-reuse spec can register a producer-bearing test plugin — the session was the one runner-builder that could not inject a requirer.

## Rejected alternatives

- **Eager def-node Marshal** (cache the ASTs): each dump drags the file's whole source, load-side allocations forfeit the tier's dominant win, and full-cold demand (39–66% of files) is the only case it helps — the incremental path (0–6 files) is the audience. Criterion kills it.
- **Delta-replacement merge**: unsound (Set-union + later-wins + whole-project finalize).
- **Per-file `Cache::Store` producers**: N fs-ops per rebuild; the access pattern needs all bundles at once — one snapshot read is the correct shape.
- **Skipping WD1 and shipping bundles alone**: on Rails corpora the slice would be a measured ~5% while 86% sits in uncached prepare — sequencing WD1 first is what makes the arc honest.

## Consequences

- Positive: plugin-light warm incremental loses its 80–92% pre-pass floor (rigor lib zero-change 540k → 149k allocs, mail 529k → 54k; pre-pass 436k → 25k / 485k → 5k); Rails incremental loses the 86% prepare re-run (WD1) and then the pre-pass on top (gitlab 16.7M → 2.06M combined, ~8×); `--verify-incremental` keeps byte-identity as the standing gate; the ADR-84 memo's identity bound tightens.
- Negative: a new snapshot section to version (SCHEMA discipline); the handle indirection adds one memoized lookup at three accessors; the cold `--incremental` baseline pays a small extra (building bundles + fingerprints), a one-time cost on a non-gated path; bundle staleness is impossible-by-construction only while the digest gate stays sound.
- Carry-over: plain (non-`--incremental`) cold runs keep today's parse+walk untouched (they never set `collect_seed_bundles:`); bundles could serve a general cached MISS too, but that path's win is small (Q8) — measure before extending.
