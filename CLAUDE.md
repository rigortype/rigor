| [`docs/adr/32-rbs-inline-comment-ingestion.md`](docs/adr/32-rbs-inline-comment-ingestion.md) | Proposed (2026-05-25) — close the gap that today makes a Ruby file's `# @rbs name: :asc \| :desc`-shaped inline-RBS comment invisible to Rigor (so a mismatched-symbol call is not flagged and the parameter types `Dynamic[Top]`). Decision: ship a bundled **`rigor-rbs-inline`** plugin that calls the upstream [rbs-inline](https://github.com/soutaro/rbs-inline) library at env-build time and contributes the synthesised RBS to the analysis environment, gated by the upstream `# rbs_inline: enabled` magic comment. Adds an optional `Plugin::Manifest` field **`source_rbs_synthesizer:`** — a `(source_file_path) -> rbs_source_string \| nil` callable — distinct from ADR-25's static bundled `signature_paths:` because the contribution is synthesised from project source at env build, not shipped inside the plugin gem. Ten working decisions: **WD1 a plugin, not a core feature** (rejected adding `rbs-inline` to the `rigortype` runtime-dep list; ADR-0 zero-runtime-dep stance binds, the plugin gem carries the dep; also rejected a Rigor-side re-implementation of the rbs-inline grammar — broad and still-evolving upstream, drift is the larger long-term cost), **WD2 honor the upstream `# rbs_inline: enabled` magic comment** (spec alignment; mix inline-RBS files and plain Ruby files freely; rejected always-on-once-loaded and a Rigor-only opt-in comment), **WD3 use the upstream library** (handles the entire grammar — `#: () -> T`, `# @rbs () -> T`, doc-style per-param, `# @rbs return:`, attributes, ivars, constants, generics, `# @rbs override`, block-as-method, `# @rbs!` raw embedding; subset filtering deferred), **WD4 a new `source_rbs_synthesizer:` manifest field** (distinct from ADR-25 `signature_paths:`; one source path in, one RBS string out — parallelisable per ADR-15, generalises to other Ruby-source-to-RBS bridges; rejected emit-to-temp-dir-and-reuse-ADR-25 because cache invalidation would key off disk I/O), **WD5 per-file synthesis** (synthesised RBS for `F` is a function of `F`'s content alone; ADR-6 per-file cache extends to `(path, sha, plugin id, plugin version, require_magic_comment value)`; non-annotated files incur only a top-of-file magic-comment check), **WD6 fail-soft on synthesis errors** (rbs-inline parse error → `source-rbs-synthesis-failed` info diagnostic + plugin returns `nil`; loud, bounded blast radius, ADR-25 conflict-handling shape), **WD7 inline-RBS parameter types are honored identically to real `.rbs`** (the synthesised RBS routes through `RbsLoader` → env → `MethodParameterBinder` exactly as a hand-written `.rbs` does; verified `argument type mismatch` already fires for the class-wrapped variant of the user's diagnostic example), **WD8 additive to the pre-1.0 plugin contract** (a new optional field; no existing plugin breaks), **WD9 top-level `def` semantics depend on upstream behaviour** — upstream rbs-inline's wiki documents `def` inside `class` / `module`; top-level `def` is to-be-verified in slice 1, with a class-wrapped workaround already known to produce the expected diagnostics, **WD10 host-context override via a `require_magic_comment:` plugin-config knob (default `true`)** — the [ADR-29](docs/adr/29-browser-playground.md) browser playground sets it to `false` so any pasted snippet with `# @rbs`-shaped comments is analysed without the user typing `# rbs_inline: enabled`; the escape hatch is per-plugin-instance (not a Rigor-wide policy change), reuses the existing plugin-config surface on `.rigor.yml`'s `plugins:` entry, and obsoletes the previously deferred "workspace-wide activation" carry-over (any project can now set it in `.rigor.yml`; the CLI-side `--treat-all-as-inline-rbs` flag remains the only un-implemented ergonomic). Three implementation slices (manifest field + engine hook + plugin skeleton + `require_magic_comment:` config → failure handling + per-file cache → plugin polish + docs); no slice scheduled by this ADR. Closes the "the `# @rbs` comment in my `.rb` looks like it should just work" UX gap. |

### Evaluating skills with `waza`

`waza` is an Agent-Skill evaluation CLI bundled in the Flake (`waza --help`; subcommands include `check`, `quality`, `dev`). Run `waza check <skill-path>` **once after authoring a new SKILL.md** as a minimal sanity check — it validates agentskills.io spec compliance (frontmatter structure, required fields, name / directory match).

Treat everything else `waza` reports as **informational, not binding**. These SKILLs are internal contributor workflows, not marketplace submissions, so `waza`'s token-budget soft limit (500 tokens), module-count advisory, "comprehensive"-complexity penalty, and `USE FOR:` / `DO NOT USE FOR:` / `**UTILITY SKILL**` routing markers — all calibrated for agentskills.io publication — do not apply. Comprehensive single-file procedural skills are the intended shape here.

Do **not** run `waza dev --auto` on these skills. It raises the compliance score by injecting `USE FOR:` / `**UTILITY SKILL** INVOKES:` boilerplate that is frequently false (e.g. listing H2 headings as trigger phrases, or claiming a procedural skill "invokes built-in analysis tools") — the score rises while the frontmatter degrades. The YAML `name:` + `description:` pair is the binding surface; keep it accurate and hand-written.

## Commit message style (mirrors AGENTS.md)

- Plain imperative subject in sentence case. No Conventional-Commits-style `type:` or `area:` prefixes.
- Subject is self-contained and reasonably short; detail belongs in the body.
- Wrap the body at ~72 columns; explain the why, not the diff.
- Release version bumps follow the fixed form `Bump up version to x.y.z`.

## Verification protocol (mirrors AGENTS.md)

After non-trivial changes, run:

```sh
nix --extra-experimental-features 'nix-command flakes' develop --command make verify
nix --extra-experimental-features 'nix-command flakes' develop --command git diff --check
```

`make verify` chains `make test`, `make lint`, and `make check`. The last target (`bundle exec exe/rigor check lib`) is the project's own self-check — it MUST stay clean. False positives there indicate either an engine regression or a missing per-class blocklist entry; fix the cause rather than disabling the rule.

If the Flake shell is unavailable, mention any skipped verification in the final report.

## Notes for delegated agents

- Do NOT bypass the Flake. `bundle`, `rake`, `rspec`, `rubocop`, and `exe/rigor` MUST run inside `nix … develop` per AGENTS.md.
- Do NOT modify `references/` submodules unless the task is "bump references/<name>". The vendored sources are read-only; engine changes happen against Rigor's own code.
- Do NOT run `bundle exec rake release` without explicit user authorisation. The release task tags `vx.y.z`, pushes to origin, and publishes to RubyGems.
- Prefer `rigor sig-gen` (ADR-14) over AI-authored RBS in this repo — the project's aspiration is for deterministic inference to be precise enough that AI suggestions are unnecessary, so gaps in sig-gen are the more valuable signal than freehand RBS. Full policy + the sig-gen output rule (do not overwrite `tighter-return` candidates that lose union members) live in [`AGENTS.md`](AGENTS.md) § "RBS Authorship".
- The reading order for a returning implementer is in [`docs/CURRENT_WORK.md`](docs/CURRENT_WORK.md). It points back at the relevant ADRs and skills for the version in progress; treat it as the resume bookmark, not as a normative spec.
