## [Unreleased]

### Fixed

- **[plugins]** `rigor-rbs-inline`'s magic-comment-free mode (`require_magic_comment: false`, used by the browser playground and `--treat-all-as-inline-rbs`) no longer degrades an unannotated project. It mapped straight onto upstream rbs-inline's opt-out mode, which synthesizes a full `def f: (untyped x) -> untyped` skeleton for **every unannotated def** — and since Rigor trusts an accepted signature over body inference, those skeletons replaced real inferred types with `untyped`. Measured on mail (zero annotations): 26 → 42 diagnostics, i.e. the mode fought the analysis on exactly the projects that write no annotations. The mode now contributes only for a file that actually carries an annotation, detected with upstream's own `AnnotationParser` rather than a regexp (the grammar stays upstream's, per [ADR-32](docs/adr/32-rbs-inline-comment-ingestion.md) WD3) and filtered for RDoc directives — upstream reads `class Foo #:nodoc:` as a type assertion of an alias named `nodoc`, which alone opted in 61 of mail's files. Annotation-free corpora (mail / kramdown / haml / liquid) are now byte-identical under the mode; an annotated project keeps its gains. The default mode (`require_magic_comment: true`) is unchanged. Found by [ADR-93](docs/adr/93-default-rbs-inline-ingestion.md)'s WD4 measurement.

- **[plugins]** `rigor-rbs-inline` no longer loses a class's inline annotations to a sibling `#:nodoc:`. Upstream reads an RDoc directive in a trailing position as the *type* — `def f #:nodoc:` becomes `def f: (untyped x) -> nodoc` — and `nodoc` resolves to nothing, so `RBS::DefinitionBuilder` raises `NoTypeFoundError` for the whole class and every real annotation in it is dropped without a warning. rbs-inline emits 29 of these for Ruby's own `lib/fileutils.rb`. The plugin now rewrites each directive to its spaced spelling (`# :nodoc:`, which upstream ignores) before synthesis, matching on shape so all 17 directives the [Ruby docs](https://docs.ruby-lang.org/ja/latest/library/rdoc.html) list are covered with no name list to maintain. Reported upstream as [soutaro/rbs-inline#248](https://github.com/soutaro/rbs-inline/issues/248).

- **[engine]** An inline-RBS contribution (`rigor-rbs-inline`) that declares a constant the project's own `sig/` also declares no longer collapses the entire RBS environment. `RBS::Environment#add_source` appends the source before inserting declarations, so the mid-insert `DuplicatedDeclarationError` left a poisoned source behind and `resolve_type_names` re-raised it outside every rescue — measured on herb (which ships both `sig/` and rbs-inline comments): 1,490 classes → 0, `require` itself stopped resolving, and 74 false `call.unresolved-toplevel` appeared. Overlap between `sig/` and inline annotations is the expected state for a migrating project. The skip is now transactional (the poisoned source is dropped), the explicit `.rbs` declaration wins, a resolve-time backstop covers the supported rbs `>= 3.0, < 5.0` range where detection timing may differ, and the dropped files are reported loudly — a once-per-run banner plus the cache-hit-safe `virtual_rbs_collision_quarantined` accessor. Found by [ADR-93](docs/adr/93-default-rbs-inline-ingestion.md)'s first WD4 measurement.

- **[cli]** `rigor check` no longer crashes with `uninitialized constant Rigor::Analysis::Baseline` when a run-cache **hit** is served with a `baseline:` configured. The boot-slimmed cache-hit fast path skipped the lazy engine require bundle that carried the baseline filter's own dependency, so the *second* ordinary `check` after wiring a baseline — the exact next step of every acknowledge-mode onboarding — failed outright (workaround was `--no-cache`). The baseline filter is now a load-time dependency of the check command (it pulls only YAML, never the engine), and the hit path stays engine-free.
- **[cli]** The `rigor baseline generate` hint for a config without `baseline:` now names the config file that actually governs the project (e.g. `.rigor.dist.yml`) instead of always saying `.rigor.yml`.

### Changed

- **[engine]** RBS `void` now translates to `top` instead of `untyped` ([ADR-92](docs/adr/92-normative-status-fidelity.md) WD2). RBS defines the two as the same type — *"They are all equivalent for the type system; they are all top type"* — with `void` carrying only a hint that the value should not be used, so mapping it to `untyped` made Rigor **looser than the toolchain it reads**. That looseness defeated the annotation's purpose: an author writing `#: void` is declaring "do not rely on this return", and `Dynamic[top]` is consistent with everything at a gradual boundary, so a caller could silently build exactly the dependency the annotation forbids. `top` demands proof instead. Diagnostics on real code are unchanged (byte-identical on mail / kramdown / haml / liquid / mastodon `app/models`) — precisely because the `static.*` family that would make `top` bite is not implemented yet; this buys the correct representation now and the diagnostic when that family lands. `special-types.md` § `void`'s distinct-`void` intent (a dedicated carrier, a "use of void value" diagnostic, generic-slot preservation) remains unimplemented and is marked as such in the spec.

- **[engine]** Every Kernel module-function fold now runs behind a single dispatcher-held ownership gate ([ADR-91](docs/adr/91-kernel-intrinsic-fold-ownership-gate.md)). Previously the "is this call really Kernel's?" check was per-fold and opt-in, which produced the `Kernel.p`-declines-while-`Kernel.format`-folds asymmetry fixed by hand earlier in this cycle, and left the `Array()` / `Integer()` / `Float()` / `Rational()` / `Complex()` conversion folds with no guard at all — a user class defining its own `Integer` method had `conv.Integer("42")` silently folded to the constant `42`. The gate now exists once in the dispatcher (method name in a compiled intrinsic table, receiver implicit or the `Kernel` module itself, no user redefinition in scope), the `format` / `sprintf` fold moved into the same tier as the rest of the family, and a table-driven parity spec pins that the implicit-self and explicit-`Kernel.` spellings infer identical types for every intrinsic. Diagnostics on real code are unchanged (four-corpus gate byte-identical); the only behavior change is the removed hijack of user-defined conversion-named methods.

- **[skills]** Onboarding-scenario feedback pass over the bundled skills, from an autonomous (non-interactive, acknowledge-mode) run of `rigor-next-steps` → `rigor-project-init` against a real Rails app. `rigor-project-init` and `rigor-next-steps` gain a *non-interactive / agent-driven runs* section (a pre-declared adoption mode settles the Phase 2 question; low-risk confirmations are covered by the delegation; committing never is; human-only verification steps are handoffs, not stalls). `severity_profile` documentation now says what the key actually does — profiles can gate whether a rule fires at all, not just re-stamp severities — and the Phase 4 profile choice is explicitly provisional until Phase 6's measured counts land. New guidance covers analysis-time plugin health (`rigor plugins` `[OK]` does not prove a plugin's capabilities survive analysis; check the stream for `plugin.<id>.load-error` before baselining it away), the UTF-8/`.scrub` JSON-parsing note at the primary `rigor triage --format json` step, conditioning `rigor-rspec` on `paths:` actually covering `spec/`, and the `rbs_collection.lock.yaml` side effect in the final file inventory. `rigor-editor-setup` now warns up front that VS Code has no first-party extension (its path is an extension-authoring task, unlike the Neovim/Helix/Emacs snippets) and that Phase 4 verification needs a human in the editor.

### Added


- **[cli]** `rigor doctor` now reports Rigor itself resolving as one of the project's dependencies ([ADR-27](docs/adr/27-tool-distribution-model.md), [ADR-77](docs/adr/77-doctor-and-upgrade-commands.md) WD1). The gem's own guardrails only fire while installing and at boot, so a project that already put `rigortype` in its `Gemfile` never sees them again — this names the state, with the fix and the pinning alternatives. The check reads `Gemfile.lock` the way the Rails-plugin check already does: no new analysis, no new rule. **Only a `rigortype` resolved from a `GEM` remote counts** — a `PATH` or `GIT` source means Rigor is being developed or vendored deliberately, and Rigor's own repository (and every fork) resolves `rigortype` under `PATH` via the `gemspec` directive, so matching the gem name alone would fail `rigor doctor` on Rigor itself. A dependency line nested under another gem, and a `CHECKSUMS` entry, are likewise not resolutions.
- **[docs]** The installation chapter gained a **Keeping Rigor up to date** section, and corrected what it says about sharing a version — the two claims turn out to be the same bug. `mise use ruby@4.0` preserves the precision you asked for and records `ruby = "4.0"`, but `mise use gem:rigortype` has no requested version to preserve and records `"gem:rigortype" = "latest"`, which each machine re-resolves to whatever is newest when it first installs. The chapter nonetheless told you to commit that config "so every contributor — and every CI run — resolves ... the same Rigor version", which a committed `latest` does not do; the command to pin is `mise use --pin gem:rigortype`, and `docs/install.md`'s agent instructions now use it. The upgrade section covers the other half: a pinned tool cannot be reported behind, because `mise upgrade` and `mise outdated` both compare against the range the config asks for and an exact pin is a range containing only itself — so a pinned setup has no passive signal that a new Rigor exists, and `mise upgrade --bump` is both how you look and how you move. Also documents the post-Ruby-change reinstall (`mise install -f "gem:*"`).
- **[docs]** The installation chapter now says *why* the version managers outrank a plain `gem install`, which it previously only asserted: RubyGems' executable starts with `#!/usr/bin/env ruby` and so runs under whatever Ruby is first on `PATH` at invocation time, and since Rigor requires Ruby 4.0 while projects pin their own, `rigor` fails to start inside a project on Ruby 3.x. mise's `gem:` backend has no such failure mode — each tool gets a private gem directory and an executable pointed at the Ruby it was installed with, so a project's Ruby pin cannot reach it. A new **If you want Bundler to manage the version** section draws the line the chapter had left implicit: the prohibition is on the *application's* `Gemfile`, not on Bundler, and the isolated `BUNDLE_GEMFILE` pattern already documented for CI ([11-ci.md](docs/manual/11-ci.md#pinning-rigors-version)) works locally and preserves everything the prohibition protects.
- **[packaging]** The gem now carries its own "not in your Gemfile" guardrails ([ADR-27](docs/adr/27-tool-distribution-model.md)). Handed nothing but `https://rubygems.org/gems/rigortype`, a coding agent reaches for `bundle add rigortype` — the gem page's own first suggestion — and Rigor had no counter-instruction anywhere that reader looks. All 39 published versions require Ruby `>= 4.0.0, < 4.1`, so on the Ruby almost every analyzed project runs the entry cannot resolve at all and the agent's next move is a destructive workaround (rewriting `.ruby-version`, `--ignore-dependencies`). On a Ruby 4.0 project it is worse: `bundle add` *succeeds*, and the failure lands later, at the next boot, as a bare `LoadError` naming `rigortype` — because `Bundler.require` requires a gem by its gem name and Rigor's library entry is `rigor.rb`. Three surfaces now carry the routing, one per moment the reader can be reached: `description` (rendered on the rubygems.org page — the moment the channel is chosen), `post_install_message` (after a `bundle add` has already succeeded; phrased conditionally, since `gem install` is a supported channel per ADR-27 WD6), and a `lib/rigortype.rb` shim that turns the boot-time `LoadError` into a warning naming the cause, the install doc, and `require: false`. The shim defines nothing — making the Gemfile install *work* is not the goal; making it explain itself is.
- **[cli]** `rigor plugins` now probes inflection availability when a loaded plugin depends on the shared `Plugin::Inflector` ([ADR-90](docs/adr/90-target-library-resolution-from-project-bundle.md)). When `ActiveSupport::Inflector` is loadable from neither Rigor's gem environment nor the analyzed project's bundle, the report warns which plugins will silently produce no inflection-dependent diagnostics and names the fix (`bundle install` the project, or install activesupport into Rigor's environment) instead of an unqualified `[OK]`; `--format json` carries a structured `inflection: {required_by:, available:}` field. A project with no inflection-consuming plugin never sees the probe.

- **[engine]** Hash literals with Integer, Float, `true` / `false` / `nil` keys now type as a value-pinned `HashShape` instead of degrading to a `Hash[K, V]` union, and a duplicate literal key is resolved **last-wins** exactly like the runtime — `{ 1 => 1, 1 => 2, 1.0 => 3, 1.00 => 4 }` types as `{ 1 => 2, 1.0 => 4 }` (previously `Hash[1 | 1.0, 1 | 2 | 3 | 4]`, with the overwritten values polluting the union), and `{ a: 1, a: 2 }` as `{ a: 2 }`.
  - Key identity follows Ruby's `Hash#eql?` semantics, matching the `flow.duplicate-hash-key` rule's key spaces: `1` and `1.0` are distinct keys while `1.0` and `1.00` collide. All existing `HashShape` projections (`[]`, `fetch`, `dig`, `key?`, `keys`, `values`, `values_at`, `slice`, `except`, `assoc`, `invert`, …) fold over the new key kinds, a lookup with a missing scalar key resolves to `nil` just like the symbol path, and non-symbol/string keys display in hashrocket form (`{ 1 => 2 }`). RBS erasure stays conservative — a shape with non-Symbol keys degrades to `Hash[K, V]`, never an invalid record. Computed keys, interpolated strings, and `**splat` entries keep today's generic-Hash behaviour. Precision-additive only: no new diagnostics.

- **[engine]** `Kernel#p` / `Kernel#pp` are now typed by their actual runtime contract — they return their argument. One argument passes through as a precision-preserving identity (`p(h)` keeps `h`'s exact type, shapes and constants included; a `Dynamic` argument stays `Dynamic`), several arguments come back as the tuple of their types (`p 1, 2` → `[1, 2]`), and the zero-arg form keeps the exact `nil`. Previously `p x` collapsed to `Dynamic[top]` and `p a, b` to `Array[Dynamic[top]]`, so wrapping an expression in a debug print destroyed its inferred type. The fold declines wherever it cannot be attributed to Kernel itself: an explicit non-Kernel receiver (`Kernel.p(x)` folds — `module_function` makes it the same intrinsic), a discovered user redefinition of `p` / `pp`, or a splatted / forwarded argument list (arity unknown). `format` / `sprintf` observe the same ownership guard, so `obj.format(...)` against a user class defining `format` is no longer folded as if it were Kernel's (one polarity for the whole intrinsic family, surfaced by the rigor-rs port's differential harness).
- **[engine]** More Kernel conversion functions constant-fold when their inputs are value-pinned: `format` / `sprintf` with a constant template and constant arguments fold to the exact string (`format("%d", 1)` → `"1"`, previously the `literal-string` carrier; a malformed directive declines to the previous behaviour), `String()` folds scalar literals (`String(42)` → `"42"`, restricted to core value classes so a user `to_s` is never modeled), and `Hash()` covers the trivially-sound shapes (a Hash-shape argument passes through; `Hash(nil)` / `Hash([])` → `{}`). A new `docs/notes/20260715-kernel-method-coverage.md` audit records the per-method coverage status for Kernel's whole surface, including the exclusion rationale for the non-deterministic / effectful set (`rand`, `gets`, `system`, …) where the wide RBS type is the correct answer.

- **[rigor check]** A new `flow.duplicate-hash-key` rule flags a Hash literal that repeats a literal key (`{ a: 1, b: 2, a: 3 }`, `m("x" => 1, "x" => 2)`), where Ruby silently keeps the last entry at runtime and only warns under `-w`.
  - The check is deliberately literal-only so it cannot fire on working code: symbols (the `key:` shorthand and `:key =>` count as the same key), plain non-interpolated strings, integers, floats, and `true` / `false` / `nil` participate; interpolated, constant, computed, and `**splat` keys are never compared. Symbol vs string (`:a` vs `"a"`) and Integer vs Float (`1` vs `1.0`) are distinct Hash keys and never collide. The diagnostic points at the later occurrence and names the line whose value it overwrites. Severity is `warning` under `balanced` (`info` lenient, `error` strict); suppress with `# rigor:disable duplicate-hash-key`.

- **[engine]** A new built-in diagnostic, **`flow.return-in-ensure`**, flags an explicit `return` lexically inside an `ensure` clause. Ruby runs `ensure` on every exit path, so a `return` there overrides the method's in-flight return value *and* silently swallows any exception being raised — the classic footgun RuboCop ships as `Lint/EnsureReturn` and PHPStan as its overwritten-exit-point rule.
  - The check is purely syntactic and frame-aware: a `return` inside a nested `def`, a lambda (`->` / `lambda`), or a `define_method` block within the `ensure` body does not fire (it exits that inner frame), while a `return` inside a plain block (`each do ... return ... end`) does — it still exits the enclosing method. Severity is `warning` under the default `balanced` profile (`info` lenient, `error` strict), evidence tier `high`. Suppress a deliberate use with `# rigor:disable flow.return-in-ensure` on the `return` line.

- **[rigor check]** A new `flow.shadowed-rescue-clause` diagnostic flags a `rescue` clause that can never run because an earlier clause in the same `begin` / `def` rescue chain already catches a superclass (or the same class) of every exception class it names — `rescue StandardError => e` followed by `rescue ArgumentError` leaves the ArgumentError arm dead, and a bare `rescue` counts as `StandardError`.
  - The rule compares only exception references that resolve to concrete classes with known ancestry (core classes via RBS, or project classes with a discovered `class Foo < Bar` chain); dynamic expressions, splats, unresolved constants, and module tags (`rescue MyGem::Error` mixin markers) keep the comparison silent, and rescuing narrow-to-wide (`ArgumentError` then `StandardError`) never fires. Severity: `warning` in the default balanced profile, `info` lenient, `error` strict; suppress with `# rigor:disable shadowed-rescue-clause` on the shadowed `rescue` line.

- **[rigor check]** A broken suppression comment is now flagged instead of silently doing nothing: `suppression.unknown-rule` fires when a `# rigor:disable` / `# rigor:disable-file` comment names a rule that does not exist (a typo like `call.undefined-metod`), `suppression.empty` fires when the marker lists no rules at all, and `suppression.unknown-marker` fires when the marker word itself is outside Rigor's grammar — typically the RuboCop reflex `# rigor:disable-next-line <rule>`, or `# rigor:enable` (Rigor's line suppression already scopes to its own line; there is no next-line or enable form). Previously such a comment was invisible to the whole suppression subsystem, surveillance included.
  - Modeled on PHPStan's ignore-parse-error check: a typo'd suppression that no-ops is the worst baseline failure mode, because the author believes the diagnostic is handled. Both rules are `:warning` in every profile, carry the offending token verbatim, and are themselves suppressible (`# rigor:disable suppression.unknown-rule`) or disable-able via `.rigor.yml`. Matching semantics are unchanged — an unrecognised token still only ever matches a diagnostic whose rule is literally that string. `plugin.`-prefixed tokens are never flagged (plugin rule vocabularies load dynamically), and known non-catalogue engine ids (`rbs_extended.*`, `dynamic.*`, `rbs.*`, `pre-eval.*`, `load-error`, …) pass.

- **[engine]** A new built-in diagnostic rule **`call.raise-non-exception`** flags a `raise x` / `fail x` whose first argument's inferred type provably cannot be raised — not an Exception class, not an Exception instance, not a String, and its class defines no `#exception` — so `raise 42`, `raise :symbol`, or `raise nil` (an explicit nil argument is a `TypeError`, unlike bare `raise`) surface at check time instead of as a runtime `TypeError` that masks the error the code meant to signal. Modeled on PHPStan's `ThrowExprTypeRule` (the 2026-07-15 PHPStan rule survey, Tier 1). The envelope is deliberately conservative: it never fires on `Dynamic` / unresolved types, a union fires only when every arm is independently illegal, a Class-object operand fires only when its RBS-known ancestry provably excludes `Exception`, the `#exception` duck protocol is honored (RBS-declared or project-defined), an explicit-receiver `obj.raise(...)` is ignored, and a project that redefines `raise` / `fail` silences the rule wherever the redefinition could resolve. Severity: `balanced` / `strict` `:error`, `lenient` `:warning`; evidence tier `high`.
- **[sig-gen]** `rigor sig-gen` now parses every signature it renders before emitting it, so it can no longer write RBS that `rbs` itself rejects.
  - Two shipped bugs had sig-gen emit unparseable RBS (a non-identifier record key, `{ :"data-contrast" => T }`; a `&block` constructor parameter rendered before the parens). Both were found downstream, as a poisoned `sig/` tree — and the consequence is now sharper: `rigor check` quarantines an unparseable `.rbs` *whole*, so one bad line deletes every other type in that file, and for a project adopting `reject-unparseable-signatures` it fails the build. A method whose rendered line does not parse is now **skipped** (`sig.skipped.unrenderable-rbs`) and reported on stderr, leaving the rest of the signatures valid and usable; under `--write`, a file whose assembled content does not parse is **refused** — the existing file is left untouched — and the command exits `1`. Such a skip is a Rigor rendering defect, not a property of the user's code, and the report says so. The guard is the `rbs` parser itself, i.e. exactly the oracle the consumer will use; it found nothing outstanding across Rigor's own `lib` plus five survey projects (~3,000 generated lines), which is the point — it is the net for the *next* rendering bug.
- **[engine]** An unparseable `.rbs` under `signature_paths:` is now reported as the `rbs.coverage.quarantined-signature` **warning**, so a broken signature file is visible everywhere a diagnostic is — `--format json`, SARIF, GitHub / GitLab annotations, the LSP — instead of only as a line on stderr.
  - Such a file is *quarantined* (skipped) so the rest of the RBS environment still loads. The failure mode that leaves behind is silence: the types it declared are absent, calls into them read `Dynamic[top]`, and the run comes back **quieter, not cleaner** — which reads as a clean run in CI. The diagnostic names the skipped file and the fix (`rbs validate`). `rigor doctor` now reports the same condition as a degraded (not healthy) RBS environment — it previously said "healthy" precisely because quarantining had kept the class count non-zero.
- **[cli]** The bleeding-edge overlay ships its first feature: **`reject-unparseable-signatures`** ([ADR-50](docs/adr/50-release-engineering-and-stability-strategy.md) § WD2/WD3). Adopting it promotes `rbs.coverage.quarantined-signature` to `:error`, so a broken signature file fails the run the way a broken source file already does.
  - Opt in with `bleeding_edge: true` (or `bleeding_edge: [reject-unparseable-signatures]`) in `.rigor.yml`, or `rigor check --bleeding-edge` for one run; `rigor show-bleedingedge` prints the overlay and what your project adopts. It is **off by default**: rejecting an input Rigor previously accepted is a new required discipline, and one that upgrading the `rbs` gem alone can trigger, so it goes through the overlay rather than turning a green build red on upgrade. It is the intended default at a future major.
- **[perf]** `rigor check` and `rigor coverage` now enable YJIT once a run outlasts a short amortization deadline, cutting wall time on large projects with no penalty to quick runs.
  - Ruby ships YJIT but leaves it off, and enabling it up front is a net loss on short runs because the JIT compile cost never amortizes (measured: a ~4s run regressed ~20%). Rigor now arms a background thread at the start of a check / coverage run that enables YJIT only after 5s, so a run that finishes first never pays the compile cost while a long run JITs its dominant tail. Measured cold on Mastodon `app`+`lib`: 25.4s → 15.1s (1.7×), matching always-on YJIT; the short-run cases (kramdown, Mastodon `app/models`, mail) stay at parity. The long-lived `rigor lsp` / `rigor mcp` servers enable YJIT at boot. Set `RIGOR_DISABLE_YJIT=1` to opt out, or `RIGOR_YJIT_DEADLINE=<seconds>` to tune the deadline. Diagnostics and allocations are unchanged.
- **[engine]** The opt-in `RIGOR_BUDGET_TRACE=1` trace now also prints a profile of the [ADR-57](docs/adr/57-self-call-return-adoption.md) user-method return memo: inference entries, memo hit rate, the non-store split (in-cycle / unroll-in-flight / fixpoint-tainted), body-evaluation counts, and the top signatures by body-eval count with their distinct memo-key counts. Dev-facing measurement input for future memo tuning (`--workers 0` for exact counts); analysis behaviour is unchanged, and a new property spec pins that dependency recording (`--incremental`) captures a callee's transitive cross-file reads for every consumer regardless of memo hits.

- **[config]** A new `cache.validation` setting (`stat`, the default, or `digest`) selects how `rigor check` re-validates cached file dependencies. `stat` uses the [ADR-87](docs/adr/87-null-build-floor.md) stat-then-digest tier (stat first, re-hash only when the file's `(size, mtime, ctime, inode)` moved); `digest` restores the previous behaviour of SHA-256'ing every recorded file on every run. `RIGOR_STRICT_VALIDATION=1` forces `digest` for a single run regardless of the setting (the per-run escape hatch for a filesystem whose stat timestamps cannot be trusted).
- **[perf]** `rigor check --incremental` now honours the worker-count knobs the standard `check` path already respects — `--workers=N`, `RIGOR_RACTOR_WORKERS`, and `.rigor.yml` `parallel.workers:` — so the closure re-analysis after an edit runs across a fork-worker pool instead of always sequentially ([ADR-46](docs/adr/46-incremental-dependency-graph.md)). Previously the incremental path silently ignored every worker setting. Each worker records its slice's cross-file dependency edges and marshals them back to the coordinator, so the dependency graph a pooled recheck rebuilds is identical to the sequential one (a subsequent recheck stays sound); the win is on large closures (a base-class / concern edit whose closure is hundreds of files), and is neutral on the common small-closure edit that the fixed per-recheck floor dominates. The default stays sequential (`workers: 0`), and `--verify-incremental` runs sequentially.

### Changed

- **[perf]** A parallel `rigor check` / `coverage` run (`--workers=N`) now enables YJIT inside its fork workers, not just the coordinator. The [deadline-armed YJIT](docs/adr/50-release-engineering-and-stability-strategy.md) runs on a background thread, and `fork` copies only the calling thread — so the parent's deadline thread never reached the workers, and a worker forked before the deadline fired ran its whole (dominant) analysis slice un-JITted, exactly the long run parallel mode exists for. Each worker now re-arms its own deferred YJIT: a worker inherits the enabled state when a slow env build pushed the fork past the deadline (a no-op), otherwise it times its own slice and JITs the tail once it proves long enough — the same amortization contract, per worker. Diagnostics stay byte-identical (verified pooled-vs-sequential); `RIGOR_DISABLE_YJIT=1` still disables it everywhere.
- **[perf]** The bundled plugins' hand-rolled AST walks no longer allocate a throwaway child-node array per node. The discoverers and scanners in 21 plugin / example files (`rigor-actionpack`, `rigor-activerecord`, `rigor-actionmailer`, `rigor-rails-routes`, `rigor-sorbet`, `rigor-rspec`, …) walked their target's AST with `node.compact_child_nodes.each`, which builds a fresh `Array` on every node — the same allocation the engine's own walkers dropped by switching to `#rigor_each_child` ([`Rigor::Source::NodeChildren`](lib/rigor/source/node_children.rb)). Those 37 `.each` sites now call `#rigor_each_child`, which yields the same children in the same order with no intermediate array. Only the plain-iteration sites migrated; the handful that need an actual array (`flat_map` / `each_with_object` / `any?` / `concat`) keep `compact_child_nodes`. Diagnostics are byte-identical (verified on the Redmine corpus and every plugin integration spec).
- **[cli]** `rigor doctor` no longer headlines "0 issue(s) found" on a run whose only findings are warnings; the summary counts warnings too.
- **[perf]** A comment-only edit under `rigor check --incremental` now re-checks only the edited file instead of its whole ancestry / file-level dependent set. When a changed file's CODE (comments stripped) is byte-identical to the snapshot, the file is declaration-stable — every cross-file fact its dependents consume is code-derived and therefore unchanged — so those dependents are served from cache (the "bundle-equality propagation gate"). Measured on GitLab (`app/models app/controllers`, 1,774 files): an in-place comment edit that previously re-analysed 19 / 66 / **341** files (a mid-fan-out model / a 25-includer concern / `ApplicationRecord`) now re-analyses **1**, dropping a base-class comment recheck from ~12.3s to ~7.9s; a body edit to the same files still re-checks the full closure. The gate fires only on edits that do not shift a method's line numbers (an added comment line does), preserving the def-site diagnostics that name a definition's `path:line`, and it disables itself when a comment-ingesting plugin (`rigor-rbs-inline`) is configured (Sorbet sigs and dry-types includes are code, so the code fingerprint already covers them). Soundness is backstopped by a fabricated-edit battery (constant / class-ivar / class-cvar / global edits stay byte-identical to a full run) plus `make check-incremental`. The snapshot schema is bumped again (a one-time clean cold rebuild).
- **[perf]** A `rigor check --incremental` recheck now re-analyzes a dependent only when the edit actually changed something the dependent can consume — extending the comment-only gate above to BODY edits ([ADR-89](docs/adr/89-semantic-propagation-gates.md)). Two cases collapse: **(1)** a same-line body edit whose method SIGNATURES are unchanged (a local rename, an internal literal) no longer re-checks the edited class's ancestry / file-level dependents — they consume only its *declaration shape* (parameter structure, visibility, ancestry, member layouts, method existence, def lines), which the edit left equal. Measured on GitLab (`app/models app/controllers`): a return-preserving edit to `ApplicationRecord.safe_find_or_create_by` that previously re-analysed **341** files now re-analyses **1**, and a `label.rb` `reference_prefix` literal change **19 → 1**, both byte-identical to a full run. **(2)** a return-preserving refactor of an eligible leaf method (one that writes no instance / class variable, does not `yield`, and makes no self-call) no longer re-checks its callers when re-evaluating it at every previously-observed call argument yields the same return type and its content-mutation effects are unchanged. Any signature / arity / visibility / added-or-removed-method / ancestry change, a moved return, a changed mutation effect, or a line-shifting edit still propagates (a line shift moves a def's `path:line`, so the file's dependents re-check to keep the def-site diagnostics sound). Sound only on top of the plugin-fact fingerprint gate — a mismatch or an opaque contributing plugin discards the gated recheck and runs a full analysis. Diagnostics are byte-identical (cold and via `--verify-incremental`); the snapshot schema is bumped (a one-time clean cold rebuild).
- **[perf]** A `rigor check --incremental` recheck does slightly less redundant work per edit: the changed set was parsed twice while computing the affected closure (once for per-symbol fingerprints, once for class declarations) and is now parsed once, and the disk-glob-only probe Runner built solely to size the banner is gone (the count comes from the session). The dominant per-recheck floor (whole-project plugin re-scans + the discovery re-walk) is unchanged — it is intrinsic to the loaded plugins not being incremental-aware.

- **[perf]** A warm `rigor check` HIT — the common "nothing changed, tell me it's still clean" run — is dramatically faster: it now serves the cached diagnostics without loading the inference engine, its plugin gems, or the RBS environment, and validates cached file dependencies by **stat** instead of re-reading and re-hashing them ([ADR-87](docs/adr/87-null-build-floor.md), the "null build" floor).
  - Two floors are removed. (1) On a monorepo a warm hit previously re-SHA-256'd every cached dependency + plugin-watched file — ~115 MB across ~52k files on GitLab `app/models` — on *every* run; a `:stat` file-entry tuple (`digest + size + mtime_ns + ctime_ns + inode + recording-instant`) and a stat-based `watch:`-glob signature now let an unchanged tree validate with **zero content bytes hashed**, the SHA-256 digest still deciding any file whose stat actually moved (a `touch` stays fresh; the `--verify-incremental` gate stays byte-identical). (2) A hit no longer boots the analyzer at all: a lightweight probe builds the [ADR-45](docs/adr/45-unchanged-project-fast-path.md) run-cache key from configuration alone and serves the cached run before the engine is required. Measured (out-of-process, on the dev host): GitLab `app/models` warm hit **1.41s → 0.34s**, mail / rigor `lib` warm hit **~0.36s → ~0.22s**, warm `--incremental` zero-change **1.85s → 1.44s**. Diagnostics are byte-identical, and `--no-cache` / editor / pool / `--coverage` / `--incremental` runs are unaffected. Set `cache.validation: digest` (or `RIGOR_STRICT_VALIDATION=1`) to restore the digest-every-file behaviour.
- **[perf]** A zero-change `rigor check --incremental` recheck no longer rewrites its on-disk snapshot (it was byte-equivalent to what was just loaded), saving the serialize + write on every null recheck ([ADR-87](docs/adr/87-null-build-floor.md) WD3).
- **[perf]** A warm `rigor check --incremental` recheck now serves plugin `#prepare` producers from the persistent cache instead of recomputing them, cutting warm-incremental cost on plugin-heavy (Rails) projects several-fold ([ADR-85](docs/adr/85-seed-bundles-and-lazy-def-node-handles.md) WD1).
  - The cross-process incremental session built each internal analyzer with no cache store, so every plugin's cached `producer` (an ActiveRecord model / schema scan, a Rails-routes helper table, …) recomputed on every `--incremental` invocation even though the [#74](https://github.com/rigortype/rigor/pull/74) / [ADR-60](docs/adr/60-pre-freeze-plugin-contract-consolidation.md) WD3 record-and-validate caches were already on disk from the previous run. Threading the store through the session lets those producers serve from disk; the whole-run [ADR-45](docs/adr/45-unchanged-project-fast-path.md) result cache stays disabled on these runs (it is incompatible with the per-file dependency recording and subset analysis the incremental path relies on). Measured on GitLab `app/models` (10 auto-loaded Rails plugins), a warm `--incremental` recheck drops from 16.7M to 2.8M allocations (~6×) — plugin `#prepare` alone from 14.3M to 0.34M — with byte-identical diagnostics. `--no-cache` recomputes fresh, exactly as before, and `--verify-incremental` now also asserts the cache-served producer path matches the uncached full run.
- **[perf]** A warm `rigor check --incremental` recheck no longer re-parses the whole project to rebuild its cross-file discovery index. It now folds each file's cached per-file *seed bundle* — plain-data discovery tables plus lazy def-node handles — from the incremental snapshot, re-walking only the files whose content changed ([ADR-85](docs/adr/85-seed-bundles-and-lazy-def-node-handles.md) WD2/WD3).
  - Every `--incremental` recheck is a cache-miss-path run: before re-analyzing its small changed subset it rebuilt the whole-project class / def-node / ancestry index by parsing and walking every file — 80–92% of a warm incremental on a plugin-light project. The snapshot now carries a per-file bundle (keyed by content digest) of that file's pre-pass contribution, with its `def` nodes stored as `(path, node_id, name, fingerprint)` handles instead of live AST nodes; a recheck rebuilds the index by folding the bundles in file order (re-walking only changed files) and materialises a def body only when an accessor actually demands it — 0–6 files per recheck. Measured warm zero-change incremental: rigor `lib` 540k → 149k allocations (the discovery pre-pass 436k → 25k), mail `lib` 529k → 54k (485k → 5k); on GitLab `app/models` the combined effect with the plugin-producer cache above is 16.7M → 2.06M (~8×). A full (non-`--incremental`) run keeps today's parse+walk unchanged, and diagnostics are byte-identical (the `--verify-incremental` gate additionally asserts the folded index matches a full re-analysis). The snapshot schema is bumped, so a snapshot written by an older Rigor is ignored (a one-time clean cold rebuild).
- **[perf]** `rigor check --incremental` change detection now stats unchanged files instead of SHA-256'ing them. A recheck previously re-hashed the full content of every project file to decide which changed; it now validates each file's recorded [ADR-87](docs/adr/87-null-build-floor.md) stat entry (`digest + size + mtime_ns + ctime_ns + inode + recording-instant`), re-hashing only a file whose `(size, mtime, ctime, inode)` tuple moved — an unchanged recheck hashes zero content bytes for change detection. The SHA-256 digest stays the sole change authority (a `touch` that moves the stat but not the content re-hashes once and stays fresh), and `cache.validation: digest` / `RIGOR_STRICT_VALIDATION=1` restores digest-every-file. `--verify-incremental` stays byte-identical.
- **[perf]** A `def self.method` / singleton-method body edit under `--incremental` now gets the same symbol-granularity scoping an instance-method edit already had: its recheck closure is limited to that method's call sites instead of degrading to the edited file's full dependent set ([ADR-46](docs/adr/46-incremental-dependency-graph.md) slice 4, extended to the singleton def tables). The change-detection fingerprint and the recorded call-site dependency edge now cover class / singleton / `module_function` methods (keyed `Class.method`, distinct from the instance `Class#method`), which the pre-pass previously tracked only for instance methods. On a base class with a large ancestry fan-out (e.g. a Rails `ApplicationRecord`) the file-granular ancestry edges still dominate the closure, so the win shows on a class-method utility whose defining file has few ancestry dependents. Diagnostics are byte-identical; the snapshot schema is bumped (a one-time clean cold rebuild).
- **[engine]** The [ADR-57](docs/adr/57-self-call-return-adoption.md) user-method return memo is now genuinely run-scoped, so a callee's inferred return is computed once per run instead of once per consumer file, and the blanket "no memoisation while a constant-arg unroll is in flight" refusal is replaced by a per-compute taint verdict ([ADR-84](docs/adr/84-cross-file-return-memo-scoping.md)).
  - The memo's bucket previously keyed on a per-file table identity, so hits never crossed a file boundary — mail's `Mail::Part#has_content_type?` was re-evaluated 564 times, once per calling file. The bucket now keys on a per-run generation token (rolled between runs in one process, so LSP re-checks and warm loops never see a stale entry), cutting cold callee body evaluations 3,355 → 557 on mail `lib` and 9,977 → 7,339 on Rigor's own `lib`. Because a cross-file hit skips the callee body walk, dependency recording (`--incremental` baselines, `--verify-incremental`) pairs every hit with cache-and-replay: the first evaluation of a signature captures the cross-file reads its body performs, and a hit replays them into the current consumer's record — recorded edges are identical to a memo-free run, pinned by property specs.
  - Memo candidacy under the ADR-55 recursion machinery is now decided post hoc instead of by the blanket unroll exclusion (82% of mail's body evaluations were refused for results that were overwhelmingly final): every transient-machinery fallback (recursion-guard hit, unroll-fuel exhaustion, ADR-55 WD1 clamp, fixpoint-cap collapse) logs the stack frame whose state it referenced, and a result is stored unless an event during its compute referenced a frame below the compute's entry depth — i.e. only when the ancestor context actually influenced it. A recursive method's own converged fixpoint memoises; a nested compute degraded by shared unroll fuel does not. Diagnostics are byte-identical across mail, kramdown, Mastodon `app/models`, Redmine `app/models`, and Rigor's own `lib`.
- **[rigor-dry-types]** The dry-types alias scan is now cached across runs, so a warm `rigor check` re-validates file digests instead of re-parsing the whole project ([ADR-60](docs/adr/60-pre-freeze-plugin-contract-consolidation.md) WD3).
  - The plugin's `#prepare` used to Prism-parse every `.rb` file under the project's `paths:` on every invocation — cold and warm alike — to find `include Dry.Types()` declarations, which dominated warm-run wall time on large Rails apps (measured at roughly a third of GitLab `app/models` warm time). The scan now rides a cached `producer` with a `watch:` glob covering the same tree: a warm run re-globs and re-digests the watched files (a cheap SHA over file bytes, no AST build) and reuses the cached alias table, recomputing only when a source file under those paths is edited, added, or removed. The empty result for a project that ships no dry-types module is cached too. `--no-cache` recomputes fresh, exactly as before.
- **[engine]** AST tree walks no longer allocate a throwaway array per node visited, cutting total allocations on every `rigor check` run — most sharply on leaf-heavy sources.
  - `Prism::Node#compact_child_nodes` builds a fresh `Array` on every call, and Rigor's walkers called it unconditionally on every node of every walk. On a Ragel-generated parser (mail's `lib`, with hundreds of thousands of integer-literal leaf nodes) those arrays were over half of all allocations. Loading `Rigor::Source::NodeChildren` now compiles a `#rigor_each_child` method onto each Prism node class that yields the same children in the same order without the array — reading each child field directly and reusing list fields' stored arrays — and the engine's tree walkers (the shared node walker, the plugin/check-rule walk, the scope-discovery seed pass, the collectors, and the sig-gen / dependency / mutation scanners) call it in place of `compact_child_nodes.each`. Diagnostics are byte-identical; the field map is derived from `Prism::Reflection` so it tracks the installed `prism`.
- **[engine]** Warm cache runs no longer re-parse the whole project. The cross-file discovery pre-pass (class discovery + the ADR-24 def-node index) is deferred out of the eager pre-pass and run only on the analysis (cache-miss / `--no-cache`) path, so a warm `rigor check` that serves its diagnostics from the ADR-45 run cache skips it entirely. Diagnostics are byte-identical; the dependency-recording and subset (`--incremental` / `--verify-incremental`) modes still force the build eagerly.
- **[engine]** On a cold / `--no-cache` run the cross-file discovery pre-pass now parses each project file once instead of twice. The class-discovery and def-node passes previously each `Prism.parse`d every file independently; they now share a single walk (`ScopeIndexer.discovered_project_index_for_paths`), parsing each file once and dropping the AST before the next (peak RSS unchanged). Diagnostics are byte-identical.
- **[engine]** A warm cache run no longer SHA-256-hashes the whole RBS signature tree. The run-diagnostics cache descriptor computes its RBS file digests lazily — the cache key reads only the `rbs` gem version + library list, and the (large, vendored) signature-tree digests are now computed solely on a cache miss. Combined with a per-run digest memo (each absolute path is hashed at most once per run across the dependency descriptor, its `fresh?` validation, the RBS tree, and every plugin producer's watched-glob validation — these sets overlap heavily), warm runs do markedly less filesystem digesting. The memo is process-local, never persisted, and reset per run, so it changes nothing about what a run observes.


### Fixed

- **[plugin]** A standalone install (`gem install rigortype`, no shared gem environment with the analyzed app) no longer silently loses every inflection-dependent Rails check ([ADR-90](docs/adr/90-target-library-resolution-from-project-bundle.md)). The bundled Rails plugins inflect through the real `ActiveSupport::Inflector` ([ADR-39](docs/adr/39-plugin-target-library-invocation.md)) but rigortype deliberately carries no activesupport runtime dependency, so in a standalone install the inflector was never loadable and `rigor-activerecord` / `rigor-rails-routes` / `rigor-actionpack` / `rigor-actionmailer` / `rigor-factorybot` degraded to producing no diagnostics. A target library that fails to require is now retried against the **analyzed project's own bundler install tree** (`vendor/bundle`, `.bundle/config`, or the user-global bundler path) — the project's locked activesupport is on disk for any bundled Rails app, and its own copy is the higher-fidelity source of inflection rules anyway. The fallback appends the bundle gems' gemspec-declared require paths to the load path (append-only — Rigor's own gems keep precedence) and, under the default `process` isolation strategy, only inside the forked worker; a project whose bundle is not installed still degrades cleanly.
- **[plugin]** The plugin isolation worker no longer dies with an opaque `Inflector::Unavailable: process isolation worker failed (EOFError)` when a target library cannot be loaded. `Rigor::Plugin::LoadError` lexically shadows the global `LoadError` inside the isolation module, so the worker loop's bare `rescue` matched the wrong class and the real `::LoadError` (a ScriptError) killed the forked worker; the rescues are now `::`-qualified and the worker replies with the clean decline (`worker error: LoadError: cannot load such file — …`) it was designed to give. The same shadowing bug is fixed in `rigor-rspec-rails`'s Rack status-table loader.

The positional slot of both commands is a doc / skill *name*, so a removed verb now resolves as an unknown name (exit 1) rather than shadowing a same-named page — which is why the verbs went. `rigor skill describe` / `--describe` (and `rigor describe`) are a no-argument action, not a name-slot verb, and are unchanged.
- **[dev]** The `parallel_tests` development dependency is dropped, along with the `make test-parallel` target and the `rake spec_parallel` task it drove. `binpacker` has been the project's parallel spec runner since [#27](https://github.com/rigortype/rigor/pull/27) (`make test-binpacker`, what `make verify` and CI run), so the second runner was dead weight. Contributors who scripted `make test-parallel` should use `make test-binpacker`; the worker count now comes from `binpacker.yml` (`workers: auto`) rather than `PARALLEL_TEST_PROCESSORS`. A consumer reading the capability catalogue must read the new key; the value's shape is unchanged.

## [0.2.9] - 2026-07-11

v0.2.9 sharpens Rigor on large Rails applications, with GitLab-scale projects as the proving ground: PostgreSQL `db/structure.sql` is accepted as a schema source, the strong-parameters chain stays typed, several route-helper and ActiveSupport coverage gaps close, and module facades now resolve across files. Protection-coverage tooling gets faster with a fork-parallel scan and more actionable — it now names when a missing-RBS gem is the cause of a hole ([ADR-82](docs/adr/82-dynamic-provenance-wiring.md)). Other fixes strengthen control-flow narrowing around `present?` / `blank?` guards and in-body mutation, and make the persistent cache robust across upgrades.

### Added

- **[rigor-activerecord]** A PostgreSQL `db/structure.sql` is now accepted as a schema source, so `schema_format = :sql` projects (GitLab-class apps) are no longer inert.
  - When `db/schema.rb` is absent the plugin parses `db/structure.sql` (configurable via `structure_sql_file`) into the same schema table the Ruby-DSL parser produces — column names, types, and Postgres array columns. Previously such a project loaded no schema at all, so every ActiveRecord check was skipped and relation chains cascaded false diagnostics. An unmappable column type (custom enum, `tsvector`) degrades to `Object` rather than being dropped.
  - A `serialize` / `mount_uploader` / custom-`attribute` column reads leniently rather than being narrowed to its SQL scalar type, so `note.position.diff_refs` and `diff.external_diff.store!` no longer read as `undefined-method`. Column existence checks (`where(col:)`) are unaffected.
- **[rigor-actionpack]** The strong-parameters fluent chain now stays typed, so `coverage --protection` counts the chained sites as protected.
  - `params.require(:user)` / `.permit(:name)` previously returned `Dynamic` at the first hop (the class ships no bundled RBS), leaking every downstream site. `require` / `permit` / `permit!` on a `Parameters` receiver now re-type to the same lenient nominal, keeping the chain a concrete receiver end-to-end. It types the container, never a caller's argument.
- **[engine]** A `module` constant now resolves to its module object across files, so calls on a module facade (`Feature.enabled?`, `Gitlab::Utils.to_boolean`) are typed instead of dynamic ([ADR-57](docs/adr/57-self-call-return-adoption.md) WD3).
  - Rigor's per-file pass always typed `module M` as the module object, but the project-wide discovery seed registered only classes, so the same constant read from a sibling file fell back to `Dynamic`. Both halves now agree: a call to a `def self.x` / `class << self` / `module_function` method declared in another file re-types the callee's body as it already did in-file. On GitLab, `Feature.enabled?` alone is 695 previously-unprotected sites.
- **[rigor coverage]** `coverage --protection` now tells you which holes an external gem's missing RBS causes, instead of filing them under "engine gap" ([ADR-82](docs/adr/82-dynamic-provenance-wiring.md) WD9).
  - When an unresolved constant (`Faraday`, `I18n`) is declared by a gem locked in your `Gemfile.lock` that ships no RBS, the whole chain rooted at it is labeled `external_gem_without_rbs` → `add_rbs` — the one answer a user can act on directly (`rbs collection install`, or write the signature). Ownership is established by parsing the gem's entry file for its declared constants, never guessed from the gem's name, and no gem code runs; a constant no locked gem declares keeps the generic cause, so the failure mode is a missing label, never a wrong one.

### Changed

- **[rigor coverage]** `coverage --protection` now runs in parallel and honours the same worker knob as `rigor check`, so a large project's protection scan is no longer stuck single-threaded.
  - The parameter-inference pre-pass and the per-file protection scan are each fork-mapped over worker processes built from one parent-side environment (RBS env, plugin registry, and cross-file seed built once and copy-on-write inherited). Worker count resolves exactly as `check` does (`--workers=N` › `RIGOR_RACTOR_WORKERS` › `.rigor.yml` `parallel.workers:` › `0`), and the output is byte-identical to a sequential run. Measured on Mastodon `app lib`: 61 s → 43 s at four workers, with peak memory roughly halved.
- **[rigor coverage]** `rigor coverage` with no path argument now falls back to the configured `paths:` (default `lib`), matching `rigor check`, instead of erroring.
- **[repo]** The `rigor-playground` browser-playground backend moved from `plugins/` to `apps/rigor-playground/` (it is a standalone Rack/Puma application, not an analyzer plugin), so its Fly.io / Docker deploy commands now reference the new path.

### Fixed

- **[rigor annotate]** Interior lines of a multi-line Hash literal (and of a multi-line keyword-argument list) no longer carry a noise `#=> Dynamic[top]` annotation; the literal's type now appears once, on the line the enclosing statement closes.
- **[cli]** `rigor check --format <name>` for a format listed as supported but not wired now fails loudly instead of printing nothing, so a drift between the supported-format list and the dispatch cannot pass silently.
- **[engine]** A guard like `if login.present?` / `return if content.blank?` now narrows a nilable receiver, so the guarded call no longer reads as `possible nil receiver`.
  - When a predicate's signature declares it always returns `false` for `nil` (as ActiveSupport's `NilClass#present?` does), a truthy answer proves the receiver was not nil and the nil arm is dropped on that edge, mirrored on the falsey edge for `blank?`. Only value-pinned `nil` / `true` / `false` arms participate, and a safe-navigation guard (`x&.blank?`) is deliberately left alone. Removes four false positives on Redmine and sixteen on GitLab, none introduced anywhere.
- **[engine]** A collection filled by a helper that mutates it (`items.each { |s| absorb(s, acc) }; … unless acc.empty?`) no longer reads as `flow.always-truthy-condition`.
  - When a call resolves to a user method that content-mutates one of its parameters directly in its body (`param[k] = v` / `param << x`), the matching caller argument is floored, so a later shape read stops folding against the stale empty-literal seed ([ADR-56](docs/adr/56-block-captured-local-mutation.md) / [ADR-57](docs/adr/57-self-call-return-adoption.md)). It only forgets a literal-shape fact the mutation invalidates, never invents one.
- **[rigor-actionpack]** `unknown-permit-key` no longer fires on a virtual (non-column) attribute in strong-parameters.
  - Permitting a non-column is ordinary Rails — a Devise virtual attribute (`password`, `remember_me`), a state-machine `*_event`, an `attr_accessor` setter. The check is now a typo detector: it fires only when the permit key is a near-miss edit-distance match of a real column (`emial` → `email`), never on a legitimate virtual attribute.
- **[rigor-rails-routes]** A project mounting a Grape API no longer reads its `grape-path-helpers` calls (`api_v4_groups_badges_path`) as `unknown-helper`.
  - The gem names each helper after its route's path segments from grape's runtime route table, which metaprogramming builds so no static parser can enumerate the names. The plugin reads the project's own Grape `prefix` and `version` declarations (`grape_api_paths:`, default `lib/api` + `app/api`) and treats `<prefix>_<version>_…_path` as valid-but-unenumerable. Teeth stay where the gem's contract makes them sound: it defines no `_url` helper, so `api_v4_groups_badges_url` still fires. Removes 68 of GitLab's 141 `unknown-helper` errors.
- **[rigor-rails-routes]** Two route-helper name-composition gaps that fired false `unknown-helper` on working code now match Rails' own naming.
  - A multi-segment string action inside a `member do` / `collection do` block (`collection { get 'granular/new' }`) is named the way Rails' `Mapper.normalize_name` does (`granular_new_<scope>_<plural>_path`) instead of the generic mis-ordered name.
  - A bare symbol action in a named scope (`scope(as: :user) { get :activity }`) now registers `<scope_as>_activity_path`; previously such a call registered no helper and read as `unknown-helper`.
- **[rigor-activerecord]** A nested / joined-table condition (`Model.where(assoc: { ... })`) no longer reads as an unknown column — the Hash value marks a join condition whose key names an association or joined table, not a column on the receiver.
- **[rigor-activesupport-core-ext]** More ActiveSupport core extensions are covered, so calls on them no longer read as `undefined-method`: `String#upcase_first` / `#remove` / `#titlecase` / `#dasherize`, `Object#in?`, `Date`/`Time#advance` / `#all_day`, `Date#to_time(form)`, and `ERB::Util.html_escape_once`.
- **[core RBS overlay]** Two stdlib signatures the pinned `rbs` gem omits are supplied so real calls stop false-firing: `Psych.parse` / `.parse_stream` no longer reads as `undefined-method`, and `CSV::MalformedCSVError.new(message, line_number)` (the documented two-arg constructor) no longer reads as `wrong-arity`.
- **[cache]** Persistent cache entries are now rebuilt after a Rigor upgrade, stale generations are reclaimed more aggressively, and a broken cache root degrades to memory-only instead of raising.
  - The cache root marker now folds in `Rigor::VERSION`, so Marshal payloads written by an older release are never reused after an upgrade — the first writable run after upgrading rebuilds the cache.
  - A read-only store (LSP / editor mode) now checks that marker before trusting a disk hit, closing the one path where an ABI-stale payload could still be unmarshalled after an upgrade.
  - Whole-project cache producers now keep only a few recent generations, reclaiming content-keyed orphans that sat below the global byte cap indefinitely, even when `cache.max_bytes` is unbounded.
  - A cache root that cannot be read or repaired (permission error, disk full, deleted root) no longer fails the run — analysis continues with the disk tier disabled.

- **[rigor sig-gen]** Generated RBS for a subclass now carries its superclass — `class GitAdapter < AbstractAdapter` instead of the bare `class GitAdapter` — for plain-constant parents (`class X < Foo` / `class X < Foo::Bar`).

A computed parent (`Struct.new` / `Data.define` / `Class.new`) is still emitted without a superclass, as before.
- **[engine]** A malformed project `.rbs` no longer collapses the entire RBS environment.
  - The referenced-type stub sweep re-declared an already-declared `class` as a `module` when stubbing an enclosing namespace (e.g. stubbing `Foo::GitAdapter::Revision` re-emitted `module Foo::GitAdapter` over the existing `class`), and the resulting `RBS::DuplicatedDeclarationError` nulled the whole env — every type-of query then degraded to `Dynamic[top]` and most diagnostics silently stopped firing. - **[gem metadata]** The gem's `documentation_uri` now points at the `master` branch, fixing the 404 the RubyGems "Documentation" link returned.

  - `String#shellescape` folds to a `Constant[String]` and `String#shellsplit` lifts its token list to a `Tuple` (`"ls -la".shellsplit` → `Tuple["ls", "-la"]`) — the String-receiver twins of the already-folded `Shellwords.escape` / `Shellwords.split`. The cue is presence-only: Rails in `Gemfile.lock` plus no `rigor-rails-*` plugin in the config.
- **[cli]** `rigor check` now prints a prominent WARNING when the RBS environment is empty (`RBS classes available: 0`). A normal run always loads the bundled core + stdlib RBS, so zero means the environment failed to build — usually a duplicate declaration in `signature_paths:` — and fell back to empty, leaving an otherwise-"successful" run with near-useless type coverage (most diagnostics and coverage cannot fire). Surfacing it stops a broken setup from being mistaken for a clean analysis — the field trial's redmine case would otherwise have wired a 0-coverage check into CI.

### Performance

- **[inference]** The `ScopeIndexer` seed pass walks each file's AST fewer times. The discovery pre-pass ran a separate full-tree descent per table; in particular the discovered-methods walk and the instance-method def-node walk had byte-identical class / module / singleton traversals yet ran independently, and the cross-file pre-pass walked the def-node tree *twice* (once in `merge_discovered_defs`, once in `record_class_sources`). One combined `walk_methods_and_def_nodes` descent now produces both tables at once, and the def-node table is threaded to its second consumer instead of recomputed. Definition-dense libraries benefit most — cold `rigor check --no-cache` on the `mail` gem (196 files) allocates ~8% fewer objects (20.6M → 18.9M); Mastodon and Redmine drop ~0.5–1%. Diagnostics are byte-identical across the survey corpus ([profiling note](docs/notes/20260620-corpus-cold-warm-reprofile.md)).

### Documentation

- **[docs]** A cross-tree consistency audit of the handbook, manual, and the internal / type specifications corrected a batch of contradictions surfaced against the implementation.
  - Severity and grammar: the handbook errors chapter listed the wrong default severity for two rules (`call.possible-nil-receiver` is `error`, not `warning`; `def.ivar-write-mismatch` is `warning` under `balanced`, not `error`); the `RBS::Extended` directive grammar carried a spurious colon on the `assert` / `assert-if-*` / `predicate-if-*` / `conforms-to` directives (only `return:` and `param:` take one) and documented a non-existent `assertion-on` directive, while the real `assert-if-true` / `assert-if-false` directives are now in the directive table; and handbook chapter 9 plus several appendices still presented the removed `flow_contribution_for` plugin hook as current, now `dynamic_return` / `type_specifier` ([ADR-52](docs/adr/52-compiled-plugin-contribution-dispatch.md)).
  - Catalogues and counts: the examples count ("sixteen" → six) and production-plugin count ("Thirty" → thirty-one) were corrected; the reserved-refinement catalogue forbade the implemented `int<min, max>` form and omitted `non-empty-hash[K, V]`; and the narrowing catalogue gained the `respond_to?` and `empty?` / `any?` / `none?` predicate shapes it already implements (the handbook had claimed `respond_to?` is never narrowed).
  - Caching, API, and rendering: the caching chapter claimed adding/removing a file forces a full run (it is handled incrementally); `plugin-cache-producers.md` claimed plugin caches are unbounded (they share the 256 MB-capped LRU store per [ADR-54](docs/adr/54-cache-slimming.md)); `public-api.md` named a non-existent `protocols` manifest member (now `protocol_contracts`); `diagnostic-shape.md`'s "before v0.1.0" lock note was updated to the [ADR-50](docs/adr/50-release-engineering-and-stability-strategy.md) v1.0 freeze; `Dynamic[Top]` was normalised to the engine's actual `Dynamic[top]` rendering throughout; and two stale source comments that had seeded doc errors were corrected in the same pass.

## [0.2.1] - 2026-06-19

v0.2.1 continues the 0.2.x evaluation line with detection and configuration polish. The headline is a `Gemfile.lock`-gated ActiveSupport RBS overlay that silences the systematic core-extension false positives a Rails project saw on `3.minutes` and friends, resolving the v0.2.0 evidence-tier feedback at its source ([ADR-72](docs/adr/72-gemfile-lock-gated-rbs-overlays.md)). `rigor check` now warns when a configuration value silently resolves to nothing, and `rigor coverage` gains a fused static-plus-dynamic protection map ([ADR-70](docs/adr/70-fused-protection-coverage.md)). Constant folding reaches a few more pure scalar and structural methods, and fixes include a gem-packaging bug that left installed gems without their bundled RBS data.

### Added

- **[inference]** Rigor now auto-loads a bundled ActiveSupport core-ext RBS overlay when `activesupport` is in your `Gemfile.lock` but ships no RBS, so core-extension calls like `3.minutes`, `6.days`, `"x".underscore`, and `hash.symbolize_keys` stop firing a false `call.undefined-method` on a Rails project with no plugin or config ([ADR-72](docs/adr/72-gemfile-lock-gated-rbs-overlays.md)).
  - It is gated on the gem actually being locked, so a plain-Ruby project with no `activesupport` still gets the genuine `undefined method 'minutes' for 3`, and a real typo on a core type (`5.minuets`) keeps firing at `evidence_tier: high`.
  - This resolves the v0.2.0 `evidence_tier` calibration report at its source rather than relabelling the firings — the tier never feeds severity, so a down-tier would have left the false error on screen.
  - The overlay stands down automatically when the opt-in [`rigor-activesupport-core-ext`](plugins/rigor-activesupport-core-ext/) plugin is loaded, and is bypassed if you supply ActiveSupport RBS yourself (via `rbs collection install` or `signature_paths:`).
- **[inference]** A few more pure, deterministic methods on literal receivers now fold to a precise `Constant` or `Tuple` instead of the widened RBS type.
  - `Symbol#name` / `#id2name` fold to `Constant[String]` and `#intern` to `Constant[Symbol]`, the natural siblings of the already-folded `to_s` / `to_sym`.
  - `Integer#finite?` / `#infinite?` / `#nonzero?` fold (closing the consistency gap with `Float`, which already folded `finite?` / `infinite?`), as do `Float#nonzero?` / `#integer?`.
  - `String#grapheme_clusters` lifts to a per-grapheme `Tuple`, the extended-grapheme-cluster sibling of the already-folded `chars`.
- **[cli]** `rigor check` now warns when a configured value silently resolves to nothing — the typo class that loads zero signatures or leaves a suppression inert, where the only symptom is a confusing downstream error.
  - Previously each of these was filtered without a word: a missing RBS path, for instance, turned every call into the types it was meant to cover into a `call.undefined-method` at `evidence_tier: high`, so a one-character mistake could read as hundreds of real errors.
  - The audit covers `signature_paths:` (missing, a non-directory, or holding no `.rbs`), `libraries:` (a name RBS does not recognize), `disable:` / `severity_overrides:` (a rule id naming no actual rule under a built-in family; plugin and `rbs_extended.*` ids are left alone), and `bundler.bundle_path` / `bundler.lockfile` / `rbs_collection.lockfile` (a configured path that does not exist).
  - Each finding is emitted per entry on STDERR and rides into the `--format=json` payload under a `config_warnings` array (each tagged with a `kind`), so CI and framework consumers can assert on them.
  - It stays a warning, not a hard error: an unset default (auto-detected `<root>/sig`, auto-detected bundle) is never warned about, so a correctly-configured project sees nothing.
- **[cli]** `rigor coverage --protection --mutation --with-tests` adds a *dynamic* protection axis: for every type-visible mutation Rigor's analysis misses, it runs your test suite and reports whether a test catches it, fusing static type-protection and dynamic test-protection into one map ([ADR-70](docs/adr/70-fused-protection-coverage.md)).
  - Each dispatch site is classified type-protected, test-protected, or unprotected (the ranked "add a type or a test here" list), so the report names the cheaper missing axis instead of a single number.
  - The test runner is the `--test-command` hook (default `bundle exec rake`) run with Bundler's environment stripped; the suite must pass on clean code first, and the expensive run is paid only for mutants the type checker did not already kill.
  - `--include-dynamic` extends the overlay to `Dynamic`-receiver call sites, where a test is the only possible protection, and `--limit N` (with `--seed`) caps the measurement to a deterministic per-file sample.

### Fixed

- **[cli]** A `severity_overrides:` (or `disable:`) value written as a bare `off` in `.rigor.yml` no longer crashes `rigor check` with a raw `NoMethodError` backtrace.
  - YAML 1.1 parses unquoted `off` / `on` / `no` / `yes` as booleans, so `flow.dead-assignment: off` reached the loader as `false`; it now raises a clear `ArgumentError` that names the key and tells you to quote the severity (e.g. `"off"`).
- **[inference]** An option hash populated through a helper inside an escaping block — the `OptionParser.new { |opts| define_options(opts, options) }` idiom — no longer keeps its literal default values, so a later guard like `if options[:mutation] && !options[:protection]` stops folding to a false `flow.always-truthy-condition` warning.
  - The escaping-block content floor ([ADR-57](docs/adr/57-self-call-return-adoption.md)) now also follows a self-call in the block body that escape-mutates one of its arguments, not just direct writes in the block itself.
- **[packaging]** The published gem now ships Rigor's bundled RBS data — the `data/vendored_gem_sigs/` per-gem stubs (nokogiri, pg, redis, mysql2, and others) and the `data/core_overlay/` core reopenings, including the v0.2.0 StringScanner fix.
  - The gemspec's `spec.files` glob matched only `data/builtins/**/*.yml`, so an installed `rigortype` gem silently lacked these `.rbs` files and produced extra `call.undefined-method` false positives a from-source checkout did not.

## [0.2.0] - 2026-06-17

v0.2.0 is Rigor's first publicly-announced (general / evaluation) release, governed by [ADR-50](docs/adr/50-release-engineering-and-stability-strategy.md): it publishes the enumerated public-compatibility surface ([`docs/compatibility.md`](docs/compatibility.md)) as a trial commitment toward the v1.0.0 freeze, and ships a bleeding-edge opt-in for previewing a future major's diagnostics. The headline is detection "teeth" — `call.undefined-method` and `call.argument-type-mismatch` now reason about union, refinement, and multi-overload receivers they used to bail on, surfaced by a new analyzer self-testing harness ([ADR-62](docs/adr/62-mutation-testing-teeth-measurement.md)) and measured by a new type-protection coverage report ([ADR-63](docs/adr/63-type-protection-coverage.md)). It also widens constant folding to more builtin methods and predefined constants, folds `Struct.new` value objects, and adds agent-facing diagnostic metadata (an evidence tier and a documentation URL). Fixes include several real-world false-positive removals plus a handful of crash and packaging issues from developer feedback.

### Added

- **[inference]** `call.undefined-method` now fires on a *union* receiver when the method is absent on every arm (`String | Symbol` responds to a method only if both do), where the scalar existence check previously bailed on any union.
  - Conservative by construction: any arm that is `Dynamic`, an unknown / open / source-declared class, the generic `Class` / `Module` metaclass, or `nil`-bearing suppresses it, and the union must have at least two distinct arm classes (a same-class shape join like `Hash[K1, V1] | Hash[K2, V2]` is left to the scalar rule).
- **[inference]** Refinement and difference receivers now get call-rule teeth: a bounded-integer (`positive-int`, `int<1,5>`), string-family (`non-empty-string`), or non-empty / non-zero (`non-empty-array`, `non-zero-int`) receiver resolves to its base class for dispatch, so `call.undefined-method`, `call.wrong-arity`, and `call.argument-type-mismatch` reason about it instead of bailing on "no single concrete class".
- **[inference]** `call.argument-type-mismatch` now fires on an argument to a multi-overload method that no overload accepts — both a `nil` argument to a parameter that rejects nil and a wrong-*typed* (non-nil) argument — closing the largest false-negative cluster the mutation sweep surfaced ([ADR-64](docs/adr/64-non-nil-argument-type-mismatch.md)).
  - The nil channel reports `5 * nil`, `"a" + nil`, and `[1, 2, 3].fetch(nil)`, deciding nil-admittance on the RBS parameter type so it sees through interface aliases (`string`, `int`) and generic aliases (`range[int?]`); a declaration-sourced ivar `nil` stays excused ([ADR-58](docs/adr/58-ivar-field-typing.md)).
  - The non-nil channel reports `[1, 2, 3].fetch("x")` while leaving `.fetch(2.0)` clean (`Float#to_int`), excludes the `coerce`-dispatch operators (`+ - * / < …`, where a non-`Numeric` argument may still be valid), and fires only on an argument typing to a single concrete RBS-known class that every overload rejects.
- **[inference]** RBS class aliases (`class Mutex = Thread::Mutex`, and any `X = Y`) now resolve to their target's method surface, so dispatch types precisely and a genuinely missing method on the alias fires `call.undefined-method`.
- **[inference]** The constant-folding catalogue covers more pure builtin methods, so more statically-known expressions fold to a precise `Constant` or `Tuple` (each verified against the live MRI value).
  - Scalar folds: `Integer#[]` / `#ceildiv` / `#to_r` / `#to_c`, `Float#quo` / `#to_r` / `#rationalize`, `String#casecmp` / `#casecmp?` / `#sum`, `Symbol#succ` / `#next`, and the full `Rational` and `Complex` arithmetic / comparison surfaces.
  - Collection folds lift to a `Tuple`: `String#codepoints`, `Integer#digits(base)` / `#gcdlcm`, `String#partition` / `#rpartition`, `Range#sum` / `#first(n)` / `#last(n)` / `#take(n)`, and `Array#minmax` / `#join`.
  - A NaN-defence guard declines any fold whose result is a NaN `Float` (or a NaN-bearing `Complex`), whose non-reflexive `==` would corrupt union dedup.
- **[inference]** Predefined Ruby / stdlib constants now receive refined types instead of the widest RBS declaration.
  - Tier 1 folds the cross-implementation-invariant numerics — `Math::PI`, `Math::E`, and the IEEE 754 limits `Float::INFINITY` / `MAX` / `MIN` / `EPSILON` — to `Constant[Float]`, so `Math::PI * 2` folds precisely (`Float::NAN` is excluded).
  - Tier 2 resolves core / stdlib constants like `RUBY_VERSION` to a refined `String` carrier via the analyzer's own runtime, while project-defined constants fall through unchanged.
- **[inference]** `Struct.new` value objects now fold member reads to precise types, the mutable sibling of the `Data.define` folding from v0.1.17 ([ADR-48](docs/adr/48-data-struct-value-folding.md)).
  - `Struct.new(:x, :y).new(1, 2).x`, `Point.new(1, 2).x`, and a bound `p = Point.new(1, 2); p.x` all type `1`, with positional and `keyword_init: true` construction and the `.members` / `.to_h` / `.deconstruct` / `.with` projections.
  - Because a `Struct` is mutable, a read off a fresh instance always folds but a read off a bound local folds only when the local is provably never mutated, aliased, or escaped — anything written, aliased, or passed away widens to `Dynamic[top]` rather than fold a stale value.
- **[cli]** `rigor coverage --protection` reports type-protection coverage — not how precise the types are but whether Rigor could catch a bug at each dispatch site — with a ranked "add a type here" list, a `--threshold` gate, and `--format json` ([ADR-63](docs/adr/63-type-protection-coverage.md)).
- **[cli]** `rigor coverage --protection --mutation` measures protection directly by introducing type-visible breakages at each dispatch site and reporting how often Rigor catches them, defaulting to the git-changed files ([ADR-63](docs/adr/63-type-protection-coverage.md) Tier 2).
  - The framing is always effectiveness / where-to-add-a-type, never raw "survival"; it productizes a supported subset of the dev-only mutation harness ([ADR-62](docs/adr/62-mutation-testing-teeth-measurement.md)).
- **[inference]** `rigor coverage --protection` now credits call-site-inferred parameter types, so an undeclared `def` parameter that flows into a receiver counts as protected instead of reading as `Dynamic` ([ADR-67](docs/adr/67-parameter-type-inference.md)).
  - The inference is precision-additive — it lives only as a method-body local, never an RBS contract, so it cannot fire a parameter-boundary diagnostic at a caller — and a `check` run stays byte-identical (only the protection scan consults it).
- **[cli]** `rigor check --bleeding-edge[=ids]` / `--no-bleeding-edge` override the configured `bleeding_edge:` selection for a single run, with the same CLI-over-config precedence as `--workers` ([ADR-50](docs/adr/50-release-engineering-and-stability-strategy.md) § WD2).
  - The overlay is empty in this release, so the flag is a no-op on diagnostics today; inspect the overlay and the active selection with `rigor show-bleedingedge`.
- **[cli]** Every built-in diagnostic now carries an `evidence_tier` (`high` / `medium` / `low`) and a stable `documentation_url` on `rigor check --format json` and via `rigor explain` ([ADR-65](docs/adr/65-diagnostic-evidence-tier-and-doc-url.md)).
  - The tier is Rigor's own confidence that a firing is a true positive, derived from the rule's gates; it is orthogonal to severity and never feeds gating, only routing attention (filter with `jq '.diagnostics[] | select(.evidence_tier == "high")'`).
- **[cli]** `rigor check --coverage` adds a type-precision coverage block to a check run, so one run reports both what fired and how much of the analyzed surface Rigor could type; it is off by default.
- **[environment]** `bundler.auto_detect` now also honours a user-global Bundler path (`~/.bundle/config`) as a last resort when a project has no in-tree bundle, resolving it relative to the project root and only when it points at a real directory.

### Changed

- **[inference]** `numeric-string` now means any single complete Ruby numeric literal — exactly the syntax that evaluates to a `Numeric` — rather than the previous signed-decimal-only definition, by delegating the predicate to the Prism parser.
  - It accepts hex / octal / binary integers, underscore separators, scientific floats, and the `r` / `i` suffixes while rejecting doubled signs, partial literals, and non-ASCII digits; two narrowings that relied on the old digit-only meaning (`Integer(numeric-string)` and `numeric-string#to_i`) were made sound for the wider grammar.

### Fixed

- **[inference]** A reference to a constant resolved through a `const_missing` hook whose optional library is absent (e.g. `Digest::UUID`) no longer crashes the whole run with `LoadError`; the lookup now resolves each path segment without triggering autoload side effects and rescues `LoadError` as a safety net.
- **[inference]** A `StringScanner` named-capture access (`scanner[:key]`) no longer false-fires `call.argument-type-mismatch`; a core overlay supplies the `(Integer | String | Symbol)` index overload that the pinned `rbs` 4.0.2 gem omits (newer `ruby/rbs` already carries it), so the new multi-overload argument check sees the `Symbol` / `String` form as valid.
- **[inference]** A local conditionally assigned across an `if / elsif / else: raise` chain is no longer false-flagged as possibly `nil` when one arm is `Dynamic`-typed and another concrete.
  - The inner `elsif … else raise` returned the bare predicate-narrowing scope with the local unbound, so the outer `if`'s merge nil-injected it; both the `if` and `unless` early-exit paths now carry the executed then-body's scope forward, mirroring the `case`/`when` rule. Surfaced by the [liquid v5.x regression sweep](docs/notes/20260616-liquid-v5.x-regression-sweep.md).
- **[inference]** A `break`-path binding inside a `for` / `while` / `until` loop is no longer dropped from the post-loop scope, fixing a false `flow.always-truthy-condition` on the common "set a flag and break" search idiom.
  - The scope at each `break` is joined into the loop continuation — precise, not a syntactic over-approximation, and lexically scoped so a `break` in a nested loop or block does not leak. Design in [`docs/notes/20260615-loop-break-binding-propagation-design.md`](docs/notes/20260615-loop-break-binding-propagation-design.md).
- **[inference]** Non-reproducible builtin results are no longer folded to a `Constant`: `#hash` (salted with a per-process SipHash seed) and `String#crypt` (the platform `crypt(3)`).
  - Folding either baked one analysis process's value into the inferred type and the on-disk cache, wrong in every other process; a universal guard now blocks `hash` / `object_id` / `__id__` across every catalogued class, while the deterministic siblings (`inspect`, `to_s`) still fold.
- **[inference]** `Integer(decimal-int-string)` and `decimal-int-string#to_i` / `#to_int` no longer narrow to `non-negative-int`, since the carrier admits a leading sign (`Integer("-7") == -7`); they now yield the full signed `int` range, keeping a precise `IntegerRange` for downstream narrowing.
- **[inference]** The opt-in `call.self-undefined-method` rule ([ADR-24](docs/adr/24-self-method-call-resolution.md) slice 4, off by default) sheds three false-positive classes its corpus evaluation surfaced — universal-base receivers (`Object` / `Kernel`), abstract / template-method base classes (suppressed when the missed method is defined on a known subclass), and dynamic non-constant superclasses (`< DelegateClass(Array)`).
  - All three are pure narrowings (a genuine typo still fires); the rule still ships off by default, since the evaluation found further false-positive classes (C-extension and metaprogrammed surfaces) the per-class scan cannot enumerate.
- **[sig-gen]** `rigor sig-gen --write` no longer emits a `module` wrapper where the source declares a compact-path `class` (`class Foo::Bar`), a `class` / `module` collision that aborted the whole RBS env build with `RBS::DuplicatedDeclarationError`.
  - The writer now folds every candidate's per-file namespace-kind map into one run-level view before grouping, so an authoritative `class Foo` recorded elsewhere governs the wrapper keyword. Surfaced by the 2026-06-16 protection-uplift pilot sweeping the `parser` gem.
- **[cli]** `rigor explain call.unresolved-toplevel` now resolves — the [ADR-34](docs/adr/34-toplevel-unresolved-self-call-default.md) rule was missing from the catalogue despite being live since v0.1.14 — and a completeness spec now asserts every rule has a catalogue entry.
- **[packaging]** The Docker build-context ignore file is scoped to the Dockerfile (`Dockerfile.dockerignore`) instead of a repo-wide `.dockerignore`, so external tools embedding the rigor source via BuildKit `--build-context` no longer get an empty context.
