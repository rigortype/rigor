# Diagnostic Policy

Rigor SHOULD prefer precise diagnostics over silent widening. This document defines the diagnostic identifier taxonomy, display rules, and the suppression-marker grammar.

The `static.*` family splits into use-site guards (`static.value-use.*`) and incomplete-inference cutoffs (`static.incomplete-inference.*`) per [ADR-100](../adr/100-static-diagnostic-family-and-void-origins.md); its first implemented identifier is `static.value-use.void` (an author-declared `-> void` return used in value context), shipped behind the `use-of-void-value` bleeding-edge feature. The budget-cutoff identifiers are still reserved (see [inference-budgets.md](inference-budgets.md)) and **not yet wired**. The display rules for negative facts and difference types are in [type-operators.md](type-operators.md). The display rule for `Dynamic[T]` is here.

## Diagnostic guidelines

> **Status.** These guidelines state the intended policy for each situation, not a claim that
> every one is implemented. A guideline whose diagnostic would live in a family marked
> **Reserved** in the taxonomy below (`compat.*`, `hint.*`, `generated.*`), or in the
> `static.incomplete-inference.*` budget half, describes intent. The `void`-value guard is now
> implemented for the direct author-declared case ([special-types.md](special-types.md) § `void`;
> [ADR-100](../adr/100-static-diagnostic-family-and-void-origins.md)), behind `bleeding_edge:`. See
> [ADR-92](../adr/92-normative-status-fidelity.md).

- Using `void` as a value is a primary diagnostic (`static.value-use.void`, opt-in behind the `use-of-void-value` bleeding-edge feature); downstream recovery uses `top` and SHOULD avoid duplicate cascade reports for the same expression.
- Calling a method on `top` without proof is a diagnostic.
- Calling a method on raw `untyped` is allowed but SHOULD be traceable to an unchecked boundary.
- Calling a method on `Dynamic[T]` MAY use the static facet `T`, but diagnostics SHOULD be able to explain that the proof depended on a dynamic-origin value.
- Strict dynamic modes MAY report dynamic-to-precise assignments, arguments, returns, and generic-slot leaks such as `Array[Dynamic[top]]`.
- Strict static modes MAY additionally report method calls or branch proofs whose safety depends on dynamic-origin facts rather than checked static facts.
- A branch narrowed by a negative fact SHOULD display that fact when it is useful, for example `String - ""` or `~"foo"`.
- Diagnostics SHOULD prefer explicit domain-bearing displays such as `String - "foo"` when a bare `~"foo"` would be ambiguous.
- Writing through a read-only shape entry is a diagnostic when Rigor has that fact.
- Passing unexpected keys to a closed keyword or options-hash shape is a diagnostic.
- Invalid or contradictory `RBS::Extended` annotations are diagnostics.
- Method implementations are checked against accepted signature contracts regardless of source: inline `#:`, `# @rbs`, rbs-inline parameter annotations, generated stubs, and external `.rbs` declarations all have the same implementation-side force.
- When inference stops because of recursion, operator ambiguity, dynamic dispatch, or budget exhaustion, Rigor MUST report the cutoff and SHOULD suggest a boundary contract rather than pretending the inferred type is precise.
- When an explicit nominal parameter type rejects a call but the method body only requires a smaller inferred capability role, Rigor MAY suggest generalizing the public signature to an interface rather than adding an ad hoc union.
- Diagnostics that involve plugin, generated, or `RBS::Extended` facts SHOULD carry stable identifiers. Public identifiers SHOULD use prefixes that make the source family clear, such as `plugin.<plugin-id>.<name>`, `rbs_extended.<name>`, or `generated.<provider>.<name>`, while internal diagnostic metadata MAY retain richer provenance.
- Losing precision during RBS export SHOULD be reportable when users request explanation or strict export mode.

## Identifier taxonomy

Diagnostic identifiers are hierarchical so plugin authors, RBS metadata, and user suppression markers can address them without colliding with internal numbering. Identifiers are stable within a major version. New diagnostics MAY be added under any prefix; renames or removals require a deprecation window.

A family row carries a **bolded status marker containing the phrase "as of this writing"** when it
does not resolve to a diagnostic the engine emits today — the same idiom
[inference-budgets.md](inference-budgets.md) uses for the unwired `budgets:` surface. Two such
statuses occur: **Reserved** names an identifier space that is claimed but carries no
implemented diagnostic, and **Not a diagnostic family** names identifiers that exist but reach the
user through another surface. Reserving the space *is* a decision — it keeps
the family free of colliding claims — but it is not a statement that the diagnostics exist.
Per [ADR-92](../adr/92-normative-status-fidelity.md), a family listed here without a
Reserved marker MUST have at least one implemented identifier; `spec/docs/manual_drift_spec.rb`
enforces this table against the engine's emitted vocabulary.

| Prefix | Use |
|---|---|
| `dynamic.*` | `untyped` and `Dynamic[T]` boundary crossings, unchecked generic leaks, and method calls whose proof depends on dynamic origin. Includes `dynamic.dependency-source.*` (e.g. `gem-not-found`) for the opt-in gem-source-inference path per [ADR-10](../adr/10-dependency-source-inference.md) (analyzer contract: [`docs/internal-spec/dependency-source-inference.md`](../internal-spec/dependency-source-inference.md)). |
| `static.*` | Static checks that stopped short of a proof, split by *which way* they fell short ([ADR-100](../adr/100-static-diagnostic-family-and-void-origins.md)). **`static.value-use.*`** — a value that demands proof reached a use position: `static.value-use.void` (implemented, see the row below) and `static.value-use.top` (the unguarded-`top`-call half, [special-types.md](special-types.md) § `top`; no implementation and no ADR yet). **`static.incomplete-inference.*`** — inference gave up and widened: the budget-cutoff identifiers (`.recursion`, `.union-size`, …) tracked by [ADR-41](../adr/41-inference-budget-design.md) (Proposed) / [#158](https://github.com/rigortype/rigor/issues/158) and marked at their source in [inference-budgets.md](inference-budgets.md) § "Budget table", authored `:info`, remain deferred with no implemented id. |
| `static.value-use.void` | An author-declared `-> void` return used in value context (an assignment right-hand side, a call receiver, or a call argument): the value the author said not to rely on was recovered to `top` and used. Both the direct-dispatch case ([ADR-100](../adr/100-static-diagnostic-family-and-void-origins.md) WD2) and the transitive / ancestor-fallback case (WD4, carried by `Inference::VoidTailSummary`). Authored `:warning`, resolved `:off` by every profile and promoted to `:warning` only by the `use-of-void-value` bleeding-edge feature — a new required diagnostic is an [ADR-50](../adr/50-release-engineering-and-stability-strategy.md) WD1 compatibility change. |
| `flow.*` | Control-flow narrowing failures, equality and predicate refinement issues, fact-stability violations |
| `compat.*` | **Reserved — no implemented identifiers as of this writing.** RBS, rbs-inline, and Steep-compatible signature compatibility. A founding-era reservation ([ADR-1](../adr/1-types.md)); the shipped signature-compatibility rules live under `def.override-*` ([ADR-35](../adr/35-override-signature-compatibility.md)) instead. |
| `call.*` | Method-call-site diagnostics: `call.undefined-method` (the method is not defined on the receiver's statically known class), `call.self-undefined-method` (an implicit-self call resolves to no method on a confidently-closed standalone class, [ADR-24](../adr/24-self-method-call-resolution.md) slice 4 — consumes the engine's own resolution miss, gated to a standalone project class with a complete in-file method surface, ships `:off` pending an external corpus FP gate), `call.unresolved-toplevel` (a top-level implicit-self call resolves against no same-file `def`, `pre_eval:` patch, or `Kernel` / `Object` method, [ADR-34](../adr/34-toplevel-unresolved-self-call-default.md)), `call.wrong-arity` (the positional-argument count matches no signature; a `.new` whose resolved `initialize` is the `::BasicObject` fallback MUST NOT witness on any receiver other than `::BasicObject` / `::Object` themselves — no loaded RBS declared a constructor there, and an absent declaration is not evidence of a nullary one, [#917](https://github.com/rigortype/rigor/issues/917)), `call.argument-type-mismatch` (an argument provably violates the parameter contract), and `call.possible-nil-receiver` (the receiver is `T \| nil`, at least one non-`nil` arm names a concrete class, and the method is not defined on `NilClass` — a union whose non-`nil` arms are all nameless (`Dynamic` / `top` / `bot`) MUST NOT witness, since nothing there can answer whether the method exists). |
| `def.*` | Method-definition diagnostics. Includes the override signature-compatibility family `def.override-visibility-reduced` / `def.override-return-widened` / `def.override-param-narrowed` ([ADR-35](../adr/35-override-signature-compatibility.md)), which verify an override against the signature it inherits from a project-defined ancestor. They fire only when both the override and the shadowed ancestor carry an author-supplied signature (inference-only either side stays silent) and map severity through `severity_profile:`; the Liskov reasoning is in [robustness-principle.md](robustness-principle.md). |
| `effect.*` | Effect-label contracts ([ADR-103](../adr/103-effect-labels.md); the label language is [effect-labels.md](effect-labels.md)). The whole family is inert without an `effects:` block. `effect.envelope-exceeded`, `effect.liskov-widened`, `effect.unknown-label` and `effect.annotations-unchecked` are implemented (see the rows below). One further identifier is reserved with no implemented diagnostic: `effect.discarded-pure-result` — the non-bang footgun, gated additionally by the catalogue's `raises` facet and shipping `:off` in every profile pending a corpus gate, tracked by [#390](https://github.com/rigortype/rigor/issues/390). The identifiers are reserved jointly with Steins, the sibling PHP analyzer, so a policy naming one reads the same against both. |
| `effect.envelope-exceeded` | A method's **proven** effect labels — its own body plus the transitive closure over the project methods it calls — are not subsumed by the envelope its author declared (`%a{pure}`, or `%a{rigor:v1:effect …}` on the method or distributed from its class), positioned at the Ruby `def` rather than at the `.rbs` line ([ADR-103](../adr/103-effect-labels.md) WD14; the semantics are [effect-labels.md](effect-labels.md) § Effect envelopes). False-positive-safe by two accepted constructions at once: **opt-in by author directive** — the envelope *is* the directive, so a firing is never unsolicited, the same construction as `rbs_extended.unsatisfied-conformance` — and **as strict as proven**: the declared lane, the exhaustiveness bit and taint are not read, so an unresolved call can never manufacture one, and `mutate.local` is tolerated by every envelope. Authored `:warning` (`:error` under `strict`). Silent without an `effects:` block, and under `effects.check: false`. |
| `effect.liskov-widened` | An override escapes the effect envelope written on the method it overrides ([ADR-103](../adr/103-effect-labels.md) WD1 / WD14; the semantics are [effect-labels.md](effect-labels.md) § Liskov inclusion). An envelope is a contract about a method, and `class PgRepo < Repo` says a `PgRepo` is usable wherever a `Repo` is, so a bound written on `Repo#find` binds `PgRepo#find` too: implementations may be purer than the bound they inherit, never less pure. Two comparisons, and an override is subject to exactly one — its **proven** labels against the inherited bound when it declares nothing of its own, and its **own declared** bound against the inherited one when it does, which is proven-independent (two authored bounds compared by subsumption) and is what keeps the two rules from putting two diagnostics on one line for one label. Both-sides-authored in the [ADR-35](../adr/35-override-signature-compatibility.md) sense: nothing fires unless someone wrote an envelope on the ancestor, so a firing is never unsolicited. **Nominal subclassing only** — an included module's method is not an override here, because Ruby's ancestry puts an includer's own `def` ahead of the module's rather than under it. Positioned at the override's Ruby `def`, where the fix goes and where `# rigor:disable` is read. Authored `:warning` (`:error` under `strict`). Silent without an `effects:` block, and under `effects.check: false`. |
| `effect.unknown-label` | A well-formed effect label the registry does not recognise after plugin load, named by an envelope (`%a{rigor:v1:effect …}` in `.rbs` or as an rbs-inline `# @rbs %a{…}` comment) or by a `.rigor.yml` label list (`effects.tolerated:` today). The whole tag fails open to ⊤ and the declaration stops bounding anything, which is silent by construction; this diagnostic is what keeps that silence honest ([effect-labels.md](effect-labels.md) § Unknown labels). Positioned at the **declaration** — the `.rbs` line, the `.rb` line for an inline annotation, or `.rigor.yml:1:1` for a config value, the `rbs.coverage.quarantined-signature` precedent — because there is no Ruby `def` that could carry the typo; Rigor does not read `# rigor:disable` comments out of `.rbs` or `.rigor.yml`, so those positions are suppressible through `disable:` and the baseline only. Fires only where label **intent is evident** (a near miss, a recognised sibling in the same list, a token of two or more dot segments, or a retired spelling): an effect vocabulary is open by construction, so a lone far-off word stays silent everywhere rather than nagging a project that is opening its own root. Authored `:info` (`:warning` under `strict`), and gated by `effects.check` exactly like `effect.envelope-exceeded` — opting into envelope enforcement is what turns on the diagnostic that says an envelope stopped enforcing. |
| `effect.annotations-unchecked` | The project's own signatures carry `%a{pure}` / `%a{rigor:v1:effect …}` while `.rigor.yml` carries no `effects:` block, so effect collection never runs and nothing checks them ([ADR-103](../adr/103-effect-labels.md) WD13). The two rules this reconciles pull against each other: an annotation must never turn collection on (one line in one signature file would otherwise impose a project-wide cost on every run), and it must never be silently inert either. One diagnostic per run, positioned at the first such annotation rather than at `.rigor.yml`, because the inert thing is what the author wrote. `effects: {}` and `effects: {check: false}` are both deliberate answers and silence it. Authored `:info` in every profile, `strict` included: a residual that failed a build would punish a project for carrying an annotation it has not opted into checking. Both annotation lanes — `sig/*.rbs` and the rbs-inline comments a plugin synthesizes — MUST be read on every run, one that analyses no file included (a warm `--incremental` whose closure is empty): WD13 refused to build an environment just to find this `:info`, but since [#784](https://github.com/rigortype/rigor/issues/784) the empty path resolves one whenever the project has files and anything on it still needs one, so the inline stratum is read off that environment and the lane no longer decides — and since [#794](https://github.com/rigortype/rigor/issues/794) that resolve is DEMAND-DRIVEN: this lane asks for an environment exactly when the plugin registry declares a source-RBS synthesizer, which is the only thing `virtual_rbs` can hold, so a project with none reads the same empty carrier without building one ([#441](https://github.com/rigortype/rigor/issues/441)); the former empty-run carve-out is retired ([#788](https://github.com/rigortype/rigor/pull/788)). The same holds on every worker-pool backend, whose coordinator never analyses a file: each backend's coordinator-side environment — the fork pool's pre-fork `WorkerSession#environment`, the Ractor pool's cache-prewarm environment — MUST carry the inline stratum out before any worker is dispatched, beside the project-signature state it already takes there ([#798](https://github.com/rigortype/rigor/issues/798)), and that environment MUST be built with the loaded plugin registry over the project's whole file list, as its workers build theirs: an environment built without either collects no plugin-synthesized RBS at all, so a lane read off it answers "no annotation" whatever the project's rbs-inline comments say. The Ractor pool's was built with neither and never read, so under `RIGOR_POOL_BACKEND=ractor` an annotation living only in an rbs-inline comment had no producer ([#813](https://github.com/rigortype/rigor/pull/813)). |
| `rbs_extended.*` | `RBS::Extended` payload validity, version compatibility, and conflict reports. Includes `rbs_extended.unsatisfied-conformance` ([rbs-extended.md](rbs-extended.md) § "Explicit conformance directive"): a class carrying `%a{rigor:v1:conforms-to _Interface}` either is missing a method the named structural interface requires (presence) or provides one whose RBS signature is not a behavioural subtype of the interface's (covariant return / contravariant params). The signature tier is FP-safe because both sides are authored RBS (the ADR-35 both-sides-authored construction) and compares only single-method-type, non-`Dynamic` positions, so it never frightens a class that already satisfies the interface. Authored `:warning` (`:error` under `strict`); the directive is opt-in, so the diagnostic is never unsolicited. An unresolvable interface name surfaces as `dynamic.rbs-extended.unresolved` `:info` instead. The PHPStan-style integer range `int<a, b>` ([ADR-109](../adr/109-ruby-native-range-notation.md) WD3) still resolves for one deprecation window and surfaces as `dynamic.rbs-extended.deprecated-form` `:info`, one row per `(payload, replacement, path, line, column)` positioned at the annotation, naming the `Integer[a..b]` spelling to write; the alias is removed at the next compatibility break. Authored `:info` and never louder, since the annotation resolved and the run is as green as it was. Both rows are positioned at the `%a{rigor:v1:conforms-to …}` the author wrote — there is no Ruby `def` a missing method could be reported at — and that position MUST NOT depend on cache state: the annotation's line and column are read off an `RBS::Location` that a warm run gets back from the ADR-54 environment cache, so the cache MUST carry an annotation's POSITION as well as its buffer name, the way `definition-build-failed` requires the name ([#799](https://github.com/rigortype/rigor/issues/799)). Collapsing it to `1:1` warm broke more than the row's readability: `--verify-incremental` normalises rows by position and only one side of its comparison runs against the cached environment, so the check FAILED on every project carrying an unsatisfied directive, and a warm `--incremental` run moved the row on a tree that had not changed. A malformed higher-kinded directive — a `rigor:v1:hkt_register` / `rigor:v1:hkt_define` ([rbs-extended.md](rbs-extended.md) § "Higher-kinded type directives") carrying an un-namespaced `uri=`, a non-positive `arity=`, a `variance=` list whose length does not match the arity or whose entries are not `out` / `in` / `inv`, a missing `params=` or `body=`, a body the [ADR-20](../adr/20-lightweight-hkt.md) parser cannot read, or an unrecognised `bound=` — surfaces as `dynamic.rbs-extended.hkt-directive-invalid` `:info`, one row per `(message, path, line, column)`, positioned at the annotation's `.rbs` line and falling back to `.rigor.yml:1:1` when the parser had no location. The directive parsers are fail-soft by construction: the type constructor simply stays unregistered and every `App[<uri>, …]` carrier naming it reads its bound (`Dynamic[top]`), which is indistinguishable from a signature that never mentioned it, so this row is the only thing that tells an author their registration did not take. Authored `:info` and never louder — a run carrying a malformed directive was green before the row existed and MUST stay green. Two constraints bind the plumbing, and each one is a way the row could be silent again. **The entry MUST reach the run's `RbsExtended::Reporter`**, whose surface is `record_unresolved` / `record_lossy_projection` / `record_hkt_error`: the parser used to write only to a duck-typed `#record` / `#<<` that the production reporter does not have, so every declined directive was dropped in every real run while the scan's own contract claimed an `:info` entry was recorded ([#785](https://github.com/rigortype/rigor/issues/785)); a duck-typed fallback MAY stay for collecting doubles, but it MUST NOT be the only arm. And **the entry MUST carry its position as `(path, line, column)` primitives, not as the `RBS::Location`**: the stream is drained out of pool workers exactly as `rbs.coverage.hkt-scan-failed` is, and for the same reason (under the pool the coordinator never demands the scan), over a channel that Marshals its payload — which an `RBS::Location` cannot cross, being a C-extension object with no `_dump` — and whose dedup would not collapse two workers' copies of one row anyway, since an `RBS::Location` compares equal only against a location over the same `RBS::Buffer` object. **That second constraint binds all three of the reporter's streams**, not only the hkt one it was written for: `dynamic.rbs-extended.unresolved` and `dynamic.shape.lossy-projection` carried the `RBS::Location` object itself until [#805](https://github.com/rigortype/rigor/issues/805), and a project whose `sig/` produced a single such event killed every fork-pool worker at drain time — the run still reported the row, from the coordinator's in-process re-analysis, but lost its parallelism and gained a `pool-degraded` warning the project could do nothing about. A record method on the reporter MUST therefore take the position triple rather than a location: a door that accepts an `RBS::Location` is the door the next stream reintroduces this through. |
| `rbs.coverage.*` | RBS environment coverage / well-formedness telemetry. `rbs.coverage.missing-gem` reports locked gems with no available RBS; `rbs.coverage.synthesized-namespace` reports project `signature_paths:` RBS that declares qualified names (`class Foo::Bar`) without the enclosing namespace — invalid upstream (`rbs validate` rejects it), which Rigor synthesizes a `module` for so the signatures still resolve. Both authored `:info`. `rbs.coverage.quarantined-signature` reports a `signature_paths:` `.rbs` that does not parse and was therefore SKIPPED: the rest of the environment still loads, but the types that file declared are absent, so the run is *quieter* rather than cleaner. Authored `:warning` (a broken sig set must not silently pass, but neither may an upgrade turn a green build red); the `reject-unparseable-signatures` bleeding-edge feature promotes it to `:error`, which is the intended default at a future major. `rbs.coverage.environment-build-failed` is its twin one tier louder in consequence: a `signature_paths:` entry that parses fine but redeclares a constant or class Rigor's bundled RBS already ships (`RBS::DuplicatedDeclarationError` at resolve) collapses the *whole* RBS environment to nil, so every type-of query reads `Dynamic[top]` and most diagnostics stop firing — the run is *empty* rather than clean. The diagnostic names the conflicting signature files (lifted off the raised error's declarations). Authored `:warning` for the same reason as its twin — the conflict is typically between the user's `sig/` and Rigor's *own* bundled RBS, so an `:error` default would let a Rigor release turn a green build red with no user change — and the same `reject-unparseable-signatures` bleeding-edge feature promotes it to `:error`. `rbs.coverage.definition-build-failed` sits BETWEEN those two by consequence, and is the third rung of the same ladder: a quarantined file removes what one *file* declared, this removes what one *class* declared, an environment-build failure removes everything. It reports a class whose `RBS::DefinitionBuilder` build raised — typically `RBS::DuplicatedMethodDefinitionError`, two signature sources declaring the same member (a project `sig/` carrying a vendored *copy* of a bundled plugin's `.rbs` is the shape that motivated it). The class stays KNOWN — `class_known?` consults the known-class-name table, never a definition build — but loses its method surface, so every call on it, real methods and typos alike, reads `Dynamic[top]` and stops being checkable; when the collision is on a class others inherit, the whole bundled type universe goes with it and the run comes back EMPTY rather than clean. Rigor MUST NOT answer this by dropping the class to genuinely-unknown: that also removes diagnostics, so it is not louder, and it changes `Dynamic[top]` semantics for every rule that consults `class_known?`. The failure is made reportable; the class is not made invisible. One diagnostic per RUN — a collision on a widely-inherited class fails every descendant, and thousands of rows about one `.rbs` line is noise rather than visibility — naming the count, a sample of the failed classes, the first failure's error class and MEMBER, and the conflicting signature files. The member is required, and is read off the error object rather than out of its message, for two reasons: the failed classes are *descendants* of the class carrying the duplicate, so the list alone never names where the fix goes, and a message built from `RBS::Location`s used to read differently on a cache hit. The env cache dumps positions, but it MUST preserve each location's buffer NAME so a warm run names the same files a cold one does; where a name is absent anyway, the reconstructed sentinel MUST be filtered out of the file list rather than reported as a path. Definition builds are lazy (per class, on first demand), so the reported set is the classes whose METHOD SURFACE the run demanded — the per-file analysis, plus the user-authored `rigor:v1:conforms-to` conformance scan, which demands the definition of every annotated class — that is what the message promises, and it is the demand set that does not depend on cache state. Three consequences bind. **A demand that is Rigor's own MUST NOT contribute**: neither a whole-universe cache producer (the eager definition tables, and the tables a worker-pool pre-warm drives) nor the hierarchy oracle's ancestry lookup, which asks whether two classes are ordered rather than whether either one's methods resolve. Both were cache-state-dependent, and each made one `class Object` duplicate report a different class list per configuration — 1,336 classes under a cold-cache pooled run, and 1,337 under the DEFAULT `--workers=0` path, where nothing pre-warms the store before the first class comparison, against 3 elsewhere. **The report MUST be taken where a definition is DEMANDED, not where the build raises**, because those walks memoise their failures: a rescue-sited report says nothing about a class a walk already touched. And under a worker pool the diagnostic MUST be drained out of the workers, for the matching reason on the other axis: the coordinator never analyses a file, so its own loader never demands the failing class. Authored `:warning` for the reason both siblings are — the collision is typically between the user's `sig/` and Rigor's *own* bundled RBS, so an `:error` default would let a Rigor release turn a green build red with no user change — and the same `reject-unparseable-signatures` bleeding-edge feature promotes it to `:error`. `rbs.coverage.inline-annotations-unsynthesized` is the [ADR-93](../adr/93-default-rbs-inline-ingestion.md) WD3 standalone residual: the project carries rbs-inline annotation comments (`# @rbs …`, `#: <type>`) but the upstream `rbs-inline` library is not installed, so nothing synthesizes them and the annotated code reads `Dynamic[top]`. Emitted only when the library is absent (when it resolves, the auto-wired or explicitly configured plugin — including a deliberate `enabled: false` opt-out — handles it and this stays silent) and the project actually carries an annotation-shaped comment, detected by a coarse routing heuristic that excludes RDoc directives, never the upstream grammar (which is what is unavailable). Authored `:info`; Rigor never bundles `rbs-inline` ([ADR-0](../adr/0-concept.md) zero-dep). `rbs.coverage.hkt-scan-failed` is the narrowest rung of the build-failure ladder ([#784](https://github.com/rigortype/rigor/issues/784)), and it covers the TWO builds behind `Environment#hkt_registry`, told apart by the stage recorded with the failure. The `:scan` stage is the implicit-HKT scan over the loaded RBS `type` aliases ([ADR-20](../adr/20-lightweight-hkt.md) slice 5): it raised, so Rigor fell back to the bundled and plugin HKT registrations — a recursive `type` alias in the project's `.rbs` or an installed `rbs collection` no longer registers as a type constructor and reads its bound (`Dynamic[top]`) instead. The `:overlay` stage ([#791](https://github.com/rigortype/rigor/issues/791)) is the aggregation of the loaded plugins' manifest-declared HKT entries (`Plugin::Registry#hkt_overlay_registry`, which runs plugin-authored code): it raised, so Rigor fell back to the bundled registrations ALONE and still ran the `type`-alias scan on top of them — the plugin's type constructors read their bound, while the project's own `.rbs` overlay survives. Each stage MUST sit inside the seam and MUST leave the other running, and the row's wording MUST follow the stage: "the implicit HKT scan over RBS `type` aliases raised" is false for a plugin defect and would send a user to signatures that are not the problem, so the overlay wording names the plugin stage, the narrower fallback, and — whenever the raise is attributable to one plugin — that plugin's id. The slot is first-write-wins, so a run whose overlay AND scan both raise reports the overlay: it is the actionable one, since a plugin is what a user can remove. The scan is a shared, memoised build first demanded from inside a file's analysis, so without this row a raise landed in every file's `analyze_body` rescue and the run came back as one identical `internal analyzer error` per file with nothing saying the analyzer never ran ([#776](https://github.com/rigortype/rigor/issues/776)). The seam MUST rescue, record, and degrade rather than raise into per-file analysis — and, since the run demands the registry on its own behalf at sites that carry no rescue above them (below), a raise that escapes the getter does not degrade the run at all but aborts it, the memo holding only on success so the raise is re-attempted at every demand; the failure MUST be drained out of pool workers (the coordinator never analyses a file under the pool, so the drain is how its snapshot learns the outcome) and snapshotted after the file loop (the build is lazy), exactly as `definition-build-failed` is. ### RBS definition-build stderr fallback

The `rbs.coverage.definition-build-failed` diagnostic and the RBS definition-build stderr banner are separate outputs. A successful internal demand that visits many RBS classes MUST emit at most one bounded summary per loader instance, even when that loader later starts another internal-demand episode; the summary names the first failure seen by the internal traversal, while the diagnostic separately reports the classes the analysis demanded and carries the culprit member and signature files. Ordinary, analysis-driven definition demands retain their existing detailed warning behavior.

If an internal-demand episode records a definition-build failure and then raises before the run can assemble its diagnostic, Rigor MUST emit the detailed stderr warning for the first newly encountered failure in that episode, even if an earlier episode already emitted the loader-instance summary. This abort-time fallback is one warning for the episode and does not create a second `rbs.coverage.definition-build-failed` diagnostic.

## `Dynamic[T]` display rules

`Dynamic[T]` provenance is rendered by the diagnostic prefix family rather than by branch:

- Diagnostics outside the `dynamic.*` family render the narrowed static facet `T` with a small `from untyped` provenance note. The narrowed facet is what the user can reason about; the wrapped form would only add noise to messages that are not about the dynamic boundary itself.
- Diagnostics in `dynamic.*`, and explanations requested through `rigor explain` or `--explain`, show the full `Dynamic[T]` form, because that is exactly the information they exist to surface.
- Internal traces, cache keys, and plugin `Scope` queries always retain the full `Dynamic[T]` form regardless of how the message renders. Plugins that need the dynamic facet to compose a higher-tier diagnostic do not need to reconstruct it.

## Severity resolution

A rule emits each diagnostic with an *authored* severity (the rule's own default). Before the diagnostic reaches the result, the active severity profile and any per-rule overrides **re-stamp** that severity. In the suppression pipeline this sits between the inline markers and the baseline: inline `# rigor:disable` → **severity resolution** → project baseline ([ADR-22](../adr/22-baseline-and-project-onboarding.md)).

Two `.rigor.yml` keys drive it ([ADR-8](../adr/8-steep-inspired-improvements.md)):

- `severity_profile:` — one of `lenient` / `balanced` (default) / `strict`. Each profile is a per-rule table mapping a canonical rule id to a severity; the profiles trade breadth of `:error` for adoption-friendliness (`lenient` drops uncertain rules to `:warning`/`:off`, `strict` raises every rule to `:error`). A rule absent from the active profile's table keeps its authored severity.
- `severity_overrides:` — a `{ rule_id => severity }` map. A key is either an exact canonical rule id (`call.undefined-method`) or a **family wildcard** (`call`) matching every rule whose first dotted segment equals the key.

The resolved severity is one of `:error` / `:warning` / `:info` / `:off`; **`:off` drops the diagnostic entirely**. `Configuration::SeverityProfile.resolve` MUST apply this precedence (highest first):

1. A `nil` rule id keeps the authored severity (there is nothing to look up).
2. An exact `severity_overrides` entry for the rule id.
3. Otherwise a family-wildcard `severity_overrides` entry (the rule id's first segment).
4. Otherwise the active profile table's entry for the rule id.
5. Otherwise the authored severity.

An unknown `severity_profile:` value falls back to `balanced`. This resolution is what the `def.override-*` and `protocol_contracts:` ([ADR-28](../adr/28-path-scoped-protocol-contracts.md)) rules mean by "severity maps through `severity_profile:`": the rule emits at a fixed authored severity and the profile decides whether it surfaces as an error, a warning, or is suppressed.

## Suppression markers

Rigor recognizes an in-source comment grammar for suppressing specific diagnostics on a single line or across a whole file. The Rigor-native markers below are the shipped surface; recognizing other ecosystems' markers is a designed-but-unshipped compatibility extension.

### Rigor-native markers

Rigor-native markers use a Ruby comment grammar that mirrors PHPStan's annotation feel without inventing an application-side type DSL.

- **Line form**: `# rigor:disable <rule1>, <rule2>` — suppresses the listed rules on that physical line. `# rigor:disable all` suppresses every rule on the line.
- **File-level form** (v0.1.2): `# rigor:disable-file <rule1>, <rule2>` — suppresses the listed rules for every line in the file. `# rigor:disable-file all` suppresses every diagnostic in the file.

The rule list is comma- and/or whitespace-separated and uses the rule-ID prefixes above (`call.undefined-method`); the literal `all` keyword and short legacy aliases resolve through the same expansion `rigor explain` uses. There is no block-scoped (`start` / `end`) form.

Inline markers are applied before the configured `severity_profile:` and before the project baseline (ADR-22), which is the last suppression layer. See the User Manual § "Diagnostics" for the operational guide.

### Marker position within a comment

A marker is recognised **only when it opens the comment**: the implementation matches every suppression-recognition pattern anchored (`\A`) against the comment token, which begins at the `#`. Both real directive shapes have that form — the whole-line `# rigor:disable-file <rules>` and the trailing `expr # rigor:disable <rules>` — while a comment that merely *mentions* a marker has prose before the quoted `#` and MUST NOT be treated as a directive. This binds the `suppression.*` surveillance rules identically: a quoted marker is not a marker, so it fires neither `suppression.unknown-rule` nor `suppression.empty` nor `suppression.unknown-marker`. Two consequences follow from the same anchor and are normative: a doubled `##` comment (the doc-tool convention) never activates a marker, because the second `#` is neither whitespace nor the marker word; and an `=begin` / `=end` embedded-document comment never activates one either, because its token starts at `=begin`. Whitespace between the `#` and the marker word is allowed, and so is none at all (`#rigor:disable <rules>`).

Position within the *file* is unconstrained and stays so — a file-level marker is honoured wherever it appears, and a line-level marker binds the physical line its comment sits on.

The patterns were unanchored until issue #306, so a directive quoted anywhere inside a doc comment silently took effect — that mis-recognition suppressed every diagnostic on Rigor's own `lib/rigor/analysis/check_rules.rb`.

### Token resolution

A rule token — in a `# rigor:disable[-file]` marker or in the `.rigor.yml` `disable:` list — is **expanded to a set of canonical rule ids at parse time** (`resolve_rule_token`); the per-line / per-file suppression match is then an exact membership test of the diagnostic's canonical `rule` against that set. Four token shapes are recognised:

- `all` — the literal wildcard; suppresses every rule in scope. It is kept as the sentinel `all` rather than expanded to the rule list.
- A **legacy unprefixed alias** (`undefined-method`) — mapped to its single canonical id (`call.undefined-method`).
- A **family wildcard** — one of the diagnostic families `call` / `flow` / `assert` / `dump` / `def` — expands to every canonical id under `<family>.`.
- An **exact canonical id** (`call.undefined-method`) — kept as itself.

An unrecognised token is kept verbatim, so it only ever matches a diagnostic whose `rule` is literally that string (effectively a no-op — see _Validity rules_). A diagnostic whose `rule` is `nil` is never suppressed. Because family expansion happens at token time, the match itself never does prefix matching — it is always exact equality against the expanded canonical-id set.

### Ecosystem-compat markers (planned, not yet implemented)

Recognizing other ecosystems' markers — Steep's line-scoped `# steep:ignore`, and opt-in Sorbet `# typed:` / RuboCop `# rubocop:disable` via `.rigor.yml` `compat.*` switches — is a designed compatibility surface that has not shipped. Until it lands, only the Rigor-native markers above are honored, and a foreign marker is treated as an ordinary comment.

### Validity rules

- An unknown or empty marker keeps its documented matching behaviour (an unrecognised token is kept verbatim; a token-less marker suppresses nothing), but it is no longer silent: a marker token that resolves to no known identifier — not a canonical rule id, legacy alias, `all`, family wildcard, known non-catalogue engine id, or a dotted id under a known non-check family (including any `plugin.`-prefixed token, which is never flagged) — fires `suppression.unknown-rule`, and a marker listing no rules at all fires `suppression.empty` (both `:warning` in every profile). Validation happens before suppression filtering, so both diagnostics are themselves suppressible like any other rule; a comment that merely mentions the marker followed by non-token text remains an ordinary comment.
